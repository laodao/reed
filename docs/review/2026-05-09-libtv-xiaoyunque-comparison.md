# 对标 LibTV / 小云雀 · 我们平台的提升点（2026-05-09）

## 上下文

review 完资产域 prompt 装配后，下一步看更广的 AI 视频制作平台做法。本次对标：

- **LibTV**（LiblibAI 旗下，节点画布 + 多模型路由的"专业向"AI 视频平台）
  · 来源：用户提供的官方使用手册（feishu wiki 导出 docx）
- **小云雀**（字节剪映团队，移动端"一句话成片"AI Agent）
  · 来源：公开报道 + 官方介绍页

⚠ **重要立场**：不是 LibTV / 小云雀 做的就一定好。本文按"是否对 AI 友好（生成质量）+ 是否对用户简单便捷"两条标准独立判断每个能力，**给出借鉴 / 不借鉴的明确意见**。

## 1. 三个平台的核心定位

| 维度 | LibTV | 小云雀 | 我们（剧集制作） |
|---|---|---|---|
| **目标用户** | 专业 / 半专业创作者；长内容 + 灵活实验 | 移动端轻量用户；要求一句话出片 | 长篇剧集 / 短剧创作者；多分镜结构化生产 |
| **核心组织方式** | 节点画布（无限拖拽 + 5 类节点 + 连线传递） | 单视频片段（智能成片 / 一镜到底）| 项目→场景→分镜→关键帧 四层树状 |
| **入门门槛** | 中高；学习曲线长 | 极低；理解分析→创意脚本→剪辑成片 全自动 | 中等；6 stage 串行 |
| **典型用法** | 节点连接组装故事；脚本节点批量出图出片 | 智能成片 / 数字人口播 / 一镜到底 | 长篇剧集分镜化生产 + 关键帧链式生成 |

## 2. LibTV 的真实工作流（从手册细节里看）

LibTV 不只是"画布 + 节点"那么简单，关键能力栈：

### 2.1 五类节点 + 连线的语义

- 5 类节点：**文本 / 图像 / 视频 / 音频 / 脚本**
- 连线含义：**上游节点输出 → 下游节点输入**（作为 reference / prompt 上下文）
- 典型工作流：风格参考图 → 图像节点（生成）→ 视频节点（图生视频）

### 2.2 脚本节点 — 长内容入口

这是 LibTV 真正的"剧集"入口，不是画布拖节点：

- 上传剧本 / 角色图 / 参考视频 → AI 自动生成分镜脚本（表格形式）
- 表格字段：场景、画面、景别、镜头、运镜、时长、音效、对白等
- 一键批量：脚本表→分镜图像（每行出一张）→分镜视频（每行出一段）
- 图片节点支持单条或批量勾选；底部可选风格 / 模型 / 画幅 / 分辨率

**这跟我们 6 stage 是一回事**，但 LibTV 把 stage 折叠成"一个脚本节点 + 上下文菜单"。

### 2.3 视频主体库（KlingO1/O3 专属）

这条值得展开看，比公开材料里的"角色三视图"更有意思：

- **图片创建模式**：右键图片节点 → 创建主体 → 智能补全 2-3 张其他视角图 → 填名称 + 添加音色（5-30s 音频）→ 一键智能生成主体描述（**字段不止备注，参与生成时被转换成 prompt 增强自动拼接**）
- **视频创建模式**：上传 3-60s 单一连续镜头视频 → 同上
- 创建好的主体在视频节点中"主体"槽位调用，输入 prompt 直接生成
- **关键差异**：subject 是给 KlingO1/O3 这类支持 subject 概念的 provider 用的，不是泛模型 ref image

### 2.4 角色三视图 / 多机位九宫格 / 25 宫格连贯分镜

这些都在图像生成器里通过 Slash 命令一键调用：

- **角色三视图**：基于当前图，一次出正 / 侧 / 背
- **多机位九宫格**：基于当前图，一次出 9 个不同机位
- **25 宫格连贯分镜**：基于当前图，一次出 25 帧连贯叙事
- **剧情推演四宫格**：基于当前图，推演前后剧情
- **画面推演-3 秒后 / 5 秒前**：时间轴推演

**核心特点**：都是"一次模型调用出多帧"，不是"分多次调用拼起来"。

### 2.5 摄像机控制（参数化）

- 相机型号（Sony Venice 等）
- 镜头（Helios 等）
- 焦距（35mm / 125mm 等）
- 光圈（f/4 / f/11 等）

**配合提示词**直接生成，参数效果对照清晰（125mm + f/11 vs 35mm + f/4 视觉差异显著）。

### 2.6 打光工具

- 3D 坐标球 26 主光点 + 9 轮廓光点
- 6 个预设（如"蓝色逆光"）
- 亮度 5 档 + 颜色（调色板）
- 智能模式：可输入"《赛博朋克 2077》同款打光"或上传打光参考图

### 2.7 运镜 20+ 预设 + 自定义

- 预设可收藏到"我的收藏"
- 自定义运镜：输入运镜提示词
- **官方提示**：不同模型对相同预设响应情况不同，画面主体多 / 大幅度动作时运镜易受干扰；建议用"首先、然后、最后"这种顺序词

### 2.8 视频解析（反向工程）

把任意视频拆成表格：画面内容、景别、图像提示词、运镜提示词、起始节点、时长、音乐节奏、人声。这是**学习参考视频结构**的工具。

### 2.9 全景 720°

- 文本 / 参考图生 720° 全景
- 4 大视角（每 90° 截一次）+ 12 大视角（每 30° 截一次）
- 进入预览模式自由旋转 + 当前角度截图

我们也有 360° 全景，目的相同。

### 2.10 分镜组（storyboard group）

多张图片节点合并成一个规整宫格 → 自动排序 → 一键导出带序号 4K 大图。比我们的 KeyframeGrid 视觉更统一。

### 2.11 模型清单（30+）

- 图像：Lib Image（最新最强）、LibNano 2/Pro、Seedream 5.0/4.5/4.0、Midjourney V7、Niji 7、Z Image Turbo、Qwen Image 等
- 视频：Seedance 2.0（多模态 12 输入：图≤9 + 视频≤3 + 音频≤3）、HappyHorse 1.0（最多 9 张参考图 + 3-15s 时长）、Kling O3/O1/3.0/2.6/2.5/2.1、Wan 2.6/2.5/2.2、Hailuo 2.3、Vidu Q3 Pro、Pixverse、OmniHuman 1.5（数字人）等
- 语音：GVLM 3.1、Minimax Speech 2.8、音色克隆等

## 3. 资产管理对比

| 能力 | LibTV | 小云雀 | 我们当前（review 修复后） |
|---|---|---|---|
| **角色资产** | 视频主体库（KlingO 系列）；图片资产库（通用） | 200+ 预制数字人 | character_bindings：多张主图 + 自由变体 |
| **角色三视图** | Slash 一键出正 / 侧 / 背 | — | 用户手动派生 view 三次（3q_left/3q_right/back 等）|
| **多角度参考图** | 智能补全 2-3 张主体视角；建议 6+ 张含表情 / 光线 / 动作 | — | 派生 view/expression/outfit/pose 各类自由 label |
| **视频提取主体** | 上传 3-60s 视频提取人物 | — | — |
| **音色 + 主体绑定** | 主体库支持本地上传 5-30s 音频自动音色 + 与图像绑定 | 200+ 预设音色 | binding.voiceId 关联（手动选）|
| **智能主体描述** | 一键 AI 生成 → 字段参与生成（不仅备注，被转 prompt 增强） | — | 需用户手填 description；有 enrichSettings AI 反推 |
| **跨项目复用** | 历史记录全局可见，可"send to canvas"复用 | — | binding 是 projectId 隔离，无跨项目复用 |
| **位置 / 物品资产** | 同一资产体系（图片库）；不区分类别 | — | location / item 同套 binding 模型，多主图 + 变体 |

### 我的判断

**LibTV 的"主体库 + 智能补全 + 智能描述"很 AI-friendly**：
- 让 AI 一次调用补全 2-3 张多角度图（视觉一致性靠 provider 内部，比让用户手动派生 3 次好）
- 自动生成的描述被转换成 prompt 增强 → 多次生成时同一主体 prompt 稳定

**值得借鉴**：
- "一键智能补全多角度"作为派生 dialog 的预设按钮（多张三视图 / 多种表情批量出）
- "AI 自动生成主体描述并参与生成"我们的 enrichSettings 已经有，但落地是"提示用户去 ② 资产 stage 编辑"，没有自动注入到 prompt 增强 — 这点可以加强

**不打算借鉴**：
- 视频提取主体（普通用户没单镜头视频素材）
- 200+ 预制数字人（与我们灵活资产模型冲突）

## 4. 提示词装配 / 工作流对比

| 能力 | LibTV | 小云雀 | 我们（review 修复后） |
|---|---|---|---|
| **提示词模板结构** | 文档建议 5 段：角色身份 / 场景 / 情节冲突 / 节奏 / 镜头偏好 | 一句话自由文本 | identity（name/desc/styleAnchors/故事背景）+ 各类硬约束 + 身份保持 + ref image |
| **结构化分镜模板** | 9 / 25 宫格 + 镜头编号 `S01_SH01` | 自动展开成分镜 | planKeyframes 链式（start→end→middle）；分镜 shotNumber 但无全局编号 |
| **运镜 / 灯光 / 摄像机** | 运镜 20+ 预设；打光 26 主光点 + 9 轮廓光；相机型号 / 镜头 / 焦距 / 光圈参数化 | 自动匹配运镜 | cameraMovement 6 类 + 角度 6 类（select），无打光 / 摄像机参数 |
| **节奏控制** | 文档建议在 prompt 模板中显式 | 自动匹配 BGM / 字幕 | 分镜 duration 显式数字，无"信息点间隔"概念 |
| **反向工程参考视频** | ✓ 视频解析（出表格：画面/景别/提示词/运镜/时长/音乐/人声）| — | — |

### 我的判断

**LibTV 的"摄像机参数化（焦距 / 光圈 / 相机型号）"是非常 AI-friendly 的做法**：
- 训练数据里大量出现 "Sony Venice 35mm f/4" 这种，AI 命中率高
- 比 push/pull/track 这种业务概念更接近图像生成 prompt 的母语
- 落地难度低：几个 select 即可

**强烈推荐借鉴**：
1. 摄像机参数（焦距 / 光圈 / 相机 / 镜头）作为分镜可选参数 — AI-friendly + 用户便捷
2. 运镜从 6 类扩到 20+ 命名预设 — 可以做成项目级"我的运镜库"
3. 打光预设（不用 3D 坐标球，6-12 个命名预设 + 自由文本即可）

**值得借鉴 + 我们要做得更好**：
- 视频解析 → 学习参考视频结构。LibTV 是"出表格让用户看"，我们可以做成"学到的分镜结构 → 一键生成项目骨架"，更进一步。

**不打算借鉴**：
- 5 段式提示词模板（文档级建议，不是产品级强约束。我们装配式 prompt 已经收口得更细）
- 9 / 25 宫格的"一次出 25 帧"（量级太大，质量难保；我们 1-9 帧关键帧 + planKeyframes 链式更稳）

## 5. 跨镜头一致性对比

| 维度 | LibTV | 小云雀 | 我们（review 修复后） |
|---|---|---|---|
| **角色外观锁** | 主体库 + 三视图 + 多视角参考 | 数字人形象固定 | binding referenceImagePath + 派生身份保持文本约束 |
| **统一模型** | 同一镜头组建议不切模型 | 全程同一模型 | 项目级 videoModel 单选 |
| **风格连贯** | 风格参考图节点 + 风格库 | 一次成片同风格 | 派生 prompt 自动带 styleAnchors + 故事背景 |
| **主体级 provider 能力** | KlingO1/O3 原生 subject 概念 | — | — |
| **一致性"物理底座"** | 6+ 张参考图（含不同表情 / 光线 / 动作） | 1 张数字人 ref | 1 张默认主图 + 用户按需派生 |
| **角度 / 时间 / 天气一致性** | 打光 / 运镜显式锁 | — | location 'variant' 按 metadata 自动锁维度 |

### 我的判断

**LibTV 用"主体库（subject ref）+ 6+ 张多角度图"作为一致性的物理底座是更扎实的做法**。我们目前是"1 张默认主图 + 用户按需派生"，覆盖度依赖用户主动性。

**值得借鉴 + 落地方案**：
1. **创建 character 时强引导用户至少出三视图**（创建 dialog 加"批量生成三视图"复选默认勾选）
2. **创建 character 时同时建议三种基础表情**（中性 / 微笑 / 愤怒）作为表情库种子
3. **派生 ref 时支持多张主图同时输入**（现在 deriveSingle 只用 1 张 base，可扩成多基图）— provider 支持多 ref（Seedance 2.0 多模态参考最多 9 张）时全部喂

**值得评估**：
- 探测 provider 能力，能用 subject 时走 subject（KlingO 系列），不能时走 ref image — 这是 provider-agnostic 抽象层

**不打算借鉴**：
- 限定特定 provider（KlingO1/O3）才支持主体 — 我们的 capability matcher 已经有 provider 路由，不需要绑定具体模型

## 6. 工作流 / 用户入口对比

| 能力 | LibTV | 小云雀 | 我们 |
|---|---|---|---|
| **画布 / 节点工作流** | ✓ 灵活但学习曲线长 | — | — |
| **一句话成片** | — | ✓ 智能成片 | — |
| **数字人口播** | OmniHuman 1.5 模型支持 | ✓ 200+ 形象 | — |
| **一镜到底** | — | ✓ 上传 2-10 张 + 描述 | ✓ keyframes2video 模式（但需走完整 6 stage） |
| **手动逐分镜修改** | ✓ | ✓ | ✓ |
| **跨画布复制** | ✓ 带连线 | — | — |
| **历史记录全局可见** | ✓ 跨项目可复用 | — | — |
| **副本 vs 复制** | ✓ 副本保留连线，复制不保留 | — | — |
| **Agent / Skill 接入** | ✓ Skill 模块封装 | 自身就是 Agent | — |
| **画布整理 / 自动布局** | ✓ shift+option+f | — | — |

### 我的判断

**LibTV 的"画布 + 节点"对长篇剧集是反模式**：
- 30+ 镜头 + 角色资产 + 场景图 + 关键帧的画布会无法浏览
- 我们的 stage 串行 + 树状层级（episode/scene/storyboard/keyframe）对长内容更适合

**坚守自己**：
- 不画布化（与我们定位冲突）
- 不预制数字人池

**值得借鉴**：
1. **一句话快速通道**（小云雀）：把 6 stage 串成"AI 一键模式"wizard：用户输入一句话 → 自动展开剧本 → 自动生成资产（默认主图 + 三视图）→ 自动分镜 → 自动关键帧 → 自动出片。每步可介入修改但不强制。**对短剧用户极度友好**
2. **历史记录全局可见 + 跨项目复用**：我们当前 binding 是 projectId 隔离，加一个"我的素材库"（user-level）让用户跨剧集复用角色 / 地点 / 物品形象（特别是 IP 矩阵 / 系列剧）
3. **Agent / Skill 接入**：把"生成关键帧 / 角色三视图 / 派生变体"原子能力封装成 Skill，外部 Agent（Claude Code / 自定义脚本）可调用。这对开发者用户 + 自动化场景有价值

**不一定要借鉴**：
- 画布整理（我们没画布）
- 副本 vs 复制（节点画布特有）

## 7. 模型编排对比

| 能力 | LibTV | 小云雀 | 我们 |
|---|---|---|---|
| **接入模型数量** | 30+ | 豆包 + DeepSeek + Seedance 2.0 + Seedream 5.0 等少量 | 用户自配 provider |
| **模型选型粒度** | 用户每节点选模型 | 黑盒 | 项目级 imageModel / videoModel 单选 |
| **多模式** | 文生 / 图生 / 视频生 / 多模态参考 | 文生 / 一镜到底（关键帧）| text2video / image2video / keyframes2video（capability matcher 自动） |
| **降级机制** | 用户手动换模型 | 黑盒 | ✓ capability matcher 自动 + trace 路径 |
| **成本可控** | 用户每节点选模型 | 黑盒 | provider 配额由用户 API key 自管 |
| **真人合规** | ✓ Seedance 2.0 真人需活体校验 | — | — |
| **音色克隆** | ✓ 录 1-15s 样本生成专属音色 | — | — |

### 我的判断

**LibTV 的"按节点选模型"给了高级用户精细成本 / 质量控制**，但对普通用户复杂。我们项目级单选简单但缺灵活。

**值得借鉴**：
1. **项目级单选 + 单分镜可覆盖**：现在所有分镜共用项目 videoModel；可加"该分镜用别的 model"的局部 override
2. **模型分级**：草稿 / 成片 / 高保真 三档，让用户在"快出草稿"和"出最终版"之间切换。配合现有 capability matcher 即可
3. **音色克隆**：我们目前依赖 voiceId 选预设音色；克隆能力对真人短剧 / 角色配音价值大。优先级看产品方向

**不打算借鉴**：
- 30+ 模型 marketplace 中心化默认接入。我们的 provider 是用户自配 API key 的开放体系，且当前已有 onboarding 流程，本次专项不重复。

## 8. 设计原则：双母语 + 用户分层

讨论过程里我两次都跑偏 — 第一次过度妥协（把"不做"砍到只剩 2 条以附和反问），第二次矫枉过正（用纯电影学院派标准评判，把短剧自媒体用户的母语贬为"混级别不专业"）。

正确的判断框架：**每条功能问两遍**

1. 对**专业用户**（导演 / 编剧 / 影视专业）它的母语价值是什么？
2. 对**大众用户**（自媒体短剧 / 个人爱好者 / 零基础创作者）它的认知负担与价值是什么？

两边都通过的才是真该做。两边只有一边通过的，要看落地形式能否做"分层 UI"（同一功能不同叫法 / tooltip）让两类用户共存。

### 三个具体的双母语场景

| 维度 | 专业母语 | 大众短剧母语 | 落地 |
|---|---|---|---|
| **角色多视角参考** | "三视图（character bible）" | "多角度参考图" | 同一功能，UI 标签默认大众语；专业用户 hover/标签可见专业术语 |
| **单镜画面描述模板** | shot-level 5 字段：subject / action / camera / lighting / mood（电影分镜表标准） | 短剧 5 段：角色 / 场景情境 / 戏剧冲突 / 节奏 / 镜头偏好（短剧叙事母语 · LibTV 形态）| 双模板切换器；后端 prompt 装配两套都能消化 |
| **摄像机参数** | 焦距 35mm / 光圈 f/4 / Sony Venice 等 | "广角，环境感强（外景大全景）"等视觉效果命名 | 同一 select 选项，每项 tooltip + 缩略示意图 |
| **故事板草稿** | thumbnail storyboard / 9 frame rough cut | "故事板预览（让 AI 把剧本展开看看）" | 同一功能，大众默认叫法；专业 hover/技术 label 显示原术语 |

> 关键认知：**短剧用户的"5 段叙事母语"不是混乱**，而是为短剧 3-5 秒一段戏的高密度叙事 native 设计的。我之前用电影学院标准评价是 elitist 偏见。

## 9. 我们应做的能力（按修正后优先级）

### 我们的真实优势（坚守）

- **结构化的长内容生产**：episode/scene/storyboard/keyframe 关系建模 + binding 数据模型 + 自动 prompt 装配
- **prompt 装配的工程化程度**（review 后 5 处入口收口到共享模块）
- **资产 metadata 维度评分系统**（角色 view/expression/outfit + 地点 angle/time/weather）
- **多层 referenceImageIds override**（binding → storyboard → keyframe）
- **capability matcher 降级机制**

LibTV 在节点画布的灵活性 + 工具丰富度，小云雀在一句话快速通道。我们应该**保持自己的层级模型 + 选择性吸收 AI-friendly 工具**，而不是被对方的产品形态拖着走。

### P0 — 高影响 + 双母语都通过

1. **9 帧故事板草稿模式**
   - **AI 友好**：一次推理出 9 帧的内部一致性远好于 9 次独立调用（同 latent + 同推理上下文）
   - **专业用户母语**：thumbnail storyboard，电影前期标准做法
   - **大众用户母语**：可视化的剧本展开，挑骨架再细化（替代"每帧从零写描述"的高认知负担路径）
   - **落地**：剧本→分镜的过渡入口；UI 默认叫"故事板预览"，专业 label 显示"thumbnail storyboard / 9 帧粗略板"

2. **双模板单镜画面描述**（替代现在的空白 textarea）
   - **短剧模板**（默认）：角色 / 场景情境 / 戏剧冲突 / 节奏 / 镜头偏好 — 短剧自媒体用户的 native 叙事母语
   - **影视模板**：subject / action / camera / lighting / mood — 专业导演的 shot-level 标准
   - **落地**：④ 分镜的画面描述上方加模板切换器；模板字段折叠展开成结构化文本；后端 prompt 装配通吃两套
   - **AI 友好**：结构化文本提高 AI 提示词命中率
   - **用户便捷**：替代空白框；新手有引导，专业用户能切到自己的标准

3. **角色一键多角度参考图**（character 资产）
   - 创建主图 dialog 加"同时生成多角度参考图（正面 / 侧面 / 背面）"复选（默认勾选）
   - 用支持多图一致性输出的模型一次出多张
   - **AI 友好**：一次推理一致性 > 多次独立派生
   - **UI 文案分层**：默认标签"多角度参考图"，专业 hover 显示"three-view sheet / character bible"

4. **摄像机参数化**（焦距 / 光圈 / 相机风格）+ 视觉效果 tooltip
   - ④ 分镜加 select：焦距（35/50/85/125mm）/ 光圈（f/1.8/f/4/f/11）/ 相机风格（电影感 / 数码 / 胶片）
   - 每个选项的 tooltip 含**视觉效果说明 + 缩略示意图**
   - 大众用户：看图 + 文字描述选；专业用户：跳过示意直接选数值
   - **AI 友好**：行业标准词汇，AI 训练数据丰富，比 push/pull 命中率高

5. **运镜预设扩到 20+**（命名化 + tooltip）
   - 现在 6 类（push/pull/pan/track/crane/static）扩到 LibTV 同级别
   - 加"希区柯克变焦 / 长镜头跟拍 / 大师推近"等命名化预设
   - 每个预设 tooltip 含视觉描述 + 适用场景
   - **AI 友好**：命名→提示词映射表
   - **用户便捷**：专业用户认得，大众用户看 tooltip 学

6. **打光命名预设**（6-12 个，不做 3D 坐标球）
   - 命名预设：伦勃朗光 / 三点照明 / 蓝色逆光 / 黄金时刻 / 蝴蝶光 / 平铺光 / 戏剧侧光 等
   - 每预设 tooltip 含氛围描述 + 示意
   - **AI 友好**：摄影术语 AI 命中高
   - **用户便捷**：6-12 个比 LibTV 26 主光点 + 9 轮廓光的 3D 坐标球简单太多

### P1 — 中影响

7. **派生时支持多基图输入**（spec 2026-05-09 多主图模型扩展）
   - DeriveVariantDialog 改成多选 checkbox（不强制单选）
   - provider 支持多 ref（如 Seedance 2.0 最多 9 张）时全部喂；不支持时降级到第一张
   - **AI 友好**：信息更全；**用户便捷**：多张主图都已存在，多勾选即可

8. **AI 一键快速通道**（短剧 / 大众用户入口）
   - 首页或 ① 内容 stage 加"AI 一键模式"wizard
   - 输入一句话 → 自动跑剧本 → 资产（含多角度参考图）→ 分镜（带 9 帧故事板）→ 关键帧 → 出片
   - 每步可介入修改但不强制
   - **用户便捷**：大众用户跳过手动；**AI 友好**：让 AI 自己选模型链路

9. **全局镜头编号**（`EP01_S03_SH04` 格式）
   - ④/⑤/⑥ stage 显示
   - 便于跨分镜引用和团队沟通
   - 专业用户母语；对大众用户至少不增加负担

10. **AI 主体描述自动参与 prompt 注入**
    - 现在 enrichSettings 反推后写 binding.description；description 已走 identity prompt 入 effective
    - 链条已通但用户不知道；UI 显式提示"已自动加强主体描述"
    - 透明度提升，让用户理解 AI 在做什么

### P2 — 高影响 + 工程量大

11. **局部可视化连线（分镜内只读子画布）**
    - **现状分析**：⑤ 制作 stage 已经是分镜中心化的卡片布局（分镜信息卡 + 关键帧卡 + 视频生成卡 + 视频预览卡 + 资产卡）。**子画布的雏形已存在**。
    - **能融合的关键**：连线信息现成可推导
      - 资产 → 关键帧（resolveSceneAssets 已建立）
      - 关键帧 → 视频（keyframes2video 已有）
      - 用户挑选的资产参考图 → 关键帧（storyboard.referenceImageIds 已有数据）
      - keyframe.referenceOverrides 已落地
    - **落地形式**：⑤ 制作 stage 加"显示生成链路"开关（默认关闭），开了就在卡片之间叠加只读连线 + 数据传递标签
    - **重要约束**：**只读、不可编辑** — 数据流仍由后端逻辑决定。这避免变成真画布化。
    - **专业用户**：debug 生成质量问题
    - **大众用户**：默认关闭无感；好奇时打开能学习"为什么这一帧是这个样子"

12. **跨项目 / 跨剧集角色库**（user-level）
    - 现在 binding 是 projectId 隔离
    - 加 user_assets 全局表（角色 / 地点 / 物品）作为模板源
    - 项目内"从我的库引用 → override 字段"两级
    - 长 IP 矩阵 / 系列剧靠这个

13. **数字人池**（少量精选 10-30 个，不是 200+）
    - 与 character_bindings 共存：加 `sourceType='preset_digital'`
    - 覆盖最常见类型：青年男 / 女主播 / 老人 / 小学生 / 中年商务 等
    - **大众用户场景**：解说混剧情 / 试制 demo / 旁白主播段
    - **不冲淡资产模型**：少量精选，不取代用户自定义角色
    - 与 LibTV 200+ / 小云雀 200+ 量级的本质区别：**精选不冲淡，量大才冲淡**

14. **Agent / Skill 接入**
    - 把"生成关键帧 / 角色三视图 / 派生变体 / 拆分镜"原子能力封装成 Skill
    - 让外部 Agent（Claude Code 等）能调用
    - 服务开发者用户 + 自动化场景

15. **视频解析**（反向工程参考视频）
    - 用户上传参考视频 → AI 拆出"画面 / 景别 / 镜头 / 运镜 / 时长 / 音乐节奏"
    - 一键导入到当前剧集作为分镜骨架
    - **AI 友好**：让 AI 从参考视频学结构；**用户便捷**：找参考 → 导入参考无缝

### P3 / 长期可能

16. **视频提取主体**（character 创建支持上传短视频）
    - 真人剧用户有此素材（拍摄样片 / 试镜片段）
    - 工程复杂度高（帧提取 + 一致性聚类 + 代表帧选择）
    - 不是定位冲突，是优先级

### 真不做（坚守）

- **节点画布作为主组织方式** — 长内容反模式；30+ 镜头剧集会被画布混乱压垮
- **用户拖拽编辑连线** — 只做 P2 的"只读可视化"，不做"用户拖拽改数据流"。后者就是真画布化。
- **200+ 预制数字人** — 量大冲淡用户自定义资产模型；少量精选（≤30）不冲突，超过就冲突
- **副本（带连线）/ 画布整理** — 节点画布特有，我们没全画布化所以不需要

### 我的优先建议

下一步先做 **P0 1-4 项**（9 帧故事板 + 双模板画面描述 + 多角度参考图 + 摄像机参数化），都是双母语都通过的、低工程量、高 AI 友好度。

5-6 项（运镜扩展 + 打光预设）紧随。

P1 系列里 8（AI 一键快速通道）对大众短剧用户体验提升最大，可以提前到 P0/P1 之间。

P2 的 11（局部子画布只读）可以晚做但不要忘 — 作为生成质量调试的辅助能力，专业用户会感激。
