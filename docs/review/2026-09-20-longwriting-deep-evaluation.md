## 二、深层问题（按严重度）

### ★1. 多入口质量治理——引流放量前必须完成定位（P1，原列 P0）

内置「长文写作」工作流（`builtin_def_long-form-writing`）节点序列 `LLM 故事线 → LLM 大纲 → loop 逐章 LLM → 拼接 → kb-ingest + save-asset`：**无设计卡、无一致性门禁、无图谱提取、无版本链，产物落资产/知识库而非长文项目库**。能力卡已把它列为「写小说」的 workflow 优先路径，但未披露「无一致性检查」。

**复核修正**：该工作流**运行次数为 0**（workflow_runs 无任何记录）——是预防性治理而非现行事故；且 Agent E2E 实测中，复杂小说需求实际被引向研讨室正轨。结论：在对话引流放量前完成其一——①快速路径挂最低一致性自检并把产物以草稿形态接入长文项目；②能力卡明示「草稿机：无一致性检查、不进项目库」。

### ★2. FK 崩溃——3 次原始 SqliteError 炸穿章法（P1）

`outline_1789839120467` 的章法写作 3 次同因失败 `FOREIGN KEY constraint failed`。复核确认：该大纲节点及关联的章节行/预写/状态摘要**四表全部为空 = 节点确已被删除**（项目早期大纲重建），但章法仍可对已删节点发起并在落库时炸穿，用户看到裸 SqliteError。修复：①删除大纲节点时级联清理或拦截引用；②chapter-writing 节点把 FK 异常翻译为人话（「该章节大纲已被删除，请刷新大纲后重试」）。

### ★3. 基础设施全局休眠 + 嵌入兜底链缺陷（P2，问题比原判断深）

- `lw_vector_indices` 与 `lw_story_memories` **全部项目均为 0 行**；**无任何项目配置过 embedding stage**。
- 追加发现：`lw-vector-index.service` 的 embedding 解析兜底链为 `stage='embedding' → stage='chapters'`，而 chapters 配的是**对话模型**（deepseek）——真跑索引会拿聊天模型当嵌入模型用，必败。修复必须含兜底链修正（聊天模型不得充当嵌入模型），而非仅补默认配置。

### ★4. 伏笔台账单向循环——全局性（P1）

全部 7 个项目 **154 条伏笔，`paid` = 0**。埋设由图谱提取自动进账，回收侧无任何工作流推动（R8 只报超期）。与 §6 节奏看板合并实现：台账上直接「标记回收/弃置」。

### 5. R9 噪音画像——可降噪约八成（P1）

最新扫描 18 个去重名字：地名 2（白鹿城/金堤城）、泛称/角色 8（校尉/刺客/老捕快/黑衣人/神秘黑衣人/神秘黑影/黑衣劫匪/押车哑巴）、疑似非名 4（金粉/方才/谢家/周大），疑似真人名仅 2-4 个。**噪音占比约 78-89%**。修复：R9 排除集从「人物名册」扩到「地点名册 + 泛称停用词」。

> 勘误说明：初版误写「31 条 R9」（31 是伏笔条数，串行），且「砍掉 60%+」低估。

### 6. 观察项：wizard_state 数据完整性（P2）

初版评估曾观察到一次瞬时非标准 JSON，复核**无法复现**——当前全部非 NULL 项目均可解析，降级为观察记录。但顺藤发现一个静态 bug：项目「天下女捕-小师妹」`wizard_state` 为 **NULL**（某条创建路径未初始化该字段）。修复：项目创建时默认初始化 `defaultRoomState()` 所在的 wizard 骨架。另注：多实例/并行会话正在成为常态，wizard_state 写入的单机单用户约定建议加实例锁或版本号（P2）。

## 三、质量闭环的不对称（设计层判断）

一致性是硬门禁（自检不过不落正文、疑点未处理拦下一章），故事性是软输出（只出结论不拦截）——当前合理。后果：「爽点/钩子达标」依赖主编自觉 + 审批单人审，**每章人审是当前唯一质量闸门**，91 章规模下的可持续性取决于节奏看板（批次二 §6）。模型质量杠杆（审读/正文统一 stage 配置）修复后已握到用户手里。
