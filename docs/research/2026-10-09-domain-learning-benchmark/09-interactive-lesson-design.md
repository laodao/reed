# 交互式图文讲义设计方案（Interactive Lesson）

> 日期：2026-10-10
> 需求（用户原话）：*"是否可以做成交互式的学习，图文并茂，且能与用户交互，你有思路吗"*
> 前置：`08-engagement-diagnosis.md`（病根诊断）；本文是它的**落地方案**，对应思路 1（交互即学习）+ 思路 2（认知冲突）+ 病根 A
> 核心判断：**方向对，且我们已有最好的地基——但必须避开三个能把它做砸的陷阱。**

---

## 一、先说结论：这件事我们比想象中更有条件

三个已经存在的地基，决定了这件事的成本远低于重做：

| 地基 | 现状 | 对交互式的意义 |
| --- | --- | --- |
| **声明式图形规格** | `figure-spec.ts`：5 类图（matrix/plot/bar/shape/network）**只存数据不存代码**，渲染层自写 SVG，零依赖、确定性、**同一规格=>同一张图可测** | 这是交互的**完美基座**：把"静态图"升级为"参数可变的图"，模型依然只产出 JSON，交互由渲染层承担 |
| **Worker 沙箱** | `code-runner.ts`：JS/TS 代码可在 Worker 里真实运行（已有单测） | 计算类交互（"改参数看结果"）**不需要新建沙箱**，复用即可 |
| **区集契约 + 版式设备** | `lesson-template.ts`（v9 锚点区+规范区+开放区）+ `lesson-layout.ts`（15 设备，**形状门禁**已实现） | 加"交互设备"是**顺着现有契约扩展**，不是另开一套体系 |

**换句话说：我们不缺画图能力，也不缺计算能力，缺的是"让用户动手"的那一层交互编排。** 这一层的成本，比做视频/动画低一个数量级。

---

## 二、三个必须避开的陷阱（先立规矩，再谈方案）

### 陷阱 1：把交互做成"装饰性动画"

**反例**：点击后元素滑入、翻牌、粒子效果、进度环旋转——用户看完"哇"一声，学习没有任何变化。

**判断标准（我建议作为硬性准入门槛）**：

> **一个交互组件，如果它不产生"用户可观测的认知结果"，就不许进讲义。**

"认知结果"的可操作定义（三选一即可）：
- 产生**预测-验证**落差（用户猜错 → 认知被修正）
- 产生**可判分的作答**（有对错，能写进 `mastery_log`）
- 产生**可操控的因果**（改参数 → 看到结果变化，理解变量关系）

**只有同时不满足这三条的"动效"，一律不做。** 这条门槛能挡掉 90% 的无效工作。

### 陷阱 2：把讲义变成"一堆小程序的拼盘"

**反例**：每一区都塞一个独立交互，彼此无关，读完记不住主线——碎片化，比文字墙更糟。

**解法**：**交互服务于叙事，不是替代叙事。** 一份讲义里的交互必须**串成一条线**：
- 开头一个**预测**（钩子：你以为会怎样？）
- 中段一到两个**操作/探索**（动手验证）
- 结尾一个**检查**（你到底懂没懂）

一份讲义 3-4 个交互是上限。**宁可少，不可滥。**

### 陷阱 3：让模型生成交互逻辑

**反例**：让 LLM 直接吐 JS/SVG/HTML 来做交互。

**为什么不行**：不可测、不可控、易注入、质量方差极大；且与我们既有的"声明式图形 + 形状门禁"纪律**直接冲突**。

**解法（沿用项目既有纪律）**：

> **模型只产出「交互规格 JSON」，交互行为全部由渲染层的固定组件实现。**

这与 `figure-spec.ts` 的设计哲学完全一致（模块注释原话："模型只产出图形规格（JSON），渲染层用自写的 SVG 渲染器画出来"）。**我们已经有这套纪律，扩展它即可，不要破例。**

## 三、方案：三层交互设备，由浅入深

我建议新增一类**区级版式设备**：`interactive`（与现有 15 个设备并列），下挂若干**交互子类型**。理由是：这样能直接复用现有的**形状门禁**机制（`checkLessonVisualQuality`）——"声明了 interactive 区，就必须有合法交互规格块"，与现有 `figure` 设备的校验方式同构。

### 第一层：预测-验证（Predict & Reveal）—— 成本最低，收益最高 ★★★★★

**形态**：给用户一个**具体预测任务**，先让他选/填，再揭示真相。

**为什么它排第一**：
- 它**直接制造认知冲突**（= 08 号档思路 2 的落地形态），是"想读下去"的核心动力；
- 它**天然产生可判分数据**（用户选了什么、对不对），可写进 `mastery_log`；
- 它**可以用现有 `figure` 规格渲染**（预测对象就是一张图/一个数字），**几乎零新增渲染代码**。

**具体样子**：

```
┌─ 先猜一下 ────────────────────────────┐
│ 下面两条曲线，哪条是"复利"，哪条是"单利"？│
│                                        │
│   [ 曲线图 A ]      [ 曲线图 B ]        │
│                                        │
│   [选 A]  [选 B]        ← 用户点击      │
└────────────────────────────────────────┘
        ↓ 点击后
┌─ 你猜对了 / 这里有个反直觉的地方 ──────┐
│ A 才是复利。注意 30 年后的差距——       │
│ 大多数人会低估到这个程度。              │
│ [看完整计算 →]                         │
└────────────────────────────────────────┘
```

**规格草案**（仅示意形状，实现时按现有 `figure-spec` 风格定稿）：

```json
{
  "type": "predict",
  "prompt": "哪条曲线是复利？",
  "options": [
    { "id": "a", "label": "曲线 A", "figure": { "type": "plot", "...": "复用现有规格" } },
    { "id": "b", "label": "曲线 B", "figure": { "type": "plot", "...": "..." } }
  ],
  "answer": "a",
  "reveal": "A 才是复利。注意 30 年后的差距……",
  "explainLink": "worked"
}
```

> **关键**：`figure` 字段**复用现有 5 类图形规格**，`answer` 字段让判分成为纯数据比对（可测、可写库）。

### 第二层：参数探索（Manipulate）—— 治"变量关系"类概念 ★★★★

**形态**：给一个可拖动的参数（滑块），图/数**实时**跟着变。

**适用场景**：凡是"某个量变了，另一个量怎么变"的概念——利率与终值、学习率与收敛、样本量与置信区间、浓度与反应速率……

**为什么值得做**：读一百句"当 x 增大时 y 加速增长"，不如自己拖一下滑块。**这是"交互"相对"文字"不可替代的地方**，也是最能体现"图文并茂 + 可交互"的形态。

**技术路径（零新基建）**：
- 模型产出：`{ "type": "explore", "param": {"name":"年利率","min":0,"max":0.2,"step":0.01,"default":0.05}, "formula": "...", "figure": {...} }`
- 渲染层：滑块 + **用参数重新计算并重画 SVG**
- **计算放哪**：简单公式用既有 KaTeX/纯函数；复杂计算**复用 `code-runner.ts` 的 Worker 沙箱**——沙箱已经存在且有测试

**这里有一个重要的克制**：不要让模型写计算函数（违反陷阱 3）。正确做法是模型给**受约束的表达式**（或从预置公式库里选 + 填参数），由渲染层求值。

### 第三层：结构化操作（Manipulate Structure）—— 治"关系/结构"类概念 ★★★

**形态**：拖拽排序、连线配对、分类归位。

**适用场景**：步骤顺序（排序）、概念与定义（配对）、前置关系（连线）、分类体系（归位）。

**为什么放最后**：它的实现复杂度最高（拖拽 + 校验 + 移动端适配），但**它的判分数据最干净**（完全可判定对错），且**与我们已有的关系图数据同构**（`dl_relation` 本就有"概念-概念"的边，配对题可以直接从图数据派生）。

## 五、图文并茂：现有能力已足够，但要注意"图的密度"

用户提到"图文并茂"。现状（`01-current-state.md:57`）：图=**5 类声明式 SVG**（matrix/plot/bar/shape/network），公式=KaTeX，代码=JS/TS Worker。

**判断**：这 5 类图**覆盖 AI/数学领域已相当充分**（原设计注释即写明"覆盖 AI/数学学习里绝大多数图形需求"）。**不建议现在扩图形类型**——先把交互做起来，用起来之后按真实缺口再扩。

**但有一个真问题**：`FIGURE_LIMITS` 显示容量上限很保守（matrix 24×24、plot 400 点、bar 16 项）。**交互式场景下这个上限会成为瓶颈**——因为"拖滑块看曲线变化"需要实时重绘，点太多会卡。

**建议**：交互区的图单独设一档更严的上限（如 plot 200 点），并**在交互区强制走轻量渲染路径**（不做过渡动画，避免拖拽时掉帧）。

**关于"AI 生图"**：明确**不做**。模块注释已写明这是用户拍板的方案 A（"不走 AI 生图——由代码按数据画图"）。**这个决定是对的**：AI 生图不可测、不可控、不可交互，与本文方向直接冲突。交互式路线反而**加强**了"声明式图形"这一既有决策的价值。

## 六、落地顺序（我建议的四步）

| 步 | 内容 | 验收 | 量级 |
| --- | --- | --- | --- |
| **S1** | 契约 + 规格层：`interactive` 设备入目录、`interactive-spec.ts`（先只做 **predict** 一类）+ 纯函数单测 | 单测绿；形状门禁能挡住"声明了 interactive 但没有合法规格" | 小 |
| **S2** | 渲染 + 生成：`InteractiveBlock.vue`（predict）+ 提示词/技能接入 | 真机出一张含预测交互的讲义，点击有揭示 | 小-中 |
| **S3** | 数据回流：作答写 `mastery_log`（接线 `self_test` trigger） | 答对/答错能影响掌握度与后续 `pickNextToLearn` | 小（数据链路已有） |
| **S4** | 扩展 explore / structure 两类 | 拖参数实时重绘；配对判分 | 中 |

**建议 S1-S3 为一个批次**——它们合起来构成"能生成、能交互、能回流"的最小闭环，且**闭环一旦成立，就能用真实数据判断后面该怎么走**。S4 视 S1-S3 的实际使用情况再定。

**关于"要不要先改默认 prose 口径"**（08 号档第 0 步）：**我的建议是解耦，不要绑在一起**。
- 交互区是**显式声明**的设备，**不受"默认 prose"影响**——它本来就要显式声明才会出现；
- 所以 **S1-S4 可以完全不动 `defaultLayoutForSection`**，绕开了那个需要你确认的决策；
- 等交互用起来、你看到实际效果后，再回头判断"默认 prose"要不要松——**那时你有真实体感做依据，比现在争论更好**。

## 七、一个诚实的风险提示

**交互式讲义对生成侧的要求更高，成本会上升。**

文字讲义的生成成本是"写一段话"；交互式讲义要求模型同时产出：**叙事线 + 交互规格 + 正确的答案与揭示文案**。这意味着：
- 单张卡的 token 消耗会上升（要把交互规格和答案写对）；
- **答案必须对**——预测题的 `answer` 字段如果标错，用户会被"错误地纠正"，这是**比文字错误严重得多的信任伤害**；
- 因此需要**门禁**：交互规格要有"答案与规格自洽性"校验（如 `answer` 必须命中 `options` 的某个 id；explore 的公式与图数据要能对上）。

**建议**：把"交互规格自洽性"直接加进既有的**五道卡级门禁**（作为形状门/视觉门的扩展）。**这是我们已经验证过的质量控制范式，扩一条判据的成本很低。**

**另一条风险**：三个陷阱里最危险的是**陷阱 2（碎片化）**。技术上做出一堆交互组件很容易，难的是**让它们服务同一条叙事线**。这需要在提示词里明确"先定叙事主线，再决定哪几处需要用户动手"，而不是"每区都塞一个"。**这条如果没有约束住，做出来的东西会比文字墙更让人疲惫。**

---

## 八、一句话总结

> **方向对，地基好，但成败在三件事上：交互必须产生认知结果（不是动效）、必须服务同一条叙事线（不是拼盘）、必须由模型出规格而非出逻辑（不是破例）。**
>
> 最有价值的发现是：**做交互式讲义，顺手就能把 `self_test` 这条悬空的测量链路接上**——一份工作量，同时治"内容枯燥"和"测量不回流"两个病根。
