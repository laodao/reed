# MemGPT / Letta: OS 式虚拟上下文管理（把 LLM 上下文当 RAM 管理）

- 链接: https://arxiv.org/abs/2310.08560 （项目后演化为 Letta, https://www.letta.com ）
- 作者: Charles Packer, Sarah Wooders, Kevin Lin, Vivian Fang, Shishir G. Patil, Ion Stoica, Joseph E. Gonzalez（UC Berkeley）
- 时间: 2023-10-12 v1; 2024-02-12 v2
- 来源: arXiv。抓取方式: arXiv API 摘要 + arXiv HTML 全文（空白规范化），2026-09-16 存档。

## 原文摘录（保留原文不翻译）

> **Abstract (开头)**: Large language models (LLMs) have revolutionized AI, but are constrained by limited context windows, hindering their utility in tasks like extended conversations and document analysis. To enable using context beyond limited context windows, we propose virtual context management, a technique drawing inspiration from hierarchical memory systems in traditional operating systems which provide the illusion of an extended virtual memory via paging between physical memory and disk.

分级记忆结构：

> MemGPT's OS-inspired multi-level memory architecture delineates between two primary memory types: main context (analogous to main memory/physical memory/RAM) and external context (analogous to disk memory/disk storage).

> Main context consists of the LLM prompt tokens —anything in main context is considered in-context and can be accessed by the LLM processor during inference. External context refers to any information that is held outside of the LLMs fixed context window. This out-of-context data must always be explicitly moved into main context in order for it to be passed to the LLM processor during inference.

> The LLM's prompt tokens (inputs), or main context, consist of the system instructions, working context, and a FIFO queue.

自我编辑（self-editing）与函数调用：

> MemGPT uses functions to move data between main context and external context (the archival and recall storage databases).

> MemGPT orchestrates data movement between main context and external context via function calls that are generated by the LLM processor...decide when to move items between contexts (e.g. when the conversation history is becoming too long) and modify its main context to better reflect its evolving understanding of its current objectives and responsibilities.

内存压力预警与递归摘要（核心运维机制）：

> The queue manager is also responsible for controlling context overflow via a queue eviction policy. When the prompt tokens exceed the 'warning token count' of the underlying LLM's context window (e.g. 70% of the context window), the queue manager inserts a system message into the queue warning the LLM of an impending queue eviction (a 'memory pressure' warning) to allow the LLM to use MemGPT functions to store important information contained in the FIFO queue to working context or archival storage...When the prompt tokens exceed the 'flush token count' (e.g. 100% of the context window), the queue manager flushes the queue to free up space in the context window: the queue manager evicts a specific count of messages (e.g. 50% of the context window), generates a new recursive summary using the existing recursive summary and evicted messages. Once the queue is flushed, the evicted messages are no longer in-context and immediately viewable to the LLM, however they are stored indefinitely in recall storage and readable via MemGPT function calls.

心跳/中断机制：

> ...and uses interrupts for control flow between the system and user.

## 核心机制拆解（中文）

- **数据模型**: main context（system instructions + working context + FIFO 消息队列）vs external context（recall storage 会话库 + archival storage 任意长文本库）。working context 是 agent 自己维护的"自我认知便签"，本质是 CoALA 里的可写 working memory。
- **流程**: LLM 本身是"OS 内核"——每轮推理可发起函数调用在两级上下文间搬数据；queue manager 负责溢出控制；70% 水位发 memory pressure 警告给 LLM 让它"自救"（把重要信息存档），100% 强制 flush 并生成递归摘要。
- **触发时机**: 溢出驱动（被动）+ LLM 主动 self-edit（随时）。没有独立的后台提炼进程——一切提炼都发生在对话循环内的函数调用里。
- **成本**: 每次 self-edit 是一次额外 LLM 调用；递归摘要把长历史压成增量更新的摘要。工程复杂度集中在队列管理与函数协议。

## 证据与局限

- 评估在 document QA 与多轮对话两个场景，用修改版 Deep Memory Retrieval 与 QA 任务验证"远超上下文窗口"的可用性；此后成为 Letta 商业产品（含 2025 年的 sleep-time agents，见另条目）。
- 局限（后续 Letta 自己也承认）：单 agent 同时管记忆和对话导致响应慢、可靠性差；记忆增量写入导致"memories may become messy and disorganized over time"。这些问题正是 sleep-time compute 条目中双 agent 拆分的动机。
- 对"经验提炼"本身着墨少：MemGPT 解决的是"装得下、找得到"，不是"从经验里学到可泛化的东西"。

## 对我们的适用性

1. **水位预警机制可直接抄**: 70% 警告→让 agent 自己抢救重要信息、100% 强制摘要 flush，这套两段式策略非常适合我们长篇小说创作中动辄超长的会话轨迹，比"一刀切断历史"优雅，且完全本地可实现。
2. **working context = agent 的自我状态便签**: 我们可以把"当前写作项目状态/角色状态/进行中的大纲决策"做成 agent 可自编辑的 working context 块，而不是散落在会话历史里——这是从"会话日志"升级为"结构化自我认知"的最低成本路径。
3. **recursion summary 的教训**: 递归摘要会累积失真；我们的 L1-L3 分层已有类似问题，MemGPT 的"原始数据永不删、只在主上下文外"（non-lossy recall storage）原则值得坚持——提炼物可以失真，但轨迹原文必须可回溯（我们已有 agent_trajectory，这是优势）。
4. **"何时提炼"的答案**: MemGPT 是纯事件驱动（溢出/函数调用），没有定时提炼。结合我们飞轮停用经验：纯溢出驱动容易"平时不提炼、溢出时来不及"，最好与任务边界（章节完成、项目收尾）结合。
