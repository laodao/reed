## 原文摘录

**论文摘要：**

> However, RAG fails on global questions directed at an entire text corpus, such as "What are the main themes in the dataset?", since this is inherently a query-focused summarization (QFS) task, rather than an explicit retrieval task. ... we propose GraphRAG, a graph-based approach to question answering over private text corpora that scales with both the generality of user questions and the quantity of source text. Our approach uses an LLM to build a graph index in two stages: first, to derive an entity knowledge graph from the source documents, then to pregenerate community summaries for all groups of closely related entities. Given a question, each community summary is used to generate a partial response, before all partial responses are again summarized in a final response to the user. For a class of global sensemaking questions over datasets in the 1 million token range, we show that GraphRAG leads to substantial improvements over a conventional RAG baseline for both the comprehensiveness and diversity of generated answers.

**官方文档《Indexing Methods》—— Standard GraphRAG 六步：**

> Standard uses a language model for all reasoning tasks:
> - entity extraction: LLM is prompted to extract named entities and provide a description from each text unit.
> - relationship extraction: LLM is prompted to describe the relationship between each pair of entities in each text unit.
> - entity summarization: LLM is prompted to combine the descriptions for every instance of an entity found across the text units into a single summary.
> - relationship summarization: LLM is prompted to combine the descriptions for every instance of a relationship found across the text units into a single summary.
> - claim extraction (optional): LLM is prompted to extract and describe claims from each text unit.
> - community report generation: entity and relationship descriptions (and optionally claims) for each community are collected and used to prompt the LLM to generate a summary report.

**《Indexing Methods》—— FastGraphRAG（NLP 替代 LLM 抽取）：**

> - entity extraction: entities are noun phrases extracted using NLP libraries such as NLTK and spaCy. There is no description; the source text unit is used for this.
> - relationship extraction: relationships are defined as text unit co-occurrence between entity pairs. There is no description.
> ... We estimate graph extraction to constitute roughly 75% of indexing cost. FastGraphRAG is therefore much cheaper, but the tradeoff is that the extracted graph is less directly relevant for use outside of GraphRAG, and the graph tends to be quite a bit noisier.

**《Indexing Outputs》—— 溯源字段（逐表 schema）：**

> **entities** ... | text_unit_ids | str[] | List of the text units containing the entity. | frequency | int | Count of text units the entity was found within. | degree | int | Node degree (connectedness) in the graph.
>
> **relationships** ... | description | str | LM-derived description of the relationship. | weight | float | Weight of the edge in the graph. This is summed from an LM-derived "strength" measure for each relationship instance. | text_unit_ids | str[] | List of text units the relationship was found within.
>
> **covariates** (Optional) If claim extraction is turned on, this is a list of the extracted covariates. ... | covariate_type | str | This is always "claim" with our default covariates. | subject_id | str | Name of the source entity (that is performing the claimed behavior). | object_id | str | Name of the target entity. | status | str | LM-derived assessment of the correctness of the claim. One of [TRUE, FALSE, SUSPECTED] | start_date / end_date | str | LM-derived start/end of the claimed activity. ISO8601 | source_text | str | Short string of text containing the claimed behavior. | text_unit_id | str | ID of the text unit the claim text was extracted from.
>
> **communities** ... This is a list of the final communities generated by Leiden. Communities are strictly hierarchical, subdividing into children as the cluster affinity is narrowed. | period | str | Date of ingest, used for incremental update merges. ISO8601
>
> **community_reports** ... | findings | dict[] | LM-derived list of the top 5-10 insights from the community. Each item contains summary and explanation values.

## 核心机制拆解（中文）

**Indexing 数据流（标准管线）：**
1. 文档 → text units（默认 300 token chunk，overlap 100）
2. 每 text unit 上 LLM 抽"实体+描述+关系（含 strength）"——gleaning 多轮补抽（继续问"还有吗"）提升召回
3. 同名实体跨 unit 合并 → entity summarization（多次出现的描述合并成单一 summary）；关系同理（weight = 各实例 strength 之和）——即**描述合并而非证据堆叠**
4. Leiden 社区检测 → 层级社区 → 每 community 生成 report（含 findings 5-10 条）
5. 可选 claim extraction（covariates 表）：**subject/object/type/description/status(TRUE|FALSE|SUSPECTED)/start_date/end_date/source_text/text_unit_id** —— 一个完整的"带真值判断与时间区间的断言"结构，且强制挂 text_unit 溯源

**溯源引用体系（对我们最关键）：** 所有派生表（entities/relationships/communities/claims）都持有 `text_unit_ids` 数组指回 chunk；documents 表持 `text_unit_ids`；chunk 持全文。即任意层的知识都可回落到原文区间。`period`（ingest 日期）字段专为增量更新合并设计。

**双检索模式：** Global（社区报告 map-reduce 式汇总答全局问题）、Local（实体邻域扩展：实体→关系→相邻实体→相关 text units→社区报告→claims）。

**成本控制：** 官方自估抽取占总索引成本 ~75%；对策是 FastGraphRAG（spaCy 名词短语 + 共现边，chunk 缩到 50-100 token）与 auto prompt tuning（用样本数据自动调 prompt）。

## 证据与局限

- 证据：3100+ 引用；微软生产化（parquet 输出、增量更新、UI 可视化）；文档把每一层 schema 写得可复现。
- 局限：(1) 索引成本高（百万 token 级语料即需数百美元级 LLM 调用，2024 社区实测常见抱怨）；(2) 全局检索依赖社区摘要质量，召回"精确事实"不如局部/向量检索；(3) claim 提取默认为"识别欺诈类恶意行为"设计（文档原话 "claims are typically oriented around identifying malicious behavior such as fraud"），并非通用事实库；(4) 增量更新弱项：新文档进来后社区报告需重算（period 字段只做 merge 标记）。

## 对我们的适用性

1. **claim/covariate 表结构几乎就是我们"原子事实+矛盾发现"的现成 schema**：subject/object/status/start_end 区间/source_text 溯源/text_unit 指针——比我们 dl_card 更原子，可直接作为"文档提炼层"的目标表示（status 三值 TRUE/FALSE/SUSPECTED 天然对接矛盾扫描）。
2. **描述合并策略**（多次出现的实体描述 LLM 合并成单 summary + 关系 weight 累加）是我们跨文档综合（同一实体在不同资料出现）可用的低成本方案。
3. **社区层级报告（Leiden + 分层 findings）** 是我们目前缺失的"自顶向下概览"层——对创作辅助（"这批资料的主题地图"）价值大，但不急。
4. 诚实说：GraphRAG 是**批处理**索引，我们已有增量式时序图谱，不应整体引入；应吸收其 schema/溯源设计而非管线。FastGraphRAG 的"NLP 抽取 + LLM 只做汇总"给了我们成本分层的样板（本地小模型做粗抽，云端 LLM 做合并与判断）。
