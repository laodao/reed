## 1. 提示词工程最佳实践（Review 标准）

> 以下原则综合自 Anthropic 官方指南、OpenAI Best Practices、2026 Prompt Engineering Guide 等权威来源。

### 1.1 结构与组织

| 原则 | 说明 |
|------|------|
| **清晰分离指令与输入** | 使用 XML 标签（`<instructions>` / `<context>`）或明确分隔符区分"要做什么"和"处理什么" |
| **关键指令放首尾** | 模型对开头和结尾的注意力最高（"Lost in the Middle" 效应），避免将关键约束放在中间 |
| **控制总长度** | System prompt 建议 150-300 词；超过 3000 tokens 后推理性能下降 |
| **静态内容前置** | 将角色设定、格式要求等静态内容放开头，动态数据放结尾，利于缓存 |

### 1.2 角色设定（Persona）

| 原则 | 说明 |
|------|------|
| **适用场景** | 对创意/开放式任务有效；对分类/事实性 QA 影响可忽略 |
| **避免过度堆砌** | 不要自动给每个 prompt 加角色（cargo-culting），只在需要时加 |
| **同一功能一致** | 同一业务流程的不同步骤应使用统一的角色设定 |
| **简洁具体** | 用一句话说明角色即可，无需过度描述（"10年经验"比"100年经验"更合理） |

### 1.3 输出格式控制

| 原则 | 说明 |
|------|------|
| **提供明确模板** | 给出期望的输出结构，而非只说"输出 JSON" |
| **Few-shot 示例** | 3-5 个多样化示例可显著提高格式稳定性 |
| **强调一次即可** | 重复强调同一约束不会提高遵从度，反而浪费 token |
| **正向表述** | 说"输出纯 JSON"比"不要输出其他内容"更有效（Pink Elephant Problem） |

### 1.4 避免的反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| ❌ 过度强调 `⚠️⚠️⚠️ CRITICAL!` | 对现代模型有反效果，引起混乱 | 用清晰的格式说明代替 |
| ❌ 否定指令 `不要做X` | 模型反而更容易执行 X | 说"要做 Y"（正向指令） |
| ❌ 模糊约束 `不要太长` | 模型无法量化 | 说"2-3 句话"或"100-200 字" |
| ❌ 过多无关细节 | 分散注意力，降低核心任务质量 | 只保留与任务直接相关的信息 |
| ❌ 标记系统不统一 | 解析复杂度高，bug 风险 | 统一使用一套标记格式 |
| ❌ 术语不一致 | 同一概念在不同提示词中用不同名称 | 建立术语表，全局统一 |

### 1.5 一致性与逻辑

| 原则 | 说明 |
|------|------|
| **业务流程连贯** | 上下游提示词的输入输出格式应严格对齐 |
| **枚举值统一** | 同一字段在不同提示词中必须使用相同的枚举值 |
| **字段定义一致** | 同名同义字段的类型、取值范围必须一致 |
| **角色分工明确** | 编剧做编剧的事（文本/剧情），导演做导演的事（镜头/画面） |

## 2. 剧本生成

**文件**: `narrative/ai/script-generator.ts`

### 2.1 完整剧本生成 — User Prompt（`SCRIPT_GENERATION_PROMPT`）

**用途**: 将小说章节拆分为结构化场景数据 + 章节梗概 + 剧本正文。

**角色设定**: `你是一位拥有10年以上一线影视工业经验的职业编剧。`

**提示词结构**（~200 行）:
```
## ⚠️⚠️⚠️ 最重要：你必须输出结构化 JSON 场景数据！

输出顺序：
1. 先输出 JSON 场景数据（【场景数据开始】...【场景数据结束】）
2. 再输出章节梗概（【梗概开始】...【梗概结束】）
3. 最后输出剧本正文（【剧本正文开始】...【剧本正文结束】）

## ⭐ 强约束：所有引用必须使用 binding ID
- locationBindingId → 从【可用地点列表】选
- characterBindingId → 从【可用角色列表】选
- itemBindingId → 从【可用物品列表】选
找不到填 null，不要瞎编 ID

## 场景拆分原则
1. 地点变化拆为新场景
2. 时间跳跃拆为新场景
3. 主要角色组合变化可拆分
4. 情感氛围显著变化可拆分
5. 每个场景有明确视觉焦点

## JSON 场景数据格式示例
{ ... 完整 JSON schema 示例 ... }

## ⭐ 字段输出质量要求
- sceneDescription: 空间布局 + 陈设材质 + 关键物件
- locationKeyObjects: 3-6 个关键物件
- lighting: 光源 + 方向 + 强度 + 色调
- outfit: 服装名称（颜色，风格）

## 可用角色列表 / 可用地点列表 / 可用物品列表 / 章节内容
```

**调用者**: `generateFullScript()`, `generateScript()`

## 3. 分镜生成

**文件**: `narrative/ai/storyboard-generator.ts`

### 3.1 批量分镜生成 — User Prompt（`STORYBOARD_GENERATION_PROMPT`）

**用途**: 根据场景剧本一次性生成全部分镜。

**角色设定**: `你是一个专业的影视导演和分镜师。`

**提示词结构**（~120 行）:
```

### 镜头角度：6 种（eye_level → worms_eye）

## 分镜设计原则
1. 开场用远景或全景
2. 对话用中景或近景正反打
3. 情感用近景或特写
4. 转场考虑前后衔接
5. 节奏控制

## 画面描述格式要求
【场景】地点 + 空间布局 + 关键物件
【人物】角色 + 位置 + 表情 + 服装 + 动作
【动作】正在发生什么 + 细节 + 交互
【氛围】光线 + 色调 + 情绪

## 输出格式
{ "storyboards": [ { ... } ] }

## 场景剧本
{sceneScript}
```

**System Prompt**: `你是一个专业的影视导演和分镜师。请严格按照 JSON 格式输出，不要添加任何额外的文字说明。`

**状态**: `@deprecated` — 建议用 `generateStoryboardsIncremental`

1. 场景开场需要建立镜头

**System Prompt**: `你是一个专业的影视导演。请根据场景内容分析分镜需求，严格按照 JSON 格式输出。`

## 9. 深度 Review 报告

### 9.1 错误与 Bug

#### 🔴 E1: 角色设定违反专业分工

**位置**: 剧本生成（2.1/2.2）、场景润色（4.1）

**问题**: 让"编剧"角色输出 JSON 结构化场景数据。

**分析**:
- 编剧的职责是写故事、对白、情节
- JSON 结构化数据是程序输出，不是创作
- 这导致模型需要在"创意写作"和"格式化输出"之间切换，降低两者质量

**建议**:
- System prompt 只强调编剧的创作能力
- 将 JSON 格式要求完全放在 user prompt 的"输出规范"部分
- 或改为"你是一个擅长结构化输出的编剧助手"

#### 🔴 E2: 标记系统不一致导致解析复杂

**位置**: 全模块

| 标记格式 | 使用位置 | 解析代码 |
|----------|----------|----------|
| `【场景数据开始】...【场景数据结束】` | 剧本生成 2.1 | 需 4 层 fallback |
| `===SCENES_JSON===...===SCENES_JSON_END===` | 梗概拆分 2.4 | 需 3 层 fallback |
| `===SCENE_JSON===...===SCENE_JSON_END===` | 场景润色输入 4.2 | 需 2 层 fallback |
| `===POLISHED_JSON===...===POLISHED_JSON_END===` | 场景润色输出 4.2 | 需 2 层 fallback |
| `===SYNOPSIS===...===SYNOPSIS_END===` | 旧格式（兼容） | 需 1 层 fallback |
| `===SCRIPT===...===SCRIPT_END===` | 旧格式（兼容） | 需 1 层 fallback |

**问题**:
- 6 种不同标记，解析代码需要多重 fallback
- 维护成本高，容易遗漏某种格式
- 用户看到不同格式的输出会困惑

**建议**:
- 统一为 `【XXX_BEGIN】...【XXX_END】` 格式
- 在提示词中只使用这一种格式
- 解析代码保留旧格式兼容 3 个月后移除

#### 🔴 E3: 枚举值不一致

**位置**: 分镜生成 vs VLM 推断

| 字段 | 分镜生成（3.1/3.2） | VLM 推断（8.1） | 问题 |
|------|---------------------|-----------------|------|
| shotType | `extreme_long / long / full / medium / close / extreme_close / detail` | `big_close_up / close_up / medium / long / wide` | **5 个值完全不同** |
| cameraAngle | `eye_level / high / low / dutch / birds_eye / worms_eye` | `eye_level / high / low / overhead / dutch` | `overhead` vs `birds_eye` |
| cameraMovement | 15 种（`static / pan_left / dolly_in / ...`） | 6 种（`static / push / pull / pan / track / handheld`） | **完全不同的预设集** |

**问题**:
- VLM 推断的输出无法直接用于分镜生成
- 需要额外的映射函数，容易出 bug
- 用户看到不一致的术语会困惑

**建议**:
- 建立统一的镜头语言枚举定义（`shared/types/episode-production.ts`）
- 所有提示词引用同一套枚举
- VLM 推断输出后通过映射函数转换为标准枚举

#### 🔴 E4: 字段定义冲突

**位置**: 资产设定反推（5.1）vs 资产自由文本提取（6.1）

| 字段 | 设定反推 5.1 | 自由文本提取 6.1 | 冲突 |
|------|--------------|------------------|------|
| race | `"east_asian" / "south_asian" / ...`（7 种枚举） | 自由文本（如"东亚" / "欧洲"） | **类型不同** |
| gender | `"男" / "女" / "其他"` | 中文描述 | **格式不同** |

**问题**:
- 同一字段在不同功能中定义不同
- 数据在两个功能间传递时需要转换
- 用户看到不一致的字段会困惑

**建议**:
- 统一字段定义为枚举类型
- 在 `shared/types/episode-production.ts` 中定义标准字段
- 所有提示词引用同一套定义

### 9.2 反模式与不良实践

#### 🟡 A1: 过度强调 JSON 输出

**位置**: 剧本生成 2.1

**问题代码**:
```
## ⚠️⚠️⚠️ 最重要：你必须输出结构化 JSON 场景数据！
**这是你最重要的任务！如果不输出 JSON 场景数据，整个任务就是失败的！**
**这部分绝对不能跳过！如果跳过，整个生成将失败！**
```

加上 system prompt 中再次强调：
```
必须输出【场景数据开始】【场景数据结束】标记的 JSON 场景数据！
```

**违反原则**:
- 重复强调同一约束不会提高遵从度（Anthropic 指南）
- 过多警告词会分散注意力，降低核心任务质量
- 违反"正向表述"原则（说"要做什么"而非"不要做什么"）

**建议**:
- 保留 1 处强调即可
- 其余用清晰的格式说明替代
- 示例：
  ```
  ## 输出格式
  请按以下顺序输出，每部分用对应标记包裹：
  1. 【场景数据开始】JSON 场景数据【场景数据结束】
  2. 【梗概开始】章节梗概【梗概结束】
  3. 【剧本正文开始】剧本正文【剧本正文结束】
  ```

#### 🟡 A2: 否定指令过多

**位置**: 多处

**示例**:
- `不要添加任何额外的开场白或结束语`
- `不要瞎编 ID`
- `不要解释，不要 markdown 围栏`
- `切勿编造完全脱离原文的细节`

**违反原则**:
- Pink Elephant Problem：否定指令反而让模型更容易执行被禁止的行为
- 应改为正向指令

**建议**:
| 否定指令 | 正向改写 |
|----------|----------|
| 不要添加开场白 | 直接输出 JSON 数据 |
| 不要瞎编 ID | 只使用提供的 ID |
| 不要解释 | 只输出 JSON |
| 切勿编造 | 没有线索时输出 null |

#### 🟡 A3: 角色设定过度堆砌

**位置**: 剧本生成、场景润色

**问题**:
- `你是一位拥有10年以上一线影视工业经验的职业编剧`
- `擅长把粗糙的剧本场景润色成富有画面感、情感张力和潜台词的成熟剧本`

**违反原则**:
- 对结构化输出任务无效（角色设定对分类/事实任务影响可忽略）
- 过度描述分散注意力

**建议**:
- 简化为：`你是影视编剧助手。`
- 将创作能力要求融入具体任务描述中

#### 🟡 A4: 模糊约束

**位置**: 实体提取 7.2

**问题**:
- `角色描述不超过 50 字` — "字"的定义不明确（中文字符？英文单词？）
- `简要描述` — 多简要？

**违反原则**:
- 模糊约束无法被模型准确执行

**建议**:
- `角色描述控制在 30-50 个中文字符`
- `描述用 1-2 句话，不超过 100 字`

### 9.3 一致性问题

#### 🟡 C1: 同一功能角色设定不一致

**位置**: 剧本生成模块

| 功能 | System Prompt 角色 | User Prompt 角色 |
|------|-------------------|------------------|
| 完整剧本生成 | 拥有10年以上一线影视工业经验的职业编剧 | 同 system |
| 简化剧本生成 | 专业的影视编剧，擅长将小说转换为视频剧本 | 同 user |
| 梗概拆分场景 | 专业的影视编剧 | 专业的影视编剧 |

**问题**:
- 同一业务流程使用 3 种不同的角色描述
- 可能导致模型行为不一致

**建议**:
- 统一为：`你是影视编剧助手，擅长将小说转换为结构化剧本。`

#### 🟡 C2: 分镜生成角色设定不一致

**位置**: 分镜生成模块

| 功能 | System Prompt 角色 | User Prompt 角色 |
|------|-------------------|------------------|
| 批量分镜生成 | 专业的影视导演和分镜师 | 同 system |
| 逐个分镜生成 | 专业的影视导演和分镜师 | 同 system |
| 分镜需求分析 | 专业的影视导演 | 无角色设定 |
| 分镜 AI 填充 | 专业的影视导演 | 专业的影视导演和分镜师 |

**问题**:
- 同一功能（分镜生成）使用"导演"和"导演+分镜师"两种角色
- 分镜需求分析完全没有角色设定

**建议**:
- 统一为：`你是影视分镜师，擅长将剧本拆解为视觉镜头。`

#### 🟡 C3: 输出格式指令不一致

**位置**: 全模块

| 功能 | 格式指令 | 位置 |
|------|----------|------|
| 剧本生成 | 在 user prompt 开头强调 | 第 1 行 |
| 分镜生成 | 在 user prompt 末尾强调 | 最后 1 段 |
| 场景润色 | 在 system prompt 末尾强调 | 最后 1 行 |
| 资产设定反推 | 在 user prompt 末尾强调 | 最后 1 行 |

**违反原则**:
- 关键指令应放在首尾，但位置不统一
- 有时在 system，有时在 user

**建议**:
- 统一将格式要求放在 user prompt 的**开头**（任务描述后）
- System prompt 只放角色设定和通用约束

#### 🟡 C4: 标记风格不统一

**位置**: 全模块

| 标记风格 | 使用位置 | 说明 |
|----------|----------|------|
| `【XXX开始】...【XXX结束】` | 剧本生成 | 中文标记 |
| `===XXX===...===XXX_END===` | 分镜/润色/资产 | 英文等号标记 |

**问题**:
- 两种完全不同的标记风格
- 增加解析复杂度

**建议**:
- 统一为 `【XXX_BEGIN】...【XXX_END】`
- 英文标记便于正则匹配，中文括号便于阅读

### 9.4 逻辑与流程问题

#### 🔴 L1: 剧本生成 → 分镜生成的数据流断裂

**问题**:
- 剧本生成输出 `locationBindingId / characterBindingId / itemBindingId`
- 分镜生成（3.1）的 user prompt 中**没有提及这些 binding ID**
- 分镜生成只看到 `characterName`，无法关联到具体资产

**影响**:
- 分镜生成无法正确引用资产
- 需要额外的绑定步骤

**建议**:
- 在分镜生成的 scene context 中包含 binding ID
- 或在分镜提示词中说明如何引用资产

#### 🔴 L2: 分镜需求分析 → 逐个分镜生成的信息丢失

**问题**:
- 3.3 分析输出 `shotTypes: ["long", "medium", "close"]`
- 3.2 逐个生成时，`{contextInfo}` 只包含前一个镜头的参数
- 没有将 3.3 的分析结果（建议的 shotTypes）传递给 3.2

**影响**:
- 3.3 的分析结果被浪费
- 3.2 无法参考整体规划

**建议**:
- 将 3.3 的 `shotTypes` 数组传递给 3.2
- 在 `{contextInfo}` 中增加"整体分镜规划"部分

#### 🟡 L3: 场景润色的输入输出不对称

**问题**:
- 输入：完整 SceneScript JSON（含所有字段）
- 输出：只输出部分字段（sceneDescription / originalText / narration / dialogues / actions）

**影响**:
- 模型需要理解"只润色这些字段，其他字段不变"
- 但提示词中没有明确说明"哪些字段不需要润色"

**建议**:
- 在 user prompt 中明确说明：
  ```
  请只润色以下字段，其他字段保持不变（不要输出）：
  - sceneDescription / originalText / narration / dialogues / actions

  以下字段不需要润色：
  - sceneNumber / location / locationBindingId / timeOfDay / weather / mood / lighting
  ```

#### 🟡 L4: 资产设定反推的 evidence 字段未使用

**问题**:
- 5.1 提示词要求输出 `_evidence` 字段（说明推断依据）
- 但代码中没有看到对 `_evidence` 的处理逻辑

**影响**:
- 模型生成 `_evidence` 浪费 token
- 用户无法看到推断依据

**建议**:
- 要么在 UI 中展示 `_evidence`
- 要么从提示词中移除该字段

### 9.5 缺失与不足

#### 🟡 M1: 缺少 Few-shot 示例

**位置**: 除剧本生成外的所有功能

**影响**:
- 模型输出格式不稳定
- 需要更多解析 fallback

**建议**:
- 为以下功能添加 1 个简短示例：
  - 分镜生成（3.1/3.2）
  - 场景润色（4.1）
  - VLM 推断（8.1）
  - 实体提取（7.2）

**示例**（分镜生成）:
```
## 示例

输入场景：
场景 1: 茶馆 · 白天
角色：张三（坐在角落）
对白：张三："请来一壶茶"

输出：
{
  "shotNumber": 1,
  "shotType": "long",
  "cameraAngle": "eye_level",
  "cameraMovement": "static",
  "frameDescription": "【场景】茶馆内景，木质桌椅，晨光从窗户洒入\n【人物】张三位于画面右下角，侧身面向柜台\n【动作】张三抬手示意店员\n【氛围】暖色调，市井氛围",
  "duration": 5
}
```

#### 🟡 M2: 缺少温度参数控制

**位置**: 所有提示词

**问题**:
- 只指定了 `maxTokens`
- 没有控制 temperature / top_p

**影响**:
- 不同模型默认参数不同
- 创意类任务可能过于保守
- 结构化任务可能过于发散

**建议**:
| 任务类型 | 建议 temperature | 说明 |
|----------|------------------|------|
| 创意写作（剧本/润色） | 0.7-0.8 | 保持创造性 |
| 结构化输出（分镜/提取） | 0.1-0.3 | 保证格式稳定 |
| 分析判断（需求分析） | 0.3-0.5 | 平衡创造与准确 |

#### 🟡 M3: 缺少输出验证提示

**位置**: 大多数提示词

**问题**:
- 只要求"输出 JSON"
- 没有让模型自检

**建议**:
- 在关键提示词末尾增加：
  ```
  请在输出前自检：
  1. JSON 是否合法（可被 JSON.parse 解析）
  2. 所有必填字段是否存在
  3. 枚举值是否在允许范围内
  ```

#### 🟡 M4: 长文实体检测硬编码截断

**位置**: 7.2

**问题**:
- `text.substring(0, 4000)` — 硬编码 4000 字
- 超过部分完全丢失

**影响**:
- 长小说无法完整处理
- 可能遗漏重要实体

**建议**:
- 改为按 token 数估算：`text.substring(0, Math.min(text.length, 8000))`
- 或分块处理：每 4000 字调用一次，合并结果
