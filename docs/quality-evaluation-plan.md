# 产物质量评估方案

## 评估目标
评估每个已完成的 BUG 修复是否真正提升了产物质量，而不是仅仅修复了格式问题。

## 评估维度

### 1. BUG-1: VLM 枚举映射
**修复内容**：VLM 输出的景别/角度/运镜值映射到分镜系统标准枚举

**质量评估**：
- **语义正确性**：映射后的枚举值是否语义正确？
  - VLM `big_close_up` → 标准 `extreme_close`？还是 `close`？
  - VLM `close_up` → 标准 `close`？
  - VLM `wide` → 标准 `long` 还是 `extreme_long`？
- **映射覆盖率**：是否有 VLM 输出的值没有被映射？
- **下游影响**：映射后的值是否影响下游的图片/视频生成质量？

**评估方法**：
1. 代码审查：检查映射表定义是否合理
2. 实际测试：调用 VLM 推断几个场景，检查映射结果
3. 人工判断：映射后的值在分镜系统中是否合理

### 2. BUG-3: race 字段统一为枚举
**修复内容**：正向提取的 race 字段从自由文本改为枚举

**质量评估**：
- **枚举准确性**：LLM 是否能正确输出枚举值？
  - 输入"东亚面孔" → 输出 `east_asian`？
  - 输入"欧洲人" → 输出 `european`？
- **信息损失**：枚举是否丢失了自由文本的细粒度信息？
  - 自由文本"中日混血" → 枚举只能选一个？
- **下游兼容性**：下游消费方是否能正确处理枚举？
  - 分镜生成提示词如何使用 race 字段？
  - 图片生成提示词如何使用 race 字段？

**评估方法**：
1. 代码审查：检查枚举定义是否覆盖所有合理场景
2. 实际测试：用不同角色描述调用正向提取，检查输出
3. 人工判断：枚举值是否足够？是否有信息损失？

### 3. BUG-4: 分镜分析结果传递给逐个分镜生成
**修复内容**：将分镜需求分析的 shotTypes/pacing 传递给逐个分镜生成

**质量评估**：
- **实际效果**：AI 是否真的参考了分析结果？
  - 分析建议 `[long, medium, close]`，实际生成的分镜是否包含这些景别？
  - 分析建议"渐快节奏"，实际镜头时长是否递减？
- **质量提升**：分镜序列是否更连贯、更合理？
  - 景别分布是否更有节奏？
  - 是否避免了连续相同景别？
- **副作用**：是否引入了问题？
  - AI 是否过度依赖分析结果，忽略了场景本身的需求？
  - 是否有场景不适合按分析结果生成？

**评估方法**：
1. 代码审查：检查传递的数据格式是否清晰
2. 实际测试：用同一场景对比修复前后
   - 修复前：不传分析结果，生成分镜
   - 修复后：传分析结果，生成分镜
3. 人工评估：对比两组分镜的质量
   - 景别分布是否更合理？
   - 镜头序列是否更连贯？
   - 是否符合场景氛围？

## 评估流程

### 阶段 1: 代码审查
- 检查每个修复的实现是否正确
- 检查是否有遗漏或副作用

### 阶段 2: 实际测试
- 为每个修复设计测试用例
- 调用真实 API 生成产物
- 收集生成结果

### 阶段 3: 质量评估
- 人工评估生成结果的质量
- 对比修复前后的差异（如有）
- 记录评估结论

### 阶段 4: 更新文档
- 将评估结论写入优化方案文档
- 如果有问题，提出修复方案

## 评估标准

| 评估项 | 合格标准 | 不合格标准 |
|--------|----------|------------|
| 语义正确性 | 映射/转换后的值在业务场景下合理 | 映射/转换后的值语义错误 |
| 信息完整性 | 没有丢失关键信息 | 丢失了重要细节 |
| 下游兼容性 | 下游消费方能正确处理 | 下游出现错误或异常 |
| 质量提升 | 修复后质量明显提升或无变化 | 修复后质量下降 |
