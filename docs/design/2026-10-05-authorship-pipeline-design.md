# 长文写作·作者性管道设计——「去 AI 味」的系统级方案

- 日期：2026-10-05
- 状态：待评审
- 定位：实施级设计。把「AI 味」从 prompt 补丁问题提升为管道架构问题，在现有章节生成链路上补出四个缺失的层（作者 / 意图 / 反馈 / 不完美性），不推翻既有架构。
- 关联：`2026-09-16-knowledge-brain-design.md`（大脑侧作者画像的数据源）、episode-production 章法工作流（唯一写作入口，5d52c927 收口后无直写旁路）。

---

## 0. 结论摘要

**诊断**：现有章节生成管道是一个「设定执行器」——大纲给情节任务、八分区注入设定、系统提示给一致性规则、质量门查字数与矛盾。每个环节都在优化**内容正确性**，没有任何环节优化**表达的独特性**。AI 味（套话、均匀、面面俱到、故作玄虚）不是某个环节的瑕疵，而是这个架构的必然输出：模型接到「根据规格生成交付物」的任务，就交付规格品——规格品的语言就是训练分布的高概率区。

**方案**：不做防御性的「负面清单」，而是建设性的**注入作者性**——让系统里存在一个「具体的作者」：

> 意图层（这章想让读者感到什么）→ 作者层（谁在写：文风卡+人格+语感锚）→ 生成层（正面笔法+两遍制）→ 反馈层（读者模拟审查，与一致性审查平行）→ 不完美性（主动引入人类的失控）

四层是乘法关系：单拎任何一项效果有限，体系立起来才有质变。

**诚实边界**：网文的「人味」很大程度是「类型的味道」（口语感、地道的类型语言），这部分可以从语料学到、被文风卡与知识大脑供给；但「真实生活经验的重量」模型没有，不过度承诺。验收以人工盲评为主、文风维度统计为辅。

---

## 1. 问题分层：AI 味的五层解剖

| 层 | 表现 | 根源 | 对应方案层 |
|---|---|---|---|
| 词汇/句法 | 高频套话、句式均匀、段落等长 | 模型默认语域（无文风指令时的分布中心） | 作者层（文风卡）+ 生成层（改稿遍） |
| 修辞 | 比喻安全、描写面面俱到、无观察个性 | 均匀注意力，没有「注意力的指纹」 | 作者层（作者人格） |
| 叙事 | 情绪直告（telling）、视角漂移、信息投喂节奏均匀 | 生成任务里没有「传达体验」的目标 | 意图层 |
| 结构 | 每章同一模板（承接-发展-钩子）、悬念等距撒、**故作玄虚**——模型把「埋伏笔」执行成均匀的氛围渲染 | 大纲只给「发生了什么」，不给「想让读者感到什么」 | 意图层（核心） |
| 意图 | 没有「想说的东西」；对所有角色一视同仁；规格品心态 | 管道里没有作者的位置 | 全部四层 |

「故作玄虚」的定位在**结构层**：现有系统提示要求「注意呼应前文伏笔、适当铺垫后续情节」，模型执行「埋伏笔」的廉价方式就是等距的氛围渲染（冥冥之中/空气凝固/欲言又止）。人类是在自己真正在意的地方下重手——这个「在意」必须由意图层显式供给。

## 2. 目标架构

```
┌──────────────────────────────────────────────────────────────┐
│ 既有管道（保留）：大纲 → 八分区设定注入 → 初稿 → 字数门 →    │
│                  写后一致性审查（ConsistencyService）          │
├──────────────────────────────────────────────────────────────┤
│ 新增四层（作者性管道）：                                      │
│  L1 作者层   文风卡（项目级资产）：样章 + 可检验维度 + 作者    │
│              人格 + 采样参数建议；上章结尾 300-500 字语感锚    │
│  L2 意图层   讲述意图（大纲行新字段）：本章要让读者感受到什么、 │
│              想玩什么花活、能量等级、闲笔预算                  │
│  L3 生成层   初稿：作者人格 + 意图 + 文风卡注入；              │
│              改稿遍：对齐文风卡的读感重写（重灾区优先）        │
│  L4 反馈层   读者模拟审查（低档）：想跳读/出戏/被戳中的段落    │
│              标注 → 触发与聚焦改稿遍 → 结果留档可查            │
└──────────────────────────────────────────────────────────────┘
```

L4 与写后一致性审查**平行**（一个管「读起来怎么样」，一个管「内容对不对」），互不替代。

## 3. L2 意图层（最便宜，先做）

### 3.1 数据模型

`lw_outlines` 加一列：

```sql
telling_intent TEXT NULL  -- 讲述意图（JSON，见 3.2）
```

### 3.2 telling_intent 的 JSON 约定

```ts
interface TellingIntent {
  /** 本章想让读者产生的核心感受（一句话，如「为程野捏一把汗」）——必填 */
  readerFeeling: string
  /** 本章作者想玩的花活（如「全程不写反派的正面镜头，只写他造成的影响」）——可选 */
  authorMove?: string
  /** 能量等级：low=平淡收束过渡章 / mid=常规推进 / high=兴头章允许写超 20%——必填，缺省 mid */
  energy: 'low' | 'mid' | 'high'
  /** 闲笔预算：本章至少一处与主线无关但有生活质感的细节（一句话建议素材方向）——可选 */
  asideHint?: string
}
```

`energy` 与 `asideHint` 同时承载 §6 的不完美性注入——不另立机制。

### 3.3 产出与消费

- **产出**：大纲生成（章法设计）的 AI 产物多一个字段；生成 prompt 增一条指令：`telling_intent = 本章的讲述意图（读者感受 + 作者花活 + 能量等级）`。存量大纲该列为空——章节生成时若为空，按 `energy=mid` 缺省，不阻塞（向后兼容）。
- **用户可编辑**：大纲编辑界面露出该字段（textarea 或表单），AI 产物只是初稿。
- **消费**：`assembleChapterGeneration` 的分区组装新增「讲述意图」分区（priority 排在章节任务之后、设定之前——它是本章的「为什么写」）。

### 3.4 为什么这层直击「故作玄虚」

悬念的等距撒布源于模型只知「要埋伏笔」不知「哪里值得下重手」。`readerFeeling` 给了每章一个具体的体验目标，`authorMove` 允许把「埋伏笔」具体化为可执行的物理动作（一件具体物件/一句反常的对话），氛围渲染失去默认位置。

## 4. L1 作者层

### 4.1 文风卡（StyleProfile）

**存储（M1 最小）**：`lw_story_overview` 已有 `style`（text）列——现状是一段风格基调文字。新增 `style_profile`（text，JSON）列承载文风卡，`style` 保留为「一句话基调」（生成 UI 已消费它，不动）：

```ts
interface StyleProfile {
  /** 文风样章：300-500 字目标文风原文（用户贴入，或从知识大脑语料选取） */
  sample: string
  /** 可检验维度（从样章归纳；生成后可统计对比——验收的客观锚点） */
  dimensions: {
    /** 平均句长（字）与句长方差（方差大=长短错落，是人味的关键指标） */
    sentenceLength: { mean: number; variance: number }
    /** 对话/叙述/描写 大致配比（如 40/40/20） */
    dialogueRatio: number
    /** 标点习惯：破折号/省略号/短句频率的定性描述 */
    punctuationNotes: string
    /** 比喻与描写的取材域（如「取材市井与食物，不用天文气象」） */
    imageryDomain: string
  }
  /** 作者人格：审美偏好与癖好，含缺陷（如「啰嗦时会重复角色口头禅；偏爱写吃食」） */
  persona: string
  /** 采样参数建议（写作链路透传；provider 支持度见 §7 风险） */
  sampling?: { temperature?: number; frequencyPenalty?: number }
}
```

**维度为什么做成数字**：`sentenceLength.variance`、`dialogueRatio` 可以在生成后程序统计、与样章对比——文风对齐从「写得像一点」的空话变成可验收的指标（§8）。

**M3 演进（本期不做）**：多卡（按场景类型供样：打斗卡/对话卡）时再立独立表；一张卡够 M1/M2 用。

### 4.2 上章结尾语感锚

`assembleChapterGeneration` 新增注入项：**上一章正文最后 300-500 字原文**，标注为「语感锚（对齐文字质感，非情节前情）」。人类是连续写完一本书的，AI 每章无状态重启——语感锚提供跨章的语言连续性，与既有的前情提要是两回事（前者对齐**怎么说**，后者对齐**说了什么**）。第一章无上文时跳过。

### 4.3 作者人格进系统提示

`SYSTEM_PROMPT_TEMPLATE`（`context-prompt.ts`，注意文件头「原样搬自 service 保回归」注释——改动需同步 service 侧并跑章节生成回归）改造为两部分：

1. **通用正面笔法**（替换/增补现有六节，只写「做什么」，零禁令）：
   - 情绪不直说——用动作、生理反应、对话停顿呈现
   - 叙述者只知道视角人物能感知的事
   - 对话允许打断、跑题、答非所问——人在说话，不是在交换信息
   - 段落长短错落；章末停在动作或对话上，不做总结
2. **作者人格位**：`「你在以 {persona} 的身份写这本书」`——从文风卡注入，项目内跨章稳定。

## 5. L4 反馈层：读者模拟审查 + 改稿遍

### 5.1 读者模拟审查（reader-review）

新服务 `reader-review.service.ts`，挂在章法工作流初稿节点之后（与写后一致性检查平行）：

```
输入：初稿全文 + 文风卡样章 + 本章讲述意图 + 目标读者感（overview.style 一句话基调）
人格：一个挑剔的连载读者（不是文学批评家——要真实反应，不要分析）
输出 JSON：
{
  skimSpans:   [{ start: 段落序号, end: 序号, reason: 「想跳读的原因」 }],   // AI 味重灾区
  breakPoints: [{ para: 序号, reason: 「出戏原因（套话/玄虚氛围/说教）」 }],
  hits:        [{ para: 序号, reason: 「被戳中的地方——改稿时保住」 }],
  overall:     1-10 读感分
}
模型档位：低档（跟随 brain 的 atomize 档或宿主缺省）；单次输入≈章全文，输出≤1k token
```

「想跳读的位置」是比任何文学批评都诚实的 AI 味信号——读者不会分析为什么无聊，只会滑过去。

### 5.2 改稿遍（revise pass）——条件触发，控制成本

```
触发规则（按成本升序，任一命中即跑）：
  a) skimSpans 覆盖率 ≤30% 且 overall ≥7 → 不改（多数章直接过，避免每章双倍成本）
  b) 局部重灾区 → 只重写标注段落（输入：该段±1 段上下文 + 文风卡 + hits 保护清单）
  c) skimSpans 覆盖率 >30% 或 overall <5 → 全文重写

改稿人格：「一个挑剔的人类作者在改自己的稿」——不是执行清单，是对齐读感目标
硬约束：情节、设定、人物动作、字数下限一个字不动；只改语言质感
hits 标注的段落：明确指令「这些地方是好的，保住」
模型档位：跟随文风卡 sampling 建议（或宿主）
```

字数门在改稿遍**之后**复核（改稿不许掉字数；不足则回到既有扩写通道）。

### 5.3 留档

`lw_chapter_versions` 现无 metadata 列（核对于 entity：仅 content/version_type/word_count 等）——新增 `review_meta`（text，nullable）一列，落读者审查摘要（overall 分/skimSpans 计数/改稿档位/触发原因）。用户事后能看到「这章为什么被重写、哪里曾被标跳读」，也是文风卡迭代的依据。

## 6. 不完美性注入（随 L2 落地，无独立机制）

- **能量等级**：`telling_intent.energy` 由大纲生成时随机倾向分配（大致 low:mid:high ≈ 2:6:2）——高能量章允许超目标字数 20%，低能量章明确「本章是收束过渡，允许平淡」。消除「每章等长等重」的规格感。
- **闲笔预算**：`asideHint` 给本章一处与主线无关的生活细节一个素材方向（路边摊的味道/配角的口音），初稿 prompt 明确「写进去，别论证它和主线的关系」。均匀的「一切为剧情服务」恰恰是 AI 味。

两项都走意图字段的生成 prompt，不新增配置面。

## 7. 与现有资产的整合

| 资产 | 接口 |
|---|---|
| 章法工作流（唯一入口） | 读者审查节点插初稿后、改稿遍插审查后、落库前；均为 fail-soft（审查失败=跳过改稿直接落库，不阻塞写作主链路） |
| `assembleChapterGeneration` 八分区 | 新增「讲述意图」分区 + 「文风样章与人格」分区 + 「上章结尾语感锚」——沿用 items 勾选机制，用户可在上下文面板里关掉任何一项 |
| `kb_brain_query` 写作工具 | 初稿与改稿的 system note 已存在；查询词建议由意图层生成（如 authorMove=「不写反派正面镜头」时提示检索「侧面描写手法」）——M3 细化 |
| 知识大脑 | **作者画像的数据源**（M3）：goal-distill 新预设「文风画像」hint（从语料归纳句长/对话密度/标点/取材域）→ 经验卡 → 用户手动转录进文风卡。自动化管线后置 |
| ConsistencyService | 平行不合并：一致性管内容对错，读感审查管体验好坏，两道门独立运行 |
| 采样参数 | 文风卡 `sampling` 透传到 provider 调用；需先核实 provider 层 temperature/frequencyPenalty 的透传支持度（M1 的前置检查项，不支持则该项降级为提示词层补偿） |

## 8. 验收口径

1. **人工盲评（主口径）**：同一大纲章节、同模型，现行链路 vs 作者性链路各生成一份，抹去标识后由用户判「哪份更像人写的」+ 标注 AI 味位置。目标：作者性链路胜率 ≥70%（10 章样本）。
2. **文风维度统计（辅口径，客观锚点）**：生成文的句长方差、对话占比与文风卡样章的偏差——`sentenceLength.variance` 显著提升（摆脱等长句）、`dialogueRatio` 向样章收敛。
3. **读感审查趋势**：同一文风卡下，连续 20 章的 overall 分与 skimSpans 覆盖率应呈下降（作者性在反馈闭环中收敛）。
4. **回归红线**：写后一致性审查通过率不因新管道下降（内容正确性不牺牲）；关掉全部新分区后，生成结果与现行链路逐字节等价（既有行为可回退）。

## 9. 实施里程碑

| 期 | 内容 | 量级 | 验收 |
|---|---|---|---|
| **M1 意图+作者** | lw_outlines.telling_intent 列 + 大纲生成产出该字段 + 大纲 UI 露出；style_profile 列 + 文风卡编辑 UI（设置抽屉）；八分区新增三分区（意图/文风/语感锚）；SYSTEM_PROMPT_TEMPLATE 正面笔法改造（含回归）；采样参数透传核实 | 2-3 天 | 同章 A/B 人工盲评有可感差异；关闭新分区=行为回退等价 |
| **M2 反馈+改稿** | reader-review.service + 工作流插节点；revise pass（三档触发）；版本元数据留档；审查结果面板（可选） | 2-3 天 | 盲评胜率 ≥60%；skimSpans 定位与人工标注的重合率抽检；fail-soft 验证（审查挂=正常落库） |

每期沿用既有作业模式：实现 → 单测 → 对抗 review → 修复 → 文档登记。

## 10. 风险与不做的事

**风险**：

| 风险 | 缓解 |
|---|---|
| 文风卡维度归纳失真（样章太短/维度填错） | 维度是建议值非硬约束（进 prompt 而非进采样硬卡）；验收统计只看方差与对话比两个稳健指标 |
| 读者模拟与改稿遍的成本（每章多 1-2 次调用） | 三档触发规则——多数健康章节零改稿；审查用低档模型；工作流开关（项目级「作者性管道」总闸，缺省开但可关） |
| 改稿遍改丢情节细节 | 硬约束写进 prompt + 改稿后跑既有一致性门禁复核（不改初稿的既检项全量重跑）；hits 保护清单 |
| provider 不透传采样参数 | M1 前置核实；不支持则该项从设计裁剪，靠人格与样章对齐补偿（不阻塞主链路） |
| SYSTEM_PROMPT_TEMPLATE 改动破坏既有回归 | 改动同步 service 侧常量（两处同源）；跑章节生成对比回归；保留旧文案于 git 历史 |
| 大纲生成的意图字段质量差（AI 填得空泛） | 字段用户可编辑；readerFeeling 生成 prompt 给反例（「更精彩❌」「为程野捏一把汗✓」）；空值不阻塞（缺省 mid） |

**不做的事**：

1. **不做负面清单**——词表打地鼠且让文风更僵（用户已定论）。
2. **不做每章无条件双遍**——成本闸门：健康章节直接过。
3. **不做文风卡自动迭代**——读感反馈只留档供人看，改不改卡由用户决定（AI 永不自动改项目级资产，对齐大脑 proposal 治理原则）。
4. **不动一致性审查**——两道门独立，读感永远不为内容正确性让路，反之亦然。
5. **M1 不做按场景类型的多文风卡**——一张卡先跑通，多卡待盲评证明有必要。
