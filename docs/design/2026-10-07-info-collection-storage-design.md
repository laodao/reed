# 信息搜集模块：数据存储与复杂数据设计（专项）

- 日期：2026-10-07
- 状态：**待评审**（主设计文档的专项细化；与主文档冲突时以本文为准）
- 主文档：`docs/design/2026-10-07-info-collection-design.md`（v2）
- 背景：主设计评审中就"搜集到的信息怎么存"展开多轮论证——文字资料与表格数据的分野、行存储的必要性、JSON 列的意义、统计能力、财报类复杂数据的处理。本文把结论固化，含完整论证链，防止后续实施时重新争论。

---

## 0. 结论摘要

> **文字资料进知识库（一条路）；表格数据双层存储——行级数据存 `ic_rows` 作为唯一权威层，知识库放"表说明页"投影供语义检索，文件只作导出物。数据字段装 JSON 列保证通用，叠加五个 measure 约定真列保证可算；宽表（财报类）归一为长表；跨行恒等式校验作为通用质量机制。**

六条结论：

1. **分形态走两条路**：文字资料 → 知识库（既有管线，零新代码）；表格数据 → 行级数据库 + kb 投影。
2. **行存数据库是必要的**：人审、溯源、版本链、增量刷新、去重全部发生在"条"这个粒度，文档存储给不了。
3. **不建物理表**：一张通用表（治理字段真列 + 数据字段 JSON 列），新主题零迁移。
4. **measure 约定列定型五列**：`value / unit / period / metric / dims_json`——定量数据的可计算投影，通用形状而非领域特化。
5. **复杂数据（宽表）宽转长归一**：一行 = 一个数据点；阅读视角的"报表"降级为人审视图与 kb 投影。
6. **行层按需启用**：纯文字资料的项目不写 `ic_rows`，行存储是数据密集型搜集的配置，不是所有搜集的入场费。

## 1. 问题定义：搜集信息的两种形态

| 形态 | 例子 | 正确路径 |
|------|------|---------|
| **文字资料** | 研究报告、新闻、政策原文、观点评述 | 提取正文 → 快照存档 → kb 文档（切块/嵌入/倒排）→ 语义检索。**一条路，无行层** |
| **表格数据** | 统计数据、清单、参数表、财报 | 抽取归一 → 行级落库（权威）→ kb 投影文档（检索）→ 查表工具（精确取数）+ 导出 |

边界情况：一篇文档里既有叙述又有数据（如年报正文）——叙述部分走文字路径，数据部分按抽取规格拆出行。两者不互斥，分的是**条目的形态**，不是来源的形态。

## 2. 存储选型论证

### 2.1 表格数据为什么不能只存知识库文档

kb 检索是"语义相关"，数据问题要求"精确"。整表切块进向量库有两类必然事故：

1. **数字张冠李戴**：查"2020 年出生人口"，召回了 2019 年那一行的 chunk，模型拿着就用。对数据来说，答错比不答更糟。
2. **切块破坏维度对齐**：某个 chunk 里的"1465 万"脱离了行上下文；单位与口径说明（往往在表格脚注）大概率不在同一个 chunk。

精确取数必须"查表"而不是"搜文档"——kb 投影负责让系统**知道有这张表、口径是什么**，取数走查表。

### 2.2 行存数据库 vs 文件（CSV/JSON/Excel 存档）

文件方案的治理需求全是行级的，文件做起来都别扭：

| 治理需求 | 整表存文件 | 行存数据库 |
|------|-----------|-----------|
| 行级溯源（某数字挂来源/引句/分级） | 做不到，来源只能挂整篇 | `source_id` 外键直接指 |
| 逐行人审（2020 待审、2019 已确认） | 只能整篇审 | `status` 逐行状态机 |
| 版本链（2025 新数替代 2024，历史可回溯） | 每次刷新 diff 两个文件 | `superseded_by` 指针 |
| 增量刷新（只补新年份） | 全量重写 | 按游标插入新行 |
| 去重（同一数据采到两次） | 文本比对 | `content_hash` 约束 |
| 批量治理（"来源 X 被证伪，撤其所有数据"） | 全文找 | 一条 `UPDATE WHERE source_id=X` |

文件在这个体系里的正确位置是**导出物**（给下游分析工具用），不是存储层；源页面上"表格长什么样"的保真由**快照**负责。

### 2.3 为什么不每个数据集建一张物理表

动态 CREATE TABLE 与仓库迁移纪律正面冲突：`synchronize: false`、迁移手工注册有序清单、schema-drift 校验、PC/Web 两端成对——运行时建表击穿全部治理。且采集量级（单数据集数千行以内）用不上真列的查询性能。做法：

- 一张通用表 `ic_rows`：**治理字段做真实列**（source_id/status/version/hash——谁都有，享受强类型与索引），**数据字段装一个 JSON 列**（因主题而异，写入口用蓝图 schema + ajv 校验把关）。
- 筛选不牺牲：SQLite `json_extract` 配表达式索引、Postgres jsonb，两端 TypeORM 均支持。
- 聚合在服务层做也毫秒级（数千行量级）。**本模块是资料库不是数仓**，百万行 OLAP 不是需求，真出现走导出进外部工具。

### 2.4 `row_json` 是什么、意义是什么

`row_json` = 一行数据的全部字段序列化成 JSON 存进一个列。它**不是"用 JSON 代替数据库"**——这一行仍是真正的数据库行（有主键、外键、状态、索引），只是"数据字段本身"装在 JSON 里。本质是**用 JSON 列代替物理列**，换取"存储层通用、校验在写入口"。

三种存法对比：

| 存法 | 适合 | 不适合 |
|------|------|--------|
| 物理表（每数据集一张真表） | 字段固定的单一场景 | 通用模块：新主题=新迁移 |
| **行 JSON 表（选定）** | 行级治理 + 任意 schema + 精确查询 + 约定列统计 | 纯聚合分析性能不如真列（约定列补齐，见 §3） |
| 文档（kb/文件） | 语义检索、人读、导出交付 | 精确取数、行级溯源、逐行审阅、增量刷新 |

类比：文档是"把整张表打印成一页纸放进档案柜"，行存储是"每条数据登记成一条台账"。搜集模块的治理动作全发生在"条"这个粒度，所以条必须是可操作单元。

## 3. measure 约定列（可计算投影）

### 3.1 五列定义

背景概念：一条定量数据 = **维度**（从哪些角度切的）+ **度量**（测出来的数）。"2019 年全国出生人口 1465 万人"：2019/全国/出生人口是维度，1465 是度量，万人是单位。

| 列 | 类型 | 含义 | 为什么这样设计 |
|----|------|------|--------------|
| `value` | NUMERIC（可空） | 数值本身：1465、3.4、1200 | 真数字类型 → SUM/AVG/增速/排序原生可用；杜绝 "1,465"、"1465万" 文本形态入库——抽取归一化清洗成纯数字，原始写法留在 row_json |
| `unit` | TEXT | 单位：万人、%、亿元 | **单位是数值身份的一部分**，不同单位不能一起算；独立成列才能 `WHERE unit='万人'` 再聚合；抽取阶段归一写法 |
| `period` | TEXT | 数据所属统计期：`2019`、`2024Q3`、`2024-06` | **不是采集时间**（那是 collected_at），是数据描述的时点；用 TEXT 因统计期粒度不统一（年/季/月），规范字符串同粒度内排序天然正确（`"2019"<"2020"`），时间序列 = `WHERE period BETWEEN ... ORDER BY period` |
| `metric` | TEXT | 指标名：出生人口、营业收入 | 按科目查时间序列是数据分析主查询，必须一等公民（财报案例从 dims_json 升真列，§3.4）；层级科目存路径 `"营业总成本/营业成本"`，天然支持汇总 |
| `dims_json` | JSON | 时间外的切分角度：`{"region":"广东省"}`、`{"segment":"大模型"}` | 不同主题切法不同，无法预建固定列（建了=领域特化）；按需 `json_extract` 筛选；时间因几乎每条定量数据都有才单独成真列 |

### 3.2 映射机制

蓝图 schema 声明映射约定，归一化器把 row_json 字段同步填进约定列：

```json
{ "id": "pop-birth", "title": "出生人口",
  "jsonSchema": { /* 完整字段定义，ajv 校验 */ },
  "convention": {
    "type": "measure",
    "map": { "value": "value", "unit": "unit", "period": "year",
             "metric": "metric", "dims": ["region"] }
  } }
```

```text
row_json: {"year":2019,"region":"全国","metric":"出生人口","value":1465,"unit":"万人","caliber":"常住人口"}
约定列:   value=1465 | unit='万人' | period='2019' | metric='出生人口' | dims_json={"region":"全国"}
（caliber 等描述性字段不参与计算，留 row_json）
```

一致性规则：**row_json 是行的全量权威，约定列由归一化器派生**；任何行编辑后重跑归一化同步（幂等），约定列与 row_json 不一致以 row_json 为准并可程序检测。

### 3.3 通用性论证

"指标-时间-维度-数值-单位"不是某个领域的形状，是**一切定量数据的通用形状**（市场规模、票房、利率、震级、评分都长这样）。它属于数据形态约定，不属于领域——与主文档"不内置领域逻辑"不冲突。约八成数据需求可套进 measure 约定走真列；特殊形状（多值行、矩阵行）留在 row_json，两者并存。**约定列是可选加速器，不是入场检查**——蓝图不声明 convention 的 schema 照常落 row_json。

### 3.4 `metric` 为什么升真列

初版约定列只有四列（value/unit/period/dims_json），指标名暂定放 dims_json。财报场景终结了这个犹豫：按科目查时间序列是财务分析的主查询（"营收五年趋势"），科目名必须可索引、可 GROUP BY。通用性检验同样通过——"指标名"在任何定量数据里都是维度之首，升真列是对通用形状的修正，不是对财报的特化。

## 4. 复杂数据：宽表归一（以财报为例）

### 4.1 阅读视角 vs 分析视角

"一张报表一行、很多列都能分析"是**阅读视角**（报表长这样）；分析的标准形状是**长表**：一行 = 一个数据点。

```text
原始（宽）：腾讯 2024 年报利润表：营业收入 | 营业成本 | 毛利 | 销售费用 | ...
归一（长，进 ic_rows）：
  value=6603 | unit='亿元' | period='2024FY' | metric='营业收入' | dims={"company":"腾讯","statement":"利润表"}
  value=3319 | unit='亿元' | period='2024FY' | metric='营业成本' | dims={"company":"腾讯","statement":"利润表"}
  ...
```

这不是迁就表结构——BI 与财务分析的标准做法就是宽转长：每列要独立筛选、独立成时间序列、独立跨公司对比，拆开后都是一行 SQL（营收趋势 = `WHERE metric='营业收入' ORDER BY period`；毛利率 = 营收行与成本行现算 JOIN）。

**宽→长归一是通用形状变换器**（问卷、参数规格表同理），不是财报特化。

### 4.2 财报处理全流程

1. **抽取**：优先网页版公告/HTML 表格；PDF 走既有解析（@firecrawl），引句锚定放宽到**表行文本级**（锚定到原文表格行，不逐科目逐字）；蓝图预算按科目数给足。
2. **归一**：宽转长 + 单位/币种归一 + 科目路径化。
3. **校验**：引句回验（表行级）+ 跨行恒等式校验（§5，财报是最大受益者）。
4. **人审**：审阅界面按**整表**呈现抽取结果、与快照并排对照——人审 UX 是报表级，治理粒度仍是行级（整表确认 = 逐行落 confirmed）。
5. **落库**：长表行（权威）+ 报表视图文档进 kb（投影）+ 快照（凭证）。

### 4.3 财报特有问题与通用解

| 问题 | 解法 | 通用机制归属 |
|------|------|------------|
| **重述/追溯调整**（2024 年报改了 2023 数据） | 冲突归因四分类的"修订关系"：新行 confirmed、旧行 superseded、归因标注"年报重述"，历史链完整 | 版本链 |
| **币种与单位混杂**（千元/百万元/不同币种） | 单位列 + 抽取归一；跨币种对比属派生计算，用采集时点汇率口径标注，**不静默换算** | 约定列 |
| **衍生指标**（毛利率/ROE/资产负债率） | 默认**查询时从基础行现算**，不落库——落库产生"衍生与基础脱节"的双权威；高频使用的才物化为派生行，带 `derived_from` 溯源（由哪几行算的） | 查询层约定 |

### 4.4 难点与务实策略

几百页 PDF、跨页合并单元格表格是最吃劲场景，属于"**有损耗但可发现**"设计：解析错了 → 恒等式不平会报 + 人审对照快照能看出 + 引句回验拒收锚不中的行。三道闸兜底，不追求解析率 100%，追求错的能被抓住。

## 5. 跨行恒等式校验（通用质量机制）

财报有勾稽关系（资产=负债+权益；营业利润=收入−成本−费用…），采完自动跑，不平打 `needs_review`——比引句回验更深一层的**数据自洽**校验。做成通用机制：

```json
{ "checks": [
  { "expr": "资产总计 = 负债合计 + 所有者权益合计", "tolerance": 0.005 },
  { "expr": "本年总人口 = prev(总人口) + 出生人口 - 死亡人口", "tolerance": 0.005 }
] }
```

- 表达式按 `(schema_id, period, dims 分组)` 求值，metric 名即操作数；tolerance 为相对容差（数值系统天然有舍入）。
- **v1 范围**：同期同维恒等式（财报勾稽为主）；带 `prev()` 的跨期规则（人口平衡方程）列为 v1.5 扩展。
- 不平不阻断入库，整数据集 `needs_review`，审阅界面标注不平的恒等式与差额。

## 6. 分层存储总图

| 层 | 载体 | 职责 | 权威性 |
|----|------|------|--------|
| 全量层 | `row_json` | 完整数据字段，任意形状兜底 | **唯一权威** |
| 可计算层 | 约定列五列 | 精确查询/聚合/统计 | 投影（归一化器派生，可互校） |
| 人读层 | kb 投影文档（**表说明页**：口径/单位约定/来源构成/头部样例行/关键聚合值） | 语义检索、口径解释 | 投影（幂等重建） |
| 审阅层 | 报表视图（UI）+ kb 报表文档 | 人审对照、阅读 | 投影 |
| 保真层 | 快照文件 | 原文存档、引句回验、反查 | 原始凭证 |
| 交付层 | 文件导出 CSV/JSON/Markdown | 下游分析工具 | 投影 |

**双写一致性收敛**：不存在同步协议问题——行表是唯一权威，其余各层全是**幂等生成的投影**，坏了从行表重建。主文档 §9 的开放问题就此关闭。

**大表纪律**：kb 投影文档封顶渲染（头部 N 行 + 聚合摘要），一万行的清单绝不整表切块进向量库污染检索；全量走查表工具与导出。

---

## 7. 行层按需启用

纯文字资料的项目（无 data 形态 IR）不写 `ic_rows`、不建数据集——行存储是数据密集型搜集的**配置项**，由蓝图是否包含 measure 约定的 schema 决定。没有数据形态需求的搜集，行层是空转负担。

## 8. 通用性验证与能力边界

### 8.1 判断标准与压力测试

**代码只认"形状"（数值/清单/文档/观点），不认"领域"（人口/金融/体育）。换主题 = 写一份新蓝图（JSON），零代码变更；换"形状"才动代码。** 用与示例主题无关的主题验证：

| 随机主题 | 蓝图里变什么 | 路径与落层 |
|---|---|---|
| 全球主要央行近 5 年利率决议 | IR=逐次决议；convention（value=利率、period=决议日、dims=央行） | 定量+事件 → 约定列可算，timeline 产出 |
| 某作家全部作品及影视改编 | IR=作品清单；自定义 schema（作品名/年份/出版社/是否改编） | 实体清单，非定量 → 不启用约定列，纯 row_json |
| 锂电池三技术路线性能成本对比 | IR=各路线参数；整理规格=comparison-matrix | 定性+定量混合 → 矩阵产出，数值进约定列 |
| 咖啡豆产地风味与专业评分 | IR=产地+风味+评分；评分映射 measure，风味走 fact | 主观+数值混合 → 评分可统计，风味卡可查 |
| 某城市历年地震记录 | IR=逐次记录（时间/震级/位置/深度） | 全映射 measure（value=震级）→ 纯数据路径 |
| 某公司近 5 年财报 | IR=三大报表逐科目；宽转长 + checks 勾稽 | §4 全流程 |

### 8.2 能力边界三档

- **完整满足**：能以网页/文档/文件形态公开获取、能被文本表达的资料与数据。语言/时间窗/信源等级蓝图均有槽位。
- **部分满足（已知缺口，需要时扩展渠道类型）**：①API/数据库型数据源（世界银行 API 等，渠道枚举暂无 api 类型——加渠道是代码变更，"新形状"）；②图片/图表内数据（需 OCR，明确不做，手动录入）；③JS 渲染动态页（抓不到正文，转手动导入清单）；④PDF 复杂表格（有损耗，三道闸兜底，§4.4）。
- **明确不管**：绕反爬、内部系统直连、实时流数据。这是搜集归档模块，不是数据管道。

## 10. 明确不做

1. 不做运行时动态建表/每数据集物理表。
2. 不做百万行级 OLAP 优化——资料库不是数仓，超规模走导出。
3. 不做图片/图表 OCR 取数。
4. 不静默换算币种/单位——换算属派生计算，必须带口径标注。
5. 不把衍生指标默认落库（查询时现算；物化例外带 `derived_from`）。
6. 不做投影与行表的双向同步协议——投影一律幂等重建。
