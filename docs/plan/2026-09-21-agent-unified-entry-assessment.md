# Agent 对话「统一业务入口」达标评估与优化方案

- 日期：2026-09-21
- 目标命题：**系统提供的所有功能，都能作为一种能力让 agent 调用——一个入口，执行任意业务功能**
- 评估对象：Agent 对话（/agent-console，宿主 system-chat-agent）；依据=本机隔离环境 8 轮界面实测 + 代码盘点（工具白名单/内置工作流库/节点库/平台服务）
- 性质：纯评估，未改任何代码

---

## 1. 结论（先说答案）

**当前达标度：内容生成类业务已闭环（≈达标）；媒体生成类部分达标（单次可、项目型不可）；项目域深度操作与系统管理类未达标。**

按「任意业务功能」的口径打分：**约 55～60 分**。能做的部分已经验证是真实闭环（不是演示）；缺的部分有明确的堵点清单和可落地的修法（见 §4）。

| 能力域 | 入口可达路径 | 状态 |
|---|---|---|
| 长文/文案生成 | 内置「长文写作」工作流 + 技能包（12 个内置技能） | ✅ 已闭环实测（1121 字成文入资产库） |
| 报告/调研 | 内置「主题深度研究/行业深度调研/吃瓜事件分析/每日早报」+ web_search/wf_web_extract 直连 + deep-analysis 技能 | ✅ 已闭环实测（web_search 失败自主换路） |
| 短视频（单条） | 内置「短视频脚本生成视频」V1/V2/V3 + short-video-script 技能 | ⚠️ 路径通（缺音色/Provider 参数枚举，实测中 agent 正确转人工确认） |
| 定时自动化 | 内置「每日热点早报」可跑；**定时触发器配置无 agent 通道** | ⚠️ 半通 |
| 图像/语音/翻译（一次性） | 仅有工作流节点承载——**无内置一次性工作流、无直连工具** | ❌ 通道缺失 |
| 知识库 | kb 节点 + 2 个内置入库工作流；**聊天宿主无 kb 直连工具**（任务树里反而有 wf_kb_retrieve） | ❌ 通道缺失 |
| 长文项目深度操作 | 研讨室宿主 lw_*（查圣经/写正文/局部修正）**不对聊天宿主开放**；入口只能生成"游离长文"，不能"在我的项目里写第3章/改设定" | ❌ 未打通 |
| 短剧项目深度操作 | ep_* 制作工具**仅项目宿主**；多集管理/资产复用/在途渲染进度 | ❌ 未打通 |
| 人设工坊/领域共学空间/应用中心 | 纯 UI，无工作流节点、无技能、无工具 | ❌ 未打通 |
| 日记 | 仅 save-diary 工作流节点（一次性写日记也要现写流程） | ❌ 通道缺失 |
| 邮件发送 | 平台 email.service 已存在，无 agent 通道 | ❌ 通道缺失 |
| 系统配置（Provider/密钥/信息源/数据路径等） | 无通道 | ⛔ 建议保持人工（明确边界即可） |

## 2. 已验证达标的部分（不虚报）

1. **能力感知**：13 张模块能力卡随系统提示注入 + discover_capabilities 的 modules 段——8 轮实测 agent 全部先查目录再动手，引用与 DB 逐条吻合、零幻觉。
2. **执行优先纪律**：写小说直接命中内置工作流并跑完；web_search 挂了自主换网页抓取；无任何「请去某某页面」式推诿（修复 f2d4121a 之后）。
3. **参数智能（部分）**：model 类参数自动跟随当前对话模型（形状校正）；业务参数缺失时一次性问清、不编造。
4. **失败诚实**：搜索未配置、目录无命中、运行超时都如实转述并给替代路径；截断输出明确标注「结尾是我补的」。
5. **可追溯**：产出入资产库（source_type=workflow + run 引用）、会话右栏有运行引用卡、时间线节点级可查。

## 3. 缺口分析（按堵点严重度排序）

### 3.1 一次性动作的「仪式成本」——最大堵点
系统里「单次转换类」能力（TTS、文生图、翻译、知识库问答、写日记）的承载只有**工作流节点**。agent 的唯一通道是：`create_workflow_draft` 生成草稿 → **用户手动到编辑器发布** → 再 `run_workflow`。为「把这段话读成语音」走一遍发布仪式，统一入口就不成立。根因：平台服务层（voice/image/translation/kb/diary service 都存在）没有被包装成 agent 直连工具。

### 3.2 结果回读通道缺失
工具回执对节点输出有 400 字摘要上限，工作流「合并成文」节点的全文 agent 拿不到——实测中 agent 只能引用截断文并自己补结尾（它诚实标注了，但这是可信度损伤）。资产库里有全文，但聊天白名单没有资产读取工具。**大产物（长文/报告/视频路径）没有一条回到对话的完整通道。**

### 3.3 项目域能力完全隔离（架构性）
lw_*/ep_* 工具靠 runtimeContext 注入 projectId，只在对应宿主可用。用户在入口说「在我的小说项目里写第3章」，agent 做不到。这层隔离是**有意设计**（写操作带人确认纪律，防止绕过设计包确认），所以解法不是简单放通，而是「只读桥接 + 写操作工作流化」（见 §4-P2）。

### 3.4 系统资源枚举缺失
视频工作流的 voiceId/videoProvider/imageProvider 等参数，agent 无工具枚举可选值（音色清单、Provider×模型清单、知识库清单、模板清单）。实测中它只能反问用户——用户往往也答不上「Provider 配置 ID」这种词。discover 的 select-dynamic 数据源在 UI 表单里能加载，对话里没有等价物。

### 3.5 对话内审批与跨轮任务跟随
- 工作流走到 human-review / form-collect 时返回 waiting_review，用户被踢去工作流页处理——闭环断在对话外。
- 长任务（分钟级）超时返回 runId 后，用户下一轮问「怎么样了」，宿主没有把在途 refs 接进上下文的机制（refs 已落 metadata，缺的是回注）。
- 定时触发器（trigger scheduler 服务已存在）无 agent 通道，「每天8点」的最后一公里靠手工。

### 3.6 工程细节（小但会咬人）
- 目录封顶 20 < 内置工作流 24（截断注记已兜底，agent 需多查一次）。
- run_workflow 每轮频控 2 次 + 等待超时 180s：多业务复合指令或长工作流会在一轮内被预算截断。
- 能力卡静态表：包启停不联动、新增模块要记得改卡（演进项已在设计文档登记）。
- 提示词注入目前只覆盖聊天宿主；Web 端若启用同宿主无分叉（已对齐），但短剧/研讨室等领域宿主未注入全域能力图（有意聚焦，可选项）。

## 4. 优化方案（分四批，含验收口径）

### P0 堵点清除（做完「大部分业务一句话可达」即成立）
1. **一次性生成直连工具集**（新增 5 个只读/低危工具，走平台服务不走工作流）：
   `tts_generate(text, voiceId?)` / `image_generate(prompt, size?)` / `translate_text(text, targetLang)` / `kb_query(kbId, question)` / `diary_append(title, content)`
   频控+按次计费标注沿用现有 write-caps 机制。验收：「把这段话转成语音/画一张…/翻译成英文/在知识库X里问…/记到日记」各一条指令、零仪式完成。
2. **结果回读通道**：`get_run_output(runId, field?)` 返回终节点全量输出；`asset_read(assetId)` 读文本资产全文。验收：写小说后 agent 汇报的正文 = 资产库全文，无「我补的结尾」。
3. **系统资源枚举**：`list_resources(kind)`，kind ∈ voice/provider/knowledge-base/data-source/template/asset，返回 id+名称+关键属性。验收：视频指令中 agent 自行列音色选项让用户选，而不是问「Provider 配置 ID」。

### P1 体验闭环（入口不把用户踢出对话）
4. **对话内审批卡**：human-review/form-collect 的 waiting 状态渲染成聊天选择卡（复用 turnRefs 卡片机制），审批回写工作流。验收：「跑一个带人工审核的流程」全程不出对话。
5. **跨轮任务跟随**：sendMessage 时把在途 workflow_runs/task trees 的状态摘要注入上下文（refs 已有），「怎么样了」直接可答。
6. **触发器能力化**：`create_workflow_trigger(definitionId, cron)`（write 危险级+确认卡），接现有 scheduler。验收：「每天早8点抓新闻生成早报」一句话含定时全部落地。
7. **预算分级**：长工作流改「异步启动+完成通知」，run_workflow 频控按时长分级，避免一轮多业务被 2 次上限截断。

### P2 能力版图扩展（项目域与注册制）
8. **项目域只读桥接**：聊天宿主经 catalogPacks 开放只读子集（lw_query_bible/outline/chapter、ep 项目/剧集状态），宿主间工具授权机制 + projectId 由用户指名（`list_projects(kind)` 配套）。验收：「我那个小说项目写到哪了」入口可答。
9. **项目域写操作工作流化**：把「在项目X写第3章」「给项目补设定」包装成带审批节点的项目工作流（chapter-writing/volume-design 已是节点，缺的是「面向已有项目的参数化外壳」）。人确认纪律不丢，入口可达。验收：入口发起、研讨室/写作台可见同一产物。
10. **能力注册制下沉**（此前已登记）：pack manifest 增 `contributions.agentCapability`，卡片随包激活/停用自动进出目录，聊天宿主摘要按注册表渲染——新增模块零遗漏。

### P3 边界与非功能
11. **「不入口化」白名单声明**：系统配置、密钥、删库、包启停等明确写进能力图边界（现在是无通道状态，缺一句「这是有意的」）。
12. **回归固化**：把本次 8 轮实测用例固化成自动化回归（隔离实例 + CDP 驱动脚本已在 /tmp/bot-e2e 可整理入库），每次改卡/改提示词跑一遍。
13. 目录封顶参数化；提示词体积监控（当前约 2KB，健康）。

## 5. 优先级建议

P0 三项是「统一入口」成立与否的分水岭（一次性动作 + 结果回读 + 资源枚举），工作量可控（全部是包装既有平台服务，无新引擎能力）；P1 是体验分；P2 决定「任意」二字的含金量（项目域是系统最重的两块资产）；P3 收尾。若只做一件事，先做 P0-1——它直接决定用户对入口的体感是「执行器」还是「指路牌」。

## 6. 评审修订：跨模块影响复查（2026-09-21 第二遍）

复查重点：优化不得影响其他业务模块。核对的事实：① `run_workflow/discover/invoke_skill` 被**研讨室宿主同时白名单引用**（room-session.ts:315）；② workflow 节点与页面共用平台服务入口（`ImageService.generateImage` 带 transient 重试+任务轮询，`VoiceService.generateSpeech` 落历史并广播 `voice:tts-completed`）；③ 生成类 Provider 与在途短剧生产**共享配额容量**（实测期间有剧集渲染在跑）。据此对原方案做 4 处修订与一组红线。

### 4 处修订

| # | 原方案 | 风险 | 修订后约束 |
|---|---|---|---|
| R1 | P0-1 直连生成工具 | 付费生成通道与在途生产**共享 Provider 配额**；若绕过节点所用的队列/重试路径会产生平行执行路径 + 限流竞争，伤及短剧/语音/图像等在途业务 | **单一服务入口红线**：工具必须调用与 workflow 节点/页面完全相同的 service 方法（继承队列/重试/历史落库/事件广播，如 `voice:tts-completed` 驱动语音页历史），禁止平行实现；每轮频控 + 同参数去重（复用 `budget.maxCalls.overrides`）；生成文件落同一存储（语音历史/资产中心可见） |
| R2 | P2-8 项目域桥接 | `lw_*/ep_*` 工具定义硬依赖 runtimeContext.projectId（lwCtxFrom），直接改动会动摇研讨室/短剧宿主 | **禁止修改共享工具定义**：另起新 packId 注册「带 projectId 入参的只读变体」，内部包装同一 service 调用；写操作一律走 P2-9 工作流化，不做直通工具 |
| R3 | P1-6 触发器 | 触发器=周期性自动执行=周期性付费+副作用，是对其他模块影响面最大的提案 | 只挂已发布工作流；强制对话内确认卡；复用既有 trigger service（UI 列表可见可删、同一审计面）；UI 列表打「来自 Agent 会话」来源标记 |
| R4 | P1-4 审批卡 | 若前端另写审批路径，会绕过 review 记录审计与 allowFields/修改限制语义 | 审批必须走与工作流页**同一个 review service**（审计+字段限制+幂等都在 service 层保证，实现前核验并发 CAS；若无则在 service 补，不在前端补），前端只做渲染 |

### 核对过的安全项（为什么不影响其他模块）

- **run_workflow 自动填充对研讨室宿主无行为变化**：room runtimeContext 无 turnModel → 静默跳过（已实测研讨室全流程正常）。但据此立规矩：system-agent-tools 是跨宿主共享面，任何修改必须回归**两个宿主**（聊天 + 研讨室）。
- P0-2 回读：只读 + 沿用 getRunDetail 既有用户属主校验；maxChars/offset 防上下文爆炸。
- P0-3 list_resources：只返回 id/名称/模型清单，**绝不返回密钥**；音色/知识库/资产按当前用户域过滤，与各页面所见一致。
- P1-7 预算分级：默认行为不变、仅配置化——已验证的早报/长文路径不受影响。
- P2-9 项目写工作流：chapter-writing 节点自带设计卡/自检/一致性门禁，`chapter-writing:projectId:outlineId` 互斥锁照常生效；chat 外壳默认禁 overwrite（重写必须用户显式说）。
- P2-10 manifest 下沉：manifest_hash 变化走 materializeSnapshot 既有路径（只更新清单内容，不翻启停开关）——已核实，安全。
- 提示词/工具 schema 增量有界（+1~2KB），registry 管线有截断兜底。

### 新增红线（实现期全程有效）

1. **只增不改**：不修改任何既有共享工具/节点/服务的行为签名；扩展一律加可选字段或新 packId。
2. **单一服务入口**：新能力只包装既有 service（继承队列/重试/历史/事件），禁止平行实现。
3. **用户域强制**：所有新读写工具过 `getCurrentUserId`，与对应页面所见一致。
4. **付费动作三层防护**：频控 + 参数去重 + 计费标注（生成类工具描述里必须写明按次计费）。
5. **回归前置**：四宿主冒烟（聊天 agent / 研讨室 / 短剧制作助理 / 任务树）通过才合入；P3-12 回归集把四条固化。
