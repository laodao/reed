# 剧集制作模块系统提示词优化方案（v2）

> **版本**：2.0（v1 已回滚：commit c6351e04）
> **最后更新**：2026-06-28
> **状态**：待评审
>
> v1 失败原因：直接套用英文模型最佳实践，未经任何效果验证，存在"改了反而更差"的风险。
> 本版本将优化项严格区分为**确定性 Bug 修复**和**待验证假设**两类，前者有代码证据证明，后者必须先做 A/B 测试再上线。

---

## 1. 总体原则

### 1.1 为什么 v1 失败了

| 问题 | 说明 |
|------|------|
| 理论依据不足 | Anthropic/OpenAI 指南主要针对 GPT-4/Claude（英文），对本项目支持的国产模型（DeepSeek、通义千问等）是否适用无数据支撑 |
| 无效果验证 | 没有 A/B 对比测试，无法证明修改后质量提升 |
| 低估格式稳定性风险 | 代码中有 4-5 层 fallback 解析（`extractJsonFromResponse` → `parseJsonString` → 多层正则），说明模型格式稳定性本就是痛点；削弱 JSON 约束可能使情况更差 |
| 角色设定简化无收益数据 | "10年经验编剧"是否真的无用？对于中文创意写作模型，角色设定对输出文风有可观察的影响 |

### 1.2 本方案的核心原则

1. **分类处理**：确定性 Bug（有代码证据证明）→ 直接修复；反模式假设（效果未知）→ 必须先验证
2. **模型针对性**：不同模型对提示词的敏感度不同，优化必须考虑目标模型特性
3. **可量化评估**：每项优化必须有可度量的预期效果指标
4. **回滚就绪**：每次优化都是独立 commit，出问题可立即回滚

### 1.3 评估维度定义

| 维度 | 指标 | 测量方式 |
|------|------|----------|
| 格式稳定性 | JSON 解析成功率 | 统计 100 次调用中首次解析即成功的比例 |
| 字段完整性 | 必填字段缺失率 | 统计解析成功后必填字段被填充的比例 |
| 枚举合规率 | 枚举值匹配率 | 输出的枚举值是否属于预定义集合 |
| 内容质量 | 人工评分（1-5 分） | 由人工对输出质量打分 |
| Token 效率 | 提示词 token 数 | 计算 system+user prompt 的 token 数量 |
| 业务通过率 | 端到端成功率 | 完整业务流程执行成功的比例 |

> 这类问题有**代码级证据**证明是错的，不需要 A/B 测试，直接修复。

### 2.1 BUG-1：VLM 景别/角度/运镜枚举与分镜系统枚举不一致

#### 2.1.1 问题描述

VLM 提示词（`vlm-shot-inferrer.ts`）使用的景别枚举与分镜系统标准枚举完全不同：

| 字段 | VLM 输出 | 分镜系统标准 | 是否匹配 |
|------|----------|--------------|----------|
| shotType | `big_close_up / close_up / medium / long / wide` | `extreme_close / close / medium / long / extreme_long / ...` | ❌ 完全不同 |
| cameraAngle | `overhead` | `birds_eye` | ❌ 不同名称 |
| cameraMovement | `push / pull / pan / track` | `dolly_in / dolly_out / pan_left / truck_right` | ❌ 完全不同 |

#### 2.1.2 代码证据

- `storyboard.ts` 中的 `ShotType` 类型有 8 个值（`extreme_long, long, full, medium, medium_close, close, extreme_close, detail`）
- VLM 提示词输出的是 5 个简化值（`big_close_up, close_up, medium, long, wide`）
- 代码里没有映射层，VLM 输出直接传给分镜系统，导致类型不匹配

#### 2.1.3 影响

VLM 推断结果无法被分镜系统直接使用，用户看到的景别/角度/运镜值不符合分镜系统枚举定义，可能导致下游生成图片/视频时引用错误的枚举值。

#### 2.1.4 修复方案（已实施，保留）

1. 在 `shared/types/episode-production/narrative.types.ts` 新增 `VLM_SHOT_TYPE_MAP` 映射表
2. 在 `vlm-shot-inferrer.ts` 中增加 `VLM_MOVEMENT_MAP` 和 `VLM_ANGLE_MAP`
3. VLM 输出通过映射表转换为标准枚举后再返回

#### 2.1.5 预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| VLM 输出枚举合规率 | 0%（VLM 枚举不在分镜系统枚举内） | 100%（通过映射转换） |
| 下游错误率 | 可能产生无效枚举值 | 消除该类错误 |

#### 2.1.6 验证方案

- ✅ 代码级验证：检查映射表覆盖 VLM 提示词中的所有枚举值
- ✅ 单元测试：对每种 VLM 枚举输入，验证输出符合分镜系统枚举
- ✅ 集成验证：端到端调用 VLM 推断流程，检查最终分镜数据中的枚举值

**状态**：✅ 已实施（commit `3e360a6d`，保留未回滚）

### 2.2 BUG-2：标记系统不一致导致解析复杂度高

#### 2.2.1 问题描述

全模块使用 6 种不同的输出标记格式，解析代码需要多重 fallback：

| 标记格式 | 使用位置 | fallback 层数 |
|----------|----------|--------------|
| `【场景数据开始】...【场景数据结束】` | 剧本生成 | 4 层 |
| `===SCENES_JSON===...===SCENES_JSON_END===` | 梗概拆分 | 3 层 |
| `===SCENE_JSON===...===SCENE_JSON_END===` | 场景润色输入 | 2 层 |
| `===POLISHED_JSON===...===POLISHED_JSON_END===` | 场景润色输出 | 2 层 |
| `===SYNOPSIS===...===SYNOPSIS_END===` | 旧格式（兼容） | 1 层 |
| `===SCRIPT===...===SCRIPT_END===` | 旧格式（兼容） | 1 层 |

#### 2.2.2 代码证据

`_helpers.ts` 中的 `extractJsonFromResponse()` 函数实现了多层 fallback：
1. 先尝试正则匹配 `===XXX===...===XXX_END===` 格式
2. 再尝试正则匹配 ``` ```json ``` ``` 代码块
3. 再尝试 `JSON.parse()` 全文
4. 再尝试 `parseJsonString()` 提取第一个 JSON 对象/数组
5. 最后尝试匹配中文标记 `【XXX开始】...【XXX结束】`

每层 fallback 都是为了兼容不同模型/不同功能的输出格式，维护复杂度高。

#### 2.2.3 影响

- 新增功能时需要添加新的标记格式，每增加一种格式，解析复杂度线性增长
- 不同模型有时不遵守指定标记，fallback 层数越多越难定位问题
- 旧格式（`===SYNOPSIS===`、`===SCRIPT===`）仍在代码中保留，增加认知负担

#### 2.2.4 修复方案

**目标**：统一为 2 种标记格式（中文标记 + 英文标记），逐步淘汰其他格式。

**阶段一（低风险）**：
1. 新增功能统一使用 `===XXX_BEGIN===...===XXX_END===` 格式（英文标记便于正则匹配）
2. 在 `_helpers.ts` 中统一所有 fallback 到一个函数
3. 保留旧格式兼容，不强制迁移

**阶段二（中风险）**：
1. 在现有功能的提示词中逐步迁移到统一标记
2. 每迁移一种格式，跑一次端到端测试验证解析成功率
3. 旧格式兼容代码保留 3 个月后移除

#### 2.2.5 预期效果

| 指标 | 修复前 | 修复后（阶段二完成） |
|------|--------|---------------------|
| 标记格式种类 | 6 种 | 1 种（英文标记） |
| 解析 fallback 层数 | 最多 5 层 | 2 层（主格式 + 代码块） |
| 新增格式维护成本 | 每次新增需改多处 | 无 |

#### 2.2.6 验证方案

- 每次迁移一种标记格式，用同一模型、同一输入跑 10 次，对比解析成功率
- 如果迁移后解析成功率下降超过 5%，回滚该迁移
- 旧格式兼容代码移除前，统计线上数据确认无流量

### 2.3 BUG-3：剧本→分镜数据流断裂（binding ID 丢失）

#### 2.3.1 问题描述

剧本生成（`script-generator.ts`）输出包含 `locationBindingId / characterBindingId / itemBindingId` 的结构化数据。

分镜生成（`storyboard-generator.ts`）的提示词中只看到 `characterName`，无法关联到具体资产 binding ID。

#### 2.3.2 代码证据

`storyboard-generator.ts` 的 `buildSceneDescription()` 函数：
```typescript
// 只传入了 characterName，没有传入 characterBindingId
const characterLines = scene.characters.map(c =>
  `- ${c.characterName}：${c.position || '未定位'}，${c.action || '无动作'}`
)
```

分镜生成时 AI 只知道"张三在说话"，不知道"张三"对应的 `characterBindingId` 是什么。

#### 2.3.3 影响

- 分镜生成无法正确引用资产，需要在后续绑定步骤补充
- 如果 AI 填充分镜时也需要引用 binding ID，同样面临信息缺失

#### 2.3.4 修复方案

在 `buildSceneDescription()` 和分镜生成的 scene context 中，把 binding ID 一并传入：
```typescript
const characterLines = scene.characters.map(c => {
  const binding = c.characterBindingId ? `（bindingId: ${c.characterBindingId}）` : ''
  return `- ${c.characterName}${binding}：${c.position || '未定位'}，${c.action || '无动作'}`
})
```

#### 2.3.5 预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 分镜输出中 binding ID 引用率 | 0%（AI 无法引用它看不到的 ID） | > 80%（AI 可以直接引用） |
| 后续手动绑定的工作量 | 需要额外绑定步骤 | 减少或消除 |

#### 2.3.6 验证方案

- 用同一场景输入，对比修复前后分镜输出中 `characterBindingId` 字段的填充率
- 检查下游资产绑定流程是否仍能正常工作（回归测试）

### 2.4 BUG-4：资产字段类型冲突（race / gender）

#### 2.4.1 问题描述

| 字段 | 资产设定反推（5.1） | 自由文本提取（6.1） |
|------|---------------------|---------------------|
| race | 枚举（`east_asian / south_asian / ...`，7 种） | 自由文本（如"东亚"） |
| gender | 枚举（`男 / 女 / 其他`） | 自由文本（如"男性角色"） |

同一字段在两个不同功能中定义不同，数据在功能间传递时需要转换。

#### 2.4.2 代码证据

`setting-enrichment-prompt.ts` 中：
```typescript
race: '"east_asian" | "south_asian" | "west_asian" | "middle_eastern" | "african" | "european" | "latin_american"'
```

`asset-setting-enrichment.service.ts` 中（自由文本提取）：
```typescript
race: '种族/民族（如：东亚、欧洲、非裔等）'
```

#### 2.4.3 影响

- 两个功能产生的资产数据格式不兼容
- 合并数据时需要额外转换逻辑
- 用户在不同界面看到同一字段的不同表示

#### 2.4.4 修复方案

统一为枚举类型：
1. 在 `shared/types/episode-production/domain.types.ts` 定义 `Race` 和 `Gender` 枚举类型
2. 两个功能的提示词都引用同一套枚举
3. 自由文本提取时，在提示词中给出枚举选项，让 AI 选择最匹配的

#### 2.4.5 预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 字段格式一致性 | 两种格式混用 | 统一为枚举 |
| 跨功能数据传递 | 需要转换逻辑 | 直接传递 |

#### 2.4.6 验证方案

- 分别用两种功能提取同一角色的 race/gender，检查输出是否属于同一枚举集合
- 检查现有数据中是否有非枚举值（兼容处理）

### 2.5 BUG-5：分镜需求分析结果未传递给逐个分镜生成

#### 2.5.1 问题描述

分镜流程：
1. **分镜需求分析**（3.3）：分析场景，输出建议的 shotTypes（如 `["long", "medium", "close"]`）、节奏规划
2. **逐个分镜生成**（3.2）：逐个生成分镜，`{contextInfo}` 只包含前一个分镜的参数

分析结果（整体规划）没有传递给逐个生成，导致每个分镜只看到局部信息，无法参考整体规划。

#### 2.5.2 代码证据

`storyboard-generator.ts` 中：
```typescript
// 3.3 输出
analysisResult = {
  shotTypes: ["long", "medium", "close"],
  pacing: "渐快",
  ...
}

// 3.2 的 contextInfo 只包含前一个分镜
const contextInfo = previousShot
  ? `前一个镜头：shotType=${previousShot.shotType}...`
  : '这是第一个镜头'
// analysisResult 的 shotTypes 没有传进来
```

#### 2.5.3 修复方案

在 `contextInfo` 中增加"整体分镜规划"部分：
```typescript
const contextInfo = [
  analysisResult ? `整体规划：建议使用景别 ${analysisResult.shotTypes.join('/')}，节奏 ${analysisResult.pacing}` : '',
  previousShot ? `前一个镜头：...` : '这是第一个镜头'
].filter(Boolean).join('\n')
```

#### 2.5.4 预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 景别建议采纳率 | 无法测量（信息根本没传入） | > 60%（AI 可以参考） |
| 分镜连贯性 | 每个分镜独立决策 | 参考整体规划，连贯性提升 |

#### 2.5.5 验证方案

- 用同一场景对比修复前后，检查分镜序列的景别分布是否符合分析建议
- 人工评估分镜连贯性是否有改善

## 3. 第二类：待验证假设

> 这类优化基于提示词工程最佳实践，但**最佳实践主要来自英文模型研究**。
> 在中文模型上效果未知，必须先做 A/B 测试，数据证明有效后再上线。

### 3.1 HYP-1：过度强调 JSON 输出是否真的有效？

#### 3.1.1 当前状态

剧本生成提示词有重度 JSON 强调：
```
## ⚠️⚠️⚠️ 最重要：你必须输出结构化 JSON 场景数据！
**这是你最重要的任务！如果不输出 JSON 场景数据，整个任务就是失败的！**
**这部分绝对不能跳过！如果跳过，整个生成将失败！**
```

加上 system prompt 中再次强调：
```
必须输出【场景数据开始】【场景数据结束】标记的 JSON 场景数据！
```

#### 3.1.2 假设

**H₀（零假设）**：重度 JSON 强调与轻度 JSON 强调的解析成功率无显著差异。
**H₁（备择假设）**：轻度 JSON 强调（只在 user prompt 格式说明处强调一次）的解析成功率不低于重度强调。

#### 3.1.3 理论依据

- **Anthropic 指南**：重复强调同一约束不会提高遵从度
- ** BUT**：此结论基于 Claude 模型；DeepSeek 等模型对提示词强调的敏感度可能不同
- **代码证据**：即使有重度强调，代码仍有 4 层 fallback，说明强调并不保证 100% 遵从
- **反面论据**：如果重度强调是有效的，那么 fallback 层数应该更少；现有 fallback 层数说明可能效果有限

#### 3.1.4 验证方案

**A/B 测试设计**：

| 项目 | 内容 |
|------|------|
| 目标模型 | DeepSeek-V3、通义千问-Max（实际使用的主流模型） |
| 对照组 A | 当前重度强调版本 |
| 实验组 B | 轻度强调：只保留 user prompt 中的格式说明，去掉 ⚠️ 警告和 system prompt 重复强调 |
| 测试样本 | 5 个不同复杂度的小说段落（500-2000 字） |
| 每组运行次数 | 每样本 × 每版本 × 10 次 = 100 次/组 |
| 主要指标 | 首次解析成功率（`extractJsonFromResponse` 第一层即成功） |
| 次要指标 | 必填字段完整率、枚举合规率、输出 token 数 |
| 成功标准 | 实验组首次解析成功率不低于对照组 5 个百分点（α=0.05） |

**如果实验组成功率显著低于对照组**：保留重度强调，放弃此优化。
**如果实验组成功率无显著差异**：采用轻度强调，节省 token 并降低提示词复杂度。

#### 3.1.5 预期效果（若验证通过）

| 指标 | 预期变化 |
|------|----------|
| 首次解析成功率 | 无显著变化（±5%） |
| 提示词 token 数 | 减少 15-25%（警告文字占相当篇幅） |
| 维护复杂度 | 降低（单一格式说明） |

### 3.2 HYP-2：角色设定对创意写作质量是否有影响？

#### 3.2.1 当前状态

剧本生成 system prompt：
```
你是一位拥有10年以上一线影视工业经验的职业编剧。
```

场景润色 system prompt：
```
你是一位拥有 10 年以上一线影视工业经验的职业编剧，擅长把粗糙的剧本场景润色成富有画面感、情感张力和潜台词的成熟剧本。
```

#### 3.2.2 假设

**H₀**：详细角色设定（"10年经验编剧"）与简化角色设定（"影视编剧助手"）的输出质量无显著差异。
**H₁**：详细角色设定的输出在"文风专业度"维度上得分显著高于简化版本。

#### 3.2.3 理论依据

- **Anthropic/OpenAI 指南**：角色设定对分类/事实任务影响可忽略（negligible）
- **BUT**：创意写作是例外场景，角色设定可以引导文风（few-shot 的轻量替代）
- **中文模型特点**：DeepSeek/通义等中文模型对角色设定的响应可能更敏感（中文创作任务更依赖语境）
- **反面论据**：没有针对中文模型的定量研究支持

#### 3.2.4 验证方案

**A/B 测试设计**：

| 项目 | 内容 |
|------|------|
| 目标模型 | DeepSeek-V3 |
| 对照组 A | 当前详细角色设定（"10年经验编剧"） |
| 实验组 B | 简化角色设定（"影视编剧助手"） |
| 测试样本 | 3 段不同风格的小说（现代/古风/悬疑） |
| 评估方式 | 双盲人工评审（3 位评审，不知道哪个是 A 哪个是 B） |
| 评分维度 | 文风专业度、画面感、对白自然度（1-5 分） |
| 每组运行次数 | 每样本 × 每版本 × 5 次 = 30 次/组 |
| 成功标准 | 实验组平均分不低于对照组 0.3 分（p<0.05） |

#### 3.2.5 预期效果（若简化版验证通过）

| 指标 | 预期变化 |
|------|----------|
| 输出质量评分 | 无显著变化 |
| 提示词 token 数 | 减少 20-40 字符 |
| 维护成本 | 统一角色描述，降低不一致性 |

### 3.3 HYP-3：添加 Few-shot 示例能否提升格式稳定性？

#### 3.3.1 当前状态

除剧本生成外，分镜生成、场景润色、VLM 推断等功能都没有 few-shot 示例。模型输出格式不稳定，需要多层 fallback 解析。

#### 3.3.2 假设

**H₀**：添加 1 个 few-shot 示例对格式稳定性无显著影响。
**H₁**：添加 1 个 few-shot 示例可将首次解析成功率提升 15 个百分点以上。

#### 3.3.3 理论依据

- **Brown et al. 2020（GPT-3 论文）**：Few-shot 示例（3-5 个）可显著提升格式稳定性
- **Anthropic 指南**：1 个示例即可覆盖大部分格式需求
- **OpenAI 指南**：对于复杂格式，few-shot 比详细规则更有效
- **适用范围**：此结论在多种模型上验证，包括部分中文模型

#### 3.3.4 验证方案

**A/B 测试设计（以分镜生成为例）**：

| 项目 | 内容 |
|------|------|
| 目标模型 | DeepSeek-V3、通义千问-Max |
| 对照组 A | 当前版本（无 few-shot 示例） |
| 实验组 B | 添加 1 个简短示例（见下方） |
| 测试样本 | 5 个不同场景（茶馆/街头/室内/夜景/群戏） |
| 每组运行次数 | 每样本 × 每模型 × 10 次 = 100 次/组/模型 |
| 主要指标 | 首次解析成功率 |
| 次要指标 | 输出 token 数（示例占用额外 token） |

**示例内容**（分镜生成）：
```
## 示例

输入场景：
场景 1: 茶馆 · 白天
角色：张三（坐在角落）
对白：张三："请来一壶茶"

输出：
{
  "shotNumber": 1,
  "shotType": "long",
  "cameraAngle": "eye_level",
  "cameraMovement": "static",
  "frameDescription": "【场景】茶馆内景，木质桌椅，晨光从窗户洒入\n【人物】张三位于画面右下角，侧身面向柜台\n【动作】张三抬手示意店员\n【氛围】暖色调，市井氛围",
  "characters": [...],
  "dialogueIds": ["dlg_1"],
  "actionIds": ["act_1"],
  "duration": 5,
  "transition": { "type": "cut", "durationMs": 300 }
}
```

#### 3.3.5 预期效果（若验证通过）

| 指标 | 预期变化 |
|------|----------|
| 首次解析成功率 | 提升 15-30 个百分点 |
| 输出 token 数 | 增加 100-200 token（示例占用） |
| 总体 token 成本 | 可能降低（fallback 重试减少） |

### 3.4 HYP-4：否定指令改为正向表述是否提升遵从度？

#### 3.4.1 当前状态

多处使用否定指令：
```
不要添加任何额外的开场白或结束语
不要瞎编 ID
不要解释，不要 markdown 围栏
切勿编造完全脱离原文的细节
```

#### 3.4.2 假设

**H₀**：否定指令与对应的正向表述对模型行为无显著差异。
**H₁**：正向表述的指令遵从率比否定指令高 10% 以上。

#### 3.4.3 理论依据

- **Pink Elephant Problem（心理学）**：否定指令反而让被禁止的概念更突出
- **Anthropic 指南**：使用正向表述（说"要做什么"而非"不要做什么"）
- **BUT**：主要基于 GPT-4/Claude 的观察；国产模型是否同样敏感尚无数据

#### 3.4.4 验证方案

| 项目 | 内容 |
|------|------|
| 测试场景 | 场景润色（否定指令最多） |
| 对照组 A | 当前否定指令版本 |
| 实验组 B | 正向表述版本 |
| 主要指标 | "出现开场白/结束语"的发生率 |
| 每组运行次数 | 30 次/组 |

**改写示例**：
| 否定指令 | 正向表述 |
|----------|----------|
| 不要添加开场白或结束语 | 直接输出 JSON 数据 |
| 不要瞎编 ID | 只使用提供的 ID，找不到时填 null |
| 不要解释 | 只输出 JSON，不含任何说明文字 |

## 5. A/B 测试基础设施

> 在做任何 HYP 验证之前，需要先建立测试基础设施。

### 5.1 测试框架

```typescript
// tests/integration/episode-production/prompt-ab-test.ts

interface PromptABTestConfig {
  name: string
  targetModels: string[]         // 目标模型（如 ['deepseek-v3', 'qwen-max']）
  controlPrompt: string          // 对照组提示词（当前版本）
  experimentPrompt: string       // 实验组提示词
  samples: Array<{               // 测试样本
    input: string                // 输入文本
    expectedOutput?: any         // 预期输出（可选）
  }>
  runsPerSample: number          // 每样本运行次数
  metrics: {
    primary: 'parseSuccessRate' | 'fieldCompleteness' | 'enumCompliance' | 'humanScore'
    secondary?: string[]
  }
}

interface ABTestResult {
  testName: string
  model: string
  controlMetrics: MetricSummary
  experimentMetrics: MetricSummary
  statisticalSignificance: number  // p-value
  recommendation: 'adopt' | 'reject' | 'inconclusive'
}
```

### 5.2 自动化指标采集

| 指标 | 采集方式 |
|------|----------|
| 解析成功率 | `extractJsonFromResponse()` 返回值是否为 null |
| 字段完整性 | 解析后检查必填字段是否存在 |
| 枚举合规率 | 检查枚举值是否属于预定义集合 |
| Token 数 | `tiktoken` 或模型 API 返回的 `usage` 字段 |
| 人工评分 | 导出 A/B 输出到评审界面，由人工打分 |

### 5.3 统计方法

- 使用**双样本 t 检验**（连续指标，如解析成功率）
- 显著性水平 α = 0.05
- 效果量（Cohen's d）报告，避免仅依赖 p 值
- 每组最少 30 次运行（中心极限定理）

## 6. 风险控制

### 6.1 回滚策略

- 每个优化项独立 commit，出问题可精准回滚

1. 只对特定 `providerConfigId` 启用新版本
