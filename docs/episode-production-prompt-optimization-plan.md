## 1. 总体原则

### 1.1 为什么 v1 失败了

| 问题 | 说明 |
|------|------|
| 理论依据不足 | Anthropic/OpenAI 指南主要针对 GPT-4/Claude（英文），对本项目支持的国产模型（DeepSeek、通义千问等）是否适用无数据支撑 |
| 无效果验证 | 没有 A/B 对比测试，无法证明修改后质量提升 |
| 低估格式稳定性风险 | 代码中有 4-5 层 fallback 解析（`extractJsonFromResponse` → `parseJsonString` → 多层正则），说明模型格式稳定性本就是痛点；削弱 JSON 约束可能使情况更差 |
| 角色设定简化无收益数据 | "10年经验编剧"是否真的无用？对于中文创意写作模型，角色设定对输出文风有可观察的影响 |

### 1.2 本方案的核心原则

1. **分类处理**：确定性 Bug（有代码证据证明）→ 直接修复；反模式假设（效果未知）→ 必须先验证
2. **模型针对性**：不同模型对提示词的敏感度不同，优化必须考虑目标模型特性
3. **可量化评估**：每项优化必须有可度量的预期效果指标
4. **回滚就绪**：每次优化都是独立 commit，出问题可立即回滚

### 1.3 评估维度定义

| 维度 | 指标 | 测量方式 |
|------|------|----------|
| 格式稳定性 | JSON 解析成功率 | 统计 100 次调用中首次解析即成功的比例 |
| 字段完整性 | 必填字段缺失率 | 统计解析成功后必填字段被填充的比例 |
| 枚举合规率 | 枚举值匹配率 | 输出的枚举值是否属于预定义集合 |
| 内容质量 | 人工评分（1-5 分） | 由人工对输出质量打分 |
| Token 效率 | 提示词 token 数 | 计算 system+user prompt 的 token 数量 |
| 业务通过率 | 端到端成功率 | 完整业务流程执行成功的比例 |

### 2.1 BUG-1：VLM 景别/角度/运镜枚举与分镜系统枚举不一致

#### 2.1.1 问题描述

VLM 提示词（`vlm-shot-inferrer.ts`）使用的景别枚举与分镜系统标准枚举完全不同：

| 字段 | VLM 输出 | 分镜系统标准 | 是否匹配 |
|------|----------|--------------|----------|
| shotType | `big_close_up / close_up / medium / long / wide` | `extreme_close / close / medium / long / extreme_long / ...` | ❌ 完全不同 |
| cameraAngle | `overhead` | `birds_eye` | ❌ 不同名称 |
| cameraMovement | `push / pull / pan / track` | `dolly_in / dolly_out / pan_left / truck_right` | ❌ 完全不同 |

#### 2.1.2 代码证据

- `storyboard.ts` 中的 `ShotType` 类型有 8 个值（`extreme_long, long, full, medium, medium_close, close, extreme_close, detail`）
- VLM 提示词输出的是 5 个简化值（`big_close_up, close_up, medium, long, wide`）
- 代码里没有映射层，VLM 输出直接传给分镜系统，导致类型不匹配

#### 2.1.3 影响

VLM 推断结果无法被分镜系统直接使用，用户看到的景别/角度/运镜值不符合分镜系统枚举定义，可能导致下游生成图片/视频时引用错误的枚举值。

#### 2.1.4 修复方案（已实施，保留）

1. 在 `shared/types/episode-production/narrative.types.ts` 新增 `VLM_SHOT_TYPE_MAP` 映射表
2. 在 `vlm-shot-inferrer.ts` 中增加 `VLM_MOVEMENT_MAP` 和 `VLM_ANGLE_MAP`
3. VLM 输出通过映射表转换为标准枚举后再返回

#### 2.1.5 预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| VLM 输出枚举合规率 | 0%（VLM 枚举不在分镜系统枚举内） | 100%（通过映射转换） |
| 下游错误率 | 可能产生无效枚举值 | 消除该类错误 |

#### 2.1.6 验证方案

- ✅ 代码级验证：检查映射表覆盖 VLM 提示词中的所有枚举值
- ✅ 单元测试：对每种 VLM 枚举输入，验证输出符合分镜系统枚举
- ✅ 集成验证：端到端调用 VLM 推断流程，检查最终分镜数据中的枚举值

**状态**：✅ 已实施（commit `3e360a6d`，保留未回滚）

### 2.2 BUG-2：标记系统不一致导致解析复杂度高（技术债务）

> **注意**：这是一个**技术债务**，不是"确定性 Bug"。目前没有数据证明它导致了解析失败率增加，但 8 层 fallback 确实增加了代码维护复杂度。

#### 2.2.1 问题描述

全模块使用 6 种不同的输出标记格式，解析代码需要多重 fallback：

| 标记格式 | 使用位置 | fallback 层数 |
|----------|----------|--------------|
| `【场景数据开始】...【场景数据结束】` | 剧本生成 | 4 层 |
| `===SCENES_JSON===...===SCENES_JSON_END===` | 梗概拆分 | 3 层 |
| `===SCENE_JSON===...===SCENE_JSON_END===` | 场景润色输入 | 2 层 |
| `===POLISHED_JSON===...===POLISHED_JSON_END===` | 场景润色输出 | 2 层 |
| `===SYNOPSIS===...===SYNOPSIS_END===` | 旧格式（兼容） | 1 层 |
| `===SCRIPT===...===SCRIPT_END===` | 旧格式（兼容） | 1 层 |

#### 2.2.2 代码证据

标记解析散落在各模块中，没有统一入口：

- `script-generator.ts` 的 `extractFullScriptFromResponse()` 方法（第 281-355 行）独立处理 6 种标记：
  1. `【梗概开始】...【梗概结束】`（新格式）
  2. `===SYNOPSIS===...===SYNOPSIS_END===`（旧格式）
  3. `【剧本正文开始】...【剧本正文结束】`（新格式）
  4. `===SCRIPT===...===SCRIPT_END===`（旧格式）
  5. `【场景数据开始】...【场景数据结束】`（新格式）
  6. `===SCENES_JSON===...===SCENES_JSON_END===`（旧格式）
  7. ` ```json ``` ` 代码块格式（DeepSeek 常用）
  8. 直接查找 `"scenes": [` 兜底

- `scene-polisher.ts` 独立处理 `===SCENE_JSON===` 和 `===POLISHED_JSON===` 两种标记

- `_helpers.ts` 的 `extractJsonFromResponse()` 只处理 ` ```json ` 代码块和裸 JSON，不处理上述自定义标记

每增加一种新标记格式，需要在对应模块中添加新的正则匹配逻辑，维护分散。

#### 2.2.3 影响

- **维护复杂度**：8 层 fallback 增加代码理解和调试难度
- **当前是否有问题**：❓ **未知**。需要统计当前解析失败率，才能判断是否有实际影响
- **未来风险**：新增功能时需要添加新的标记格式，维护成本会持续增加

#### 2.2.4 修复方案

**目标**：统一为 2 种标记格式（中文标记 + 英文标记），逐步淘汰其他格式。

**阶段一（低风险）**：
1. 新增功能统一使用 `===XXX_BEGIN===...===XXX_END===` 格式（英文标记便于正则匹配）
2. 在 `_helpers.ts` 中统一所有 fallback 到一个函数
3. 保留旧格式兼容，不强制迁移

**阶段二（中风险）**：
1. 在现有功能的提示词中逐步迁移到统一标记
2. 每迁移一种格式，跑一次端到端测试验证解析成功率
3. 旧格式兼容代码保留 3 个月后移除

**前置条件**：
- 统计当前解析失败率，确认是否有实际影响
- 如果没有实际影响，可以延后修复

#### 2.2.5 预期效果

| 指标 | 修复前 | 修复后（阶段二完成） |
|------|--------|---------------------|
| 标记格式种类 | 6 种 | 1 种（英文标记） |
| 解析 fallback 层数 | 最多 5 层 | 2 层（主格式 + 代码块） |
| 新增格式维护成本 | 每次新增需改多处 | 无 |

#### 2.2.6 验证方案

- 每次迁移一种标记格式，用同一模型、同一输入跑 10 次，对比解析成功率
- 如果迁移后解析成功率下降超过 5%，回滚该迁移
- 旧格式兼容代码移除前，统计线上数据确认无流量

**状态**：✅ 监控已添加（commit `af46a352`），待收集数据后决策是否统一

#### 2.2.7 前置工作：添加结构化监控日志

> **目的**：收集每种解析路径的实际命中频率，判断是否有必要做标记统一。

**现有代码已有日志**（`script-generator.ts` 第 285-598 行），但都是非结构化的 `console.log`，无法统计。

**改造方案（已实施）**：在 `extractFullScriptFromResponse` 方法中，添加了 `pathTrace` 对象：

```typescript
const pathTrace = {
  synopsisPath: 'new' | 'old' | 'json-fallback' | 'none',

  scenesPath: 'new' | 'old' | 'json-block' | 'fallback' | 'failed',
  scenesCount: number,

```

每次解析后输出一条 JSON 格式的日志：
```

```

- 在 Electron 主进程中，每次解析后 `console.log` 一条 JSON 格式的统计信息

- 如果 `scenesJsonBlock` 命中率 > 20% → 说明 DeepSeek 等模型确实偏好代码块格式，应该把代码块格式作为主要格式之一
- 如果 `scenesFailed` > 5% → 说明确实有解析失败问题，需要优先修复标记系统

**状态**：✅ 已完成（commit `af46a352`），待收集数据

### 2.3 BUG-3：资产字段类型冲突（race 字段双写不一致）

#### 2.3.1 问题描述（v2.3 修正：已确认为实际 Bug）

> **v2.2 → v2.3 更新**：之前认为是"设计评估"，但深入读代码后发现两个功能**写入同一个数据库字段** `CharacterBindingEntity.race`，造成实际数据不一致。

两个不同功能的 race 字段定义不同，且**写入同一个字段**：

| 功能 | 代码位置 | 输出格式 | 写入字段 |
|------|----------|----------|----------|
| 设定反推（enrich） | `setting-enrichment-prompt.ts` 第 54 行 | 枚举（`"east_asian"` / `"south_asian"` / ...） | `CharacterBindingEntity.race` |
| 正向文本提取（extractFields） | `asset-setting-enrichment.service.ts` 第 239 行 | 自由文本（如 `"东亚"` / `"欧洲"`） | `CharacterBindingEntity.race`（同一字段） |

#### 2.3.2 代码证据

**写入路径 1（enrich）**：
`setting-enrichment-prompt.ts` 第 54 行，提示词要求输出枚举值：
```
race: 人种（"east_asian" / "south_asian" / "southeast_asian" / "central_asian" / "european" / "african" / "south_american" 之一）
```
`asset-setting-enrichment.service.ts` 第 469 行，写入数据库：
```typescript
if (!b.race && typeof f.race === 'string' && f.race.trim()) patch.race = f.race.trim()
// patch.race = "east_asian"  ← 枚举值
```

**写入路径 2（extractFields）**：
`asset-setting-enrichment.service.ts` 第 239 行，提示词要求输出自由文本：
```
- race: 自由文本（如"东亚" / "欧洲"；保留中文）
```
第 325 行，校验后写入（不做枚举校验）：
```typescript
if (typeof data.race === 'string' && data.race.trim()) out.race = data.race.trim()
// out.race = "东亚"  ← 自由文本
```
然后通过 `applyCharacter` 写入同一个 `CharacterBindingEntity.race` 字段。

#### 2.3.3 影响

- **同一字段两种格式**：用户先用"设定反推"得到 `"east_asian"`，再用"正向提取"可能被覆盖为 `"东亚"`，格式不一致
- **下游消费方困惑**：分镜生成、图片生成提示词使用 `character.race` 时，拿到的可能是英文枚举或中文文本，无法统一处理
- **数据迁移风险**：如果未来统一为枚举，需要清洗已有数据库中所有自由文本格式的 race 值

#### 2.3.4 修复方案

**目标**：统一为枚举格式，两个功能输出相同格式。

**方案**：修改正向提取的提示词，使用与设定反推相同的枚举值：
```typescript
// 修改 buildExtractFieldsSystemPrompt 中的 race 描述
- race: 自由文本（如"东亚" / "欧洲"；保留中文）
+ race: 人种（"east_asian" / "south_asian" / "southeast_asian" / "central_asian" / "european" / "african" / "south_american" 之一）
```
并在 `validateAndCoerceExtracted` 中增加枚举校验：
```typescript
const validRaces = ['east_asian', 'south_asian', 'southeast_asian', 'central_asian', 'european', 'african', 'south_american']
if (typeof data.race === 'string' && validRaces.includes(data.race)) {
  out.race = data.race as ExtractedFields['race']
}
```

**数据迁移**：修复后，需要清洗已有数据库中非枚举格式的 race 值：
- 检查 `CharacterBindingEntity` 中所有 race 值
- 将中文文本（如"东亚"）映射回枚举（如"east_asian"）
- 无法映射的值保留，但标记为待人工校验

#### 2.3.5 预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| race 字段格式 | 两种格式混用（枚举 + 自由文本） | 统一为枚举 |
| 跨功能数据一致性 | 可能互相覆盖 | 格式一致 |
| 下游消费方处理 | 需要判断格式 | 直接使用 |

#### 2.3.6 验证方案

- 用同一角色分别调用两个功能，检查 race 字段是否为相同枚举值
- 检查现有数据库中 race 字段的实际值分布
- 数据迁移后，验证所有 race 值都符合枚举定义

### 2.4 BUG-4：分镜需求分析结果未传递给逐个分镜生成

#### 2.4.1 问题描述

分镜流程：
1. **分镜需求分析**（3.3）：分析场景，输出建议的 shotTypes（如 `["long", "medium", "close"]`）、节奏规划
2. **逐个分镜生成**（3.2）：逐个生成分镜，`{contextInfo}` 只包含前一个分镜的参数

分析结果（整体规划）没有传递给逐个生成，导致每个分镜只看到局部信息，无法参考整体规划。

#### 2.4.2 代码证据

`storyboard-generator.ts` 中：
```typescript
// 3.3 输出
analysisResult = {
  shotTypes: ["long", "medium", "close"],
  pacing: "渐快",
  ...
}

// 3.2 的 contextInfo 只包含前一个分镜
const contextInfo = previousShot
  ? `前一个镜头：shotType=${previousShot.shotType}...`
  : '这是第一个镜头'
// analysisResult 的 shotTypes 没有传进来
```

#### 2.4.3 修复方案

在 `contextInfo` 中增加"整体分镜规划"部分：
```typescript
const contextInfo = [
  analysisResult ? `整体规划：建议使用景别 ${analysisResult.shotTypes.join('/')}，节奏 ${analysisResult.pacing}` : '',
  previousShot ? `前一个镜头：...` : '这是第一个镜头'
].filter(Boolean).join('\n')
```

#### 2.4.4 预期效果

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 景别建议信息 | 未传入逐个分镜生成（信息被浪费） | 传入逐个分镜生成（AI 可参考） |
| 分镜连贯性 | 每个分镜独立决策 | 参考整体规划，连贯性**预期**改善（需验证） |

> **注意**：预期效果中"连贯性改善"是推测，需要通过实际测试验证。AI 是否会参考传入的建议、参考程度如何，都无数据支撑。

#### 2.4.5 验证方案

- 用同一场景对比修复前后，检查分镜序列的景别分布是否符合分析建议
- 人工评估分镜连贯性是否有改善

### 3.1 HYP-1：过度强调 JSON 输出是否真的有效？

#### 3.1.1 当前状态

剧本生成提示词有重度 JSON 强调：
```
## ⚠️⚠️⚠️ 最重要：你必须输出结构化 JSON 场景数据！
**这是你最重要的任务！如果不输出 JSON 场景数据，整个任务就是失败的！**
**这部分绝对不能跳过！如果跳过，整个生成将失败！**
```

加上 system prompt 中再次强调：
```
必须输出【场景数据开始】【场景数据结束】标记的 JSON 场景数据！
```

#### 3.1.2 假设

**H₀（零假设）**：重度 JSON 强调与轻度 JSON 强调的解析成功率无显著差异。
**H₁（备择假设）**：轻度 JSON 强调（只在 user prompt 格式说明处强调一次）的解析成功率不低于重度强调。

#### 3.1.3 理论依据

- **观察**：代码中有 8 层 fallback 解析逻辑，说明模型输出格式不稳定
- **推测**：重度强调（⚠️⚠️⚠️）可能不是最有效的方式，但**无法确定**
  - 有 fallback **不代表**强调无效
  - 可能强调减少了格式问题，但仍有部分问题需要 fallback
  - 也可能强调本身效果有限，fallback 才是关键
- **需要验证**：对比三组（重度强调 vs 轻度强调 vs 无强调），才能得出结论

> **注意**：v1 中"Anthropic 指南说重复强调无效"的推理是错误的。该结论基于 Claude 模型，对 DeepSeek 等国产模型不一定适用。

#### 3.1.4 验证方案

**A/B/C 测试设计**：

| 项目 | 内容 |
|------|------|
| 目标模型 | DeepSeek-V3、通义千问-Max（实际使用的主流模型） |
| 对照组 A | 当前重度强调版本（⚠️⚠️⚠️） |
| 实验组 B | 轻度强调：只保留 user prompt 中的格式说明，去掉 ⚠️ 警告和 system prompt 重复强调 |
| 实验组 C | 无强调：只保留最基本的格式说明，没有任何强调性语言 |
| 测试样本 | 5 个不同复杂度的小说段落（500-2000 字） |
| 每组运行次数 | 每样本 × 每版本 × 10 次 = 100 次/组 |
| 主要指标 | 首次解析成功率（`extractJsonFromResponse` 第一层即成功） |
| 次要指标 | 必填字段完整率、枚举合规率、输出 token 数 |
| 成功标准 | 实验组 B 或 C 的首次解析成功率不低于对照组 A 5 个百分点（α=0.05） |

**如果实验组成功率显著低于对照组**：保留重度强调，放弃此优化。
**如果实验组成功率无显著差异**：采用轻度强调，节省 token 并降低提示词复杂度。

### 3.3 HYP-3：添加 Few-shot 示例能否提升格式稳定性？

#### 3.3.1 当前状态

除剧本生成外，分镜生成、场景润色、VLM 推断等功能都没有 few-shot 示例。模型输出格式不稳定，需要多层 fallback 解析。

#### 3.3.2 假设

**H₀**：添加 1 个 few-shot 示例对格式稳定性无显著影响。
**H₁**：添加 1 个 few-shot 示例可将首次解析成功率提升 15 个百分点以上。

#### 3.3.3 理论依据

- **GPT-3 论文（Brown et al. 2020）**：Few-shot 示例（3-5 个）可显著提升格式稳定性
  - **局限性**：
    - GPT-3 论文的实验是在**英文模型**上进行的，对中文模型的适用性未知
    - 论文中的任务是**简单的 QA 和文本生成**，不是复杂的结构化输出
    - 不能直接推导到中文模型和复杂任务
- **Anthropic/OpenAI 指南**：1 个示例即可覆盖大部分格式需求
- **需要验证**：在中文模型和复杂结构化输出任务上，few-shot 示例是否真的能提升格式稳定性

> **注意**：few-shot 示例的**理论依据相对充分**（有 GPT-3 论文支撑），但需要验证其在中文模型上的适用性。

#### 3.3.4 验证方案

**A/B 测试设计（以分镜生成为例）**：

| 项目 | 内容 |
|------|------|
| 目标模型 | DeepSeek-V3、通义千问-Max |
| 对照组 A | 当前版本（无 few-shot 示例） |
| 实验组 B | 添加 1 个简短示例（见下方） |
| 测试样本 | 5 个不同场景（茶馆/街头/室内/夜景/群戏） |
| 每组运行次数 | 每样本 × 每模型 × 5 次 = 50 次/组/模型 |
| 主要指标 | 首次解析成功率 |
| 次要指标 | 字段完整率、枚举合规率、token 效率 |

**示例内容**（分镜生成）：
```

输入场景：

{
  "shotNumber": 1,
  "shotType": "long",
  "cameraAngle": "eye_level",
  "cameraMovement": "static",
  "frameDescription": "【场景】茶馆内景，木质桌椅，晨光从窗户洒入\n【人物】张三位于画面右下角，侧身面向柜台\n【动作】张三抬手示意店员\n【氛围】暖色调，市井氛围",
  "characters": [...],
  "dialogueIds": ["dlg_1"],
  "actionIds": ["act_1"],
  "duration": 5,
  "transition": { "type": "cut", "durationMs": 300 }
}
```

#### 3.3.5 测试结果（已完成）

**测试时间**：2026-06-28
**测试配置**：每样本 5 次，共 50 次/组/模型

| 模型 | 对照组（无 few-shot） | 实验组（有 few-shot） | p-value | 结论 |
|------|----------------------|----------------------|---------|------|
| DeepSeek-V3 | 100% | 100% | 1.0000 | 无显著差异 |
| 通义千问-Max | 100% | 100% | 1.0000 | 无显著差异 |

**分析**：
1. **解析成功率都是 100%**：当前提示词对这两个模型已经足够清晰，没有格式错误
2. **Few-shot 示例无额外收益**：在解析成功率已经达到 100% 的情况下，few-shot 示例无法进一步提升
3. **假设不成立**：H₁（提升 15 个百分点）未得到数据支持

**原因推测**：
- 当前提示词已经足够清晰（明确的 JSON 格式要求 + 枚举约束）
- 测试场景不够复杂，不足以触发格式问题
- 这两个模型（DeepSeek-V3、通义千问-Max）能力较强，能稳定输出格式

**结论**：**reject**（保留对照组，不添加 few-shot 示例）

**后续建议**：
- 如果遇到格式不稳定的模型，可以重新测试
- 可以测试更复杂的场景（多角色、复杂动作、特殊镜头）
- 可以测试其他指标（字段完整率、枚举合规率）是否受影响

#### 3.3.5 预期效果（若验证通过）

|------|----------|

### 3.4 HYP-4：否定指令改为正向表述是否提升遵从度？

#### 3.4.1 当前状态

多处使用否定指令：
```
不要添加任何额外的开场白或结束语
不要瞎编 ID
不要解释，不要 markdown 围栏
切勿编造完全脱离原文的细节
```

#### 3.4.2 假设

**H₀**：否定指令与对应的正向表述对模型行为无显著差异。
**H₁**：正向表述的指令遵从率比否定指令高 10% 以上。

#### 3.4.3 理论依据

- **Pink Elephant Problem（心理学）**：否定指令反而让被禁止的概念更突出
  - **局限性**：
    - Pink Elephant Problem 是针对**人类心理**的概念，描述人类对否定指令的认知偏差
    - LLM（大语言模型）是否受此影响**尚无研究**
    - 不能直接推导到 LLM
- **Anthropic 指南**：使用正向表述（说"要做什么"而非"不要做什么"）
  - **局限性**：
    - 主要基于 GPT-4/Claude 的观察
    - 国产模型是否同样敏感**尚无数据**
- **需要验证**：否定指令对 LLM 的影响是否与对人类的影响相同

> **注意**：这个假设的**理论依据最弱**（心理学概念不能直接推导到 LLM），优先级应该最低。

#### 3.4.4 验证方案

| 项目 | 内容 |
|------|------|
| 测试场景 | 场景润色（否定指令最多） |
| 对照组 A | 当前否定指令版本 |
| 实验组 B | 正向表述版本 |
| 主要指标 | "出现开场白/结束语"的发生率 |
| 每组运行次数 | 30 次/组 |

**改写示例**：
| 否定指令 | 正向表述 |
|----------|----------|
| 不要添加开场白或结束语 | 直接输出 JSON 数据 |
| 不要瞎编 ID | 只使用提供的 ID，找不到时填 null |
| 不要解释 | 只输出 JSON，不含任何说明文字 |

### 历史教训

1. **v1 教训**：直接套用英文模型最佳实践，未经任何效果验证
2. **v2.0 教训**：部分 BUG 声明未经代码验证即写入（BUG-3 为推断而非事实）

**核心原则**：每个优化项都要回答三个问题：
1. 问题来源是什么？（用户反馈？日志？代码审查？）
2. 有没有数据支撑？（失败率？错误次数？）
3. 修复的成本和收益是什么？（工作量？预期改善？）
