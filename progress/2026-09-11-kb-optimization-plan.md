# 知识库检索优化最终方案（2026-09-11）

> 背景：针对「pdf/epub 解析与切片质量、章节级语义完整、检索可度量」的系列讨论沉淀。
> 前序已完成（分支 feat/kb-parse-chunking，均已推送）：
> - 解析层：pdf→@firecrawl/pdf-inspector、epub→@firecrawl/anydoc，输出结构化 Markdown
> - 切片层：段落感知子切（段落最小单元、短段合并、无 8000 硬切、首标题前言保留、锚点噪音清理）
> - 真实文档验证（《深度学习》epub 重处理）：491 块，内容缺失 0、顺序异常 0、相邻重复 0、
>   锚点噪音 0、最大块长 1498（≤1500）
> - 待办中心：三列表序号/时间列 + 固定底部分页（cd9de8ea）

---

## 一、目标

1. **检索质量可度量**（当前没有任何量化评估，一切优化凭感觉）
2. **语义完整性**：切片不被切断句子只是底线；章节级上下文（路径+摘要）让检索命中子块时也能"看见整章"
3. **能力上限**：复杂/多跳问题可通过 agentic 升级通道解决，且不影响默认管线的稳定与成本

## 二、优化地图（分层）

### P0-1 评估基线（先建度量，再谈优化）
- 建 **golden QA 评估集**：取代表性文档 3 篇（技术书《深度学习》epub、numpy-user.pdf、中文文本/合同类），每篇人工标 15~25 条「问题 → 应命中章节/段落」
- 指标：`recall@k`（k=5/10）、`NDCG@10`、`章节命中率`
- 产出：评估脚本 + 数据集（tests/ 或 progress/ 工具化），先跑通当前 pipeline 记录 **baseline 数字**
- 意义：后续每个优化（摘要注入、RRF、rerank）都用同一数据集对比，用数字证明有效/无效

### P0-2 章节树数据层
- 章节实体表（chapter：id/title/level/parent_id/start/end/content_hash）+ repository + 树形查询接口
- 现有 `StructureDetector` 已产出 `sections{title,level,parentTitle}`，落库即可
- 与 chunk 同生命周期：重处理/删除时级联重建
- 消费面：摘要挂载（P0-3）、检索上下文（P1-1）、UI 树（P2-2）

### P0-3 章节摘要生成
- LLM 逐章生成摘要（章级必出；子节级可选配置，默认章级）
- **异步 + 失败标记可重试，绝不影响切片入库**（切片先落库，摘要后补）
- 摘要存章节表；语言/长度可配置（默认中文、2~4 句）
- 成本模型：每章 1 次 LLM 调用（《深度学习》约 20 次/书）

### P1-1 检索上下文注入（contextual chunk，对标 Anthropic 思路）
- 检索命中 **child（段落块）** 后，组装给 LLM 的上下文 = `[章节路径 + 章节摘要] + 被命中块（可含相邻块）`
- 轻量实现：**检索时动态拼接**（不动库、不重向量化）；评估对比「有/无摘要注入」的 recall/答案质量
- 这是"用户章节树+摘要想法"与行业 contextual retrieval 的合流点

### P1-2 检索融合与过滤
- **Hybrid RRF**：BM25（复用 kb_inverted_index + nodejieba 中文分词）+ 向量（LanceDB）分数 RRF 融合
- **Rerank 全覆盖**：现有 kb-rerank 核对并接通所有检索路径（文档检索、QA 对检索、workflow 检索）
- **Metadata 过滤**：章节路径/文档类型/日期入 metadata，检索后置过滤 + 命中来源展示
- 每步用 P0-1 评估对比

### P2-1 查询端（可选，成本换精度）
- Query rewriting：检索前 LLM 改写为检索友好形式（轻量，+1 次查询调用）
- HyDE：假设文档嵌入（成本×2，暂缓）

### P2-2 UI 章节树（用户「树形数据+摘要」体验面）
- 文档详情侧边栏：章节树 + 摘要折叠 + 点击定位到切片
- 依赖 P0-2/P0-3 数据层

### P3 Agentic RAG 升级通道（不默认启用）
- 现有骨架已具备：workflow 引擎、agent-loop 节点、wf:kb-retrieve 工具、planner
- 落地形态：**分层升级**——默认走快速检索管道（便宜稳定），路由判断为复杂/多跳/低置信时升级到
  编排的 workflow 模板：`规划→检索→分析→再检索→总结（可含反思自检）`
- 模式对照：Planning（问题路由/拆解）、Iterative Retrieval（多轮再查）、Tool Use（kb 检索+web 搜索等）、
  Reflection（可选自检）

## 三、明确不做（技术判断）

| 方案 | 原因 |
|---|---|
| Late chunking | 依赖支持该能力的 embedding API，当前 text-embedding-v4 无此接口 |
| GraphRAG（微软） | 为「跨多文档全局综合」设计，成本极高；本项目以单文档局部检索为主 |

### M4 评估定论（双数据集权重扫参；真实检索管线）

| 策略 | 语义型 32 条 recall@1 | 语义型 NDCG@10 | 关键词型 10 条 recall@1 | 关键词型 recall@3 | 关键词型 NDCG@10 |
|---|---|---|---|---|---|
| 纯向量 w=1.0（现默认） | **96.9%** | **98.8%** | 70.0% | 70.0% | 74.3% |
| 混合加权 w=0.8 | 93.8% | 97.7% | 70.0% | 80.0% | 79.6% |
| 混合加权 w=0.7 | 93.8% | 97.7% | 80.0% | 80.0% | 84.3% |
| 混合加权 w=0.5 | 93.8% | 97.7% | 80.0% | 90.0% | 86.3% |
| **混合 RRF w=0.5** | **96.9%** | 98.2% | **80.0%** | **90.0%** | **86.3%** |

**结论**：不存在单一最优——语义型问句纯向量最强，关键词型查询（API 符号/法条编号/专有名词）混合显著更强。
**RRF 综合最优**：语义型 recall@1 与纯向量持平（96.9%）、关键词型 +10pt@1 / +20pt@3。
**当前决策**：默认保持纯向量（不因 10 条小样本改动全局行为），RRF 保留为可选开关；
**下一步建议**：查询自适应路由（检测到编号/符号/英文 API 名词 → 自动切 RRF）或把开关暴露到知识库配置。
