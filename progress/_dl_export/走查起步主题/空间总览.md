## [区:what] 它是什么：一句话 + 定位

**一句话定义（本空间快照，确证）**：认知走查是人因/可用性领域的一种**走查（walkthrough）变体**——评估者以**新手用户视角**，沿**任务步骤**逐问『用户能否注意到这个操作、知道该怎么做、得到正确反馈』，从而评估界面的**可学习性（learnability）**。

**权威佐证（NN/g，已读元信息）**：NN/g 将本页命名为 *Evaluate Interface Learnability with Cognitive Walkthroughs*，页面描述为『可学习性是**复杂且新颖的界面** UX 的关键组成，认知走查能找出**把新用户带偏的设计问题**』；其关键词把 cognitive walkthrough 与 heuristic evaluation 同列于 **usability inspection methods** 家族——即它属于『专家/评估者检查』类方法，而非『招募真实用户测试』类。

> 关键词句（NN/g）：*Learnability is a crucial component of UX for complex and novel interfaces. Cognitive walkthroughs can identify design problems that derail new users.*

## [区:when] 何时用它（部分为待验证先验）

依据 NN/g 的定位与快照定义，可确认的核心场景是：**想评估『新手第一次用能不能学会/走通』而非『老手用得快不快』**。

以下为【待验证先验】（超出已读证据，需人审或补原典核实）：
- 常用于**设计早期/原型阶段**，因为可以**不招募真实用户、不需要可运行系统**，靠评估者脑内模拟即可执行；
- 适合**界面新、任务结构复杂、首次使用成功率重要**的产品（如企业软件、复杂表单、新交互范式）；
- 与启发式评估的区别取向：启发式评估对着一组通用原则逐项挑毛病；认知走查**锚定具体任务的一步步动作**，问『新手在每一步会不会卡住』。

## [区:how] 怎么做：核心问题与走查流程

**核心三问（快照确证）**：沿任务步骤，以新手视角对**每一步**问：
1. **用户能否注意到操作？**（界面上有没有足够线索让他发现『这里可以/应该这样做』）
2. **用户知道怎么做吗？**（即便注意到了，他能否把目标映射到具体动作）
3. **用户能得到正确反馈吗？**（做完后界面是否告诉他『做对了/做错了』）

**典型走查流程（此条为【待验证先验】，为通行做法的概括，建议以原典 Wharton et al. 1994 / Polson et al. 1992 核校后标注）**：
1. 明确**目标用户画像**与要评估的**关键任务**；
2. 把任务拆成**可操作的动作序列**（每一步 = 用户做的一个具体操作）；
3. 对每一步，由评估者扮演新手回答上述问题，并假设一个**合理的用户目标/心智模型**；
4. 记录**失败步骤**——哪一步用户会卡住、卡住的原因（没看到？看不懂？反馈缺失？）；
5. 汇总成**可学习性问题清单**，按任务与步骤编号排列，交设计修复。

```mermaid

  A[选定新手用户画像与关键任务] --> B[拆解为逐步骤动作序列]
  B --> C[每步逐问: 能否注意到/知道怎么做/得到反馈]
  C --> D{能顺利走通?}
  D -- 否 --> E[记录失败步骤与失败原因]
  D -- 是 --> F[下一步骤]
  E --> F
  F --> G[汇总可学习性问题清单]
```

## [区:output] 产出物与判读口径（待验证先验）

以下为【待验证先验】概括：
- **产出**：一张『任务×步骤』的问题清单，每条含：位置（第几任务/第几步）、卡点描述、违反的三问中的哪一问、可能的修复方向；
- **判读口径**：如果多处步骤卡在同一问上，往往对应一类系统性问题（例如整体『操作可见性』不足，或整体『反馈缺失』）；
- 它是**定性诊断**而非定量指标，通常**不输出通过率/评分**，而是给设计团队可行动的定性反馈。

## [区:limits] 边界与局限（待验证先验）

以下为【待验证先验】：
- 评估者**并非真实用户**，对『新手会不会卡』的判断依赖评估者对新手认知的移情与任务假设，可能高估或低估难度；
- 擅长发现**可学习性**问题，**不太覆盖**美观、长期使用效率、性能等其它维度；
- 逐步骤推演较耗时，适合**关键任务**而非全界面地毯式扫描；
- 常与启发式评估、真实用户测试**互补**使用，而不是互相替代。

## [区:what] 是什么：一句话定位

**走查（walkthrough）** 是本空间定义为『一种轻量级同行评审：由作者引导、参与者按步骤逐项『走』过代码/设计/文档等产物，边读边提问，以发现问题并统一理解』的评审活动。

英文资源（DBpedia）将其定位为 **form of software peer review（软件同行评审的一种形式）**；'Structured walkthrough（结构化走查）' 一词在资源中重定向到本条目，可视为别名（待核实中文教材用法）。

在评审家族里，它与 inspection（检查）、technical review（技术评审）、code review（代码评审）等同属「软件评审/软件同行评审」概念族（据 DBpedia 关联数据）。

## [区:why] 为什么需要：价值与目标

- **目标双元**：① 发现问题（缺陷/歧义/逻辑错误）；② 统一理解（让参与者与被走查产物在认识上对齐）——这是空间定义强调的定位。
- **轻量、非正式、低成本**：相对『检查 inspection』更轻，适合项目节奏；正因为轻，才适合作为日常质量活动起步（本空间即以『走查起步』为主题）。
- 先验提示（needs_verification）：评审类活动用于『把缺陷留在开发上游、越早发现修复成本越低』的说法为软件工程通识，本讲义未及从已读资料取据。
- 先验提示：同行评审同时有**学习教育价值**（新成员通过旁听走查熟悉代码/设计），详见『走查流程与角色』节点教学。

## [区:object] 走查什么：对象与形态

据 DBpedia 资源关联，软件走查语境下被走查的产物可包括：
- **源代码（Source code）**
- **软件设计文档（Software design document）**
- **测试用例（Test case）**
- **用例（Use cases）** 等

即：凡『可由作者逐步引导走过、参与者在过程中对照提问』的开发产物，都可走查。

另有 **Reverse walkthrough**（DBpedia 关联到独立词条，据资源名推测为『从后往前/反向走查』的变体，含义待核实）与 **Cognitive walkthrough**（见下方辨析）。

## [区:vs] 别混淆：两个同名近邻

1. **认知走查 Cognitive walkthrough（UX 语境）≠ 软件评审走查**：认知走查是**可用性评估/检查**方法——评估者模拟（新）用户按步骤执行任务来『走查』界面，找出潜在的失败点（potential failure points）。它与代码评审无关，只是共享『walkthrough』这个名字（DBpedia 亦将 Cognitive_walkthrough 列为独立关联词条）。

2. **检查 Inspection（正式评审）≠ 走查**：inspection 是更正式、通常有清单与缺陷度量的评审类型（DBpedia 关联 Fagan inspection、Software inspection 等词条佐证其作为独立且更正式形态的存在）；具体差异（正式度、角色分工、是否产出缺陷统计、走查不要求独立清单式检查等）为本讲义先验，详见『检查（正式评审）』与『走查流程与角色』节点。

## [区:trend] 延伸：走查类方法的前沿

走查方法正进入『用大模型模拟/自动化』的研究视野。arXiv:2512.03568（2025）以认知走查（CW）为例：
- 动机：『像认知走查这样的可用性测试成本可能很高』，作者尝试用 LLM（GPT-4、Gemini-2.5-pro）**模拟人类走查过程**；
- 发现：LLM 驱动的走查任务完成率更高、导航路径更优，但**识别出的潜在失败点更少**；经额外提示后 LLM 能预测人类发现的部分失败点。

启示：走查这类『逐步走过+提问找茬』的方法学既可用于人，也正被研究如何交给模型做低成本预筛——但模型目前仍会漏检（对『失败点』敏感度低于真人小组），说明人机结合的走查形态值得关注。

# 讲义: 检查（正式评审）

- 状态: draft | version: 1
- 更新时间: 2026-09-09 01:52:08.197

## [区:definition] 一句话定义与定位

**定义（空间快照·确证）：** 检查（正式评审）是与**走查相对**的正式同行评审形式：成员先独立准备，按**固定角色**与**检查清单**逐项查找缺陷并记录**度量**（如 Fagan 检查），比走查更正式、可度量。

关键定位：
- 同属**同行评审/软件评审**家族，与走查（walkthrough）构成对照：走查偏讲解型/宽松，检查偏查找缺陷型/正式。
- “正式”体现在：先独立准备 → 角色分工明确 → 依清单逐项找缺陷 → 缺陷被**记录并量化**（度量），而不是边读边随意讨论。
- 原型代表是 **Fagan 检查**（见 [来源: 快照]；经典出处 Fagan 1976，原文待补读）。
- 在“走查起步主题”学习路径上，**先学走查、再学检查**（快照显示 走查→检查 为前置依赖）。

## [区:why] 为什么值得学：检查能带来什么

直觉：缺陷发现得越早、修改成本越低；而仅靠作者自查或松散走查，容易漏掉**复杂、底层的缺陷**。正式检查通过“多人各自独立准备 + 清单化 + 记录度量”把找缺陷变成可重复、可度量的过程，并把缺陷数据反哺组织改进。

已读证据（arXiv:2204.10107，企业案例研究）：
- 有全球 ICT 企业把一种**回溯式检查（retro-inspection）**制度化，其形态“similar to Fagan inspection but differs in terms of stage, participants, etc.”——即业界确有与 Fagan 检查同族的正式检查实践。
- 研究发现该检查“**distinguishes itself from peer code review by identifying more complicated and underlying defects**”——与普通同行代码评审相比，能识别更复杂、更底层的缺陷。
- 企业主张检查“can benefit not only **quality assurance** (like Fagan inspection), but also internal audit, inter-division communication, and competence promotion”——检查的价值不止质量保证，还外溢到内部审计、跨部门沟通与能力建设。
（[先验·待验证] 关于“早期缺陷成本杠杆”“检查比走查缺陷检出率高”等定量结论常见于教科书，需原文核实后引用。）

与“同行代码评审（peer code review）”的区分（[arXiv:2204.10107 证据]）：正式检查被认为能识别**更复杂、更底层**的缺陷，与偏快速/工具化的现代代码评审是不同的实践形态。

## [区:mechanism] Fagan 检查怎么运作（模型先验·待验证）

> ⚠️ 本节约内容来自教科书经典模型，**未在本轮读到的资料中直接验证**，落地为讲义草稿仅供人审参考，后续须以 Fagan 1976 原文 / IEEE 1028 标准核对。

经典流程（常见表述为六阶段）：
1. **计划（Planning）**：确定检查对象、时间、参与者；
2. **预检（Overview）**：作者向检查组成员介绍背景；
3. **准备（Preparation）**：各成员独立阅读、按检查清单找缺陷；
4. **检查会议（Inspection meeting）**：由“讲解者”逐行/逐段念，主持人控制节奏，**只记录缺陷、不在会上修改**；
5. **返工（Rework）**：作者修正缺陷；
6. **跟踪/复查（Follow-up）**：主持人核对是否全部关闭，决定是否复检。

常见角色分工：主持人（moderator）、作者（author）、讲解者（reader）、记录员（recorder）、检查员（inspectors）。

配套要素：**检查清单（checklist）**（按缺陷类型逐项排查）、**度量（metrics）**（缺陷密度、检查速度、返工工作量等）、**退出准则**与**过程改进**（用缺陷数据改进清单与流程）。

## [区:metrics-pitfalls] 度量、常见误区与自动化延伸

**为什么要“记录度量”？**（[快照确证]）——度量使“正式”落地：检查不再只是“开个会”，而是可统计、可比较、可改进的数据来源。典型度量（[先验·待验证]）：缺陷密度（defects/KLOC）、检查速率、返工成本、缺陷按类型分布。

常见误区（[先验·待验证，供人审]）：
- 把检查会当成讨论会/修复会（正式检查会上**不改**缺陷）；
- 角色混同（作者既讲又记、无人主持节奏）；
- 跳过“独立准备”直接开会，退化成走查；
- 只做清单勾选、不记录度量，失去过程改进数据。

**自动化延伸**（已读证据 arXiv:cs/0607063）：静态检查工具可作为**附加的自动化检查步骤**纳入开发周期（“Static software checking tools are useful as an additional automated software inspection step...”），可视为人工正式检查的互补而非替代。

## [区:definition] 定义与定位（快照确证）

**一句话定义（本空间快照确证）**：组织一次走查所需的**角色**（作者 / 走查组长 / 记录员 / 走查成员）与**大致步骤**（计划 → 会前准备 → 走查会议 → 修订 → 跟踪）。

## [区:roles] 四类角色

**角色名称来自快照确证**：走查由以下四类人组织起来：
1. **作者（Author）**：被走查产物的作者/负责人，向与会者讲述其产物。
2. **走查组长（Moderator / 组长）**：主持走查、控制进程与节奏，保证会议聚焦于“找问题”而非“评人”。
3. **记录员（Recorder / Scribe）**：如实记录会上发现的问题，形成问题清单。
4. **走查成员（Reviewer / 参与者）**：以读者视角查读材料、提出问题与改进意见。

> ⚠️ 待验证：上表中每条“职责”为模型先验（对应英文术语如 Author/Moderator/Recorder/Reviewer 也需在中文语境核对）；快照仅确证“存在这四类角色”，未确证各自职责。

**入门要点**：走查强调“作品查读 + 多方视角找问题”，角色分工是为了让讨论有序、让问题被完整记录——这也是为什么需要独立的组长与记录员。

## [区:process] 五步流程（阶段名来自快照确证）

走查大致经历五步（阶段顺序为快照确证，各步活动为待验证先验）：
1. **计划（Planning）**：确定走查对象、时间、参与人与组长。
2. **会前准备（Preparation）**：与会者事先阅读待走查材料，标出疑点。
3. **走查会议（The Walkthrough Meeting）**：作者讲解产物，走查成员按流程逐段查读提问，组长主持，记录员把问题记入问题清单。
4. **修订（Rework）**：作者依据问题清单修改产物。
5. **跟踪（Follow-up）**：核对修订是否完成、问题是否关闭，防止“改了没跟踪”。

> ⚠️ 待验证：各阶段“做什么”及英文对应（Planning/Preparation/Meeting/Rework/Follow-up 等）为模型先验，需用权威来源（如 IEEE 1028 评审标准、软件工程教材“评审/走查”章节）逐条核验。

**入门要点**：步骤里“走查会议”是核心，“修订→跟踪”闭环则保证走查不只是开一次会——发现问题后要有人负责改、有人负责核。

## [区:linkage] 产出衔接（与后继概念的关系）

按快照，本概念后继为「**走查产出：问题清单与修订跟踪**」：

# 讲义: 走查产出：问题清单与修订跟踪

- 概念 id: cd18ed1f-dea8-4611-a1b6-a7307cf09163
- 本质类型: K-concept
- 状态: draft | version: 1
- 更新时间: 2026-09-09 01:59:11.667
- 自动核验: status=verified issues=9

## [区:definition] 一句话定义（本空间确证）

**走查会后的产物：把发现的问题/疑问/建议与结论记录成清单，并指定行动项跟踪到修订完成，让走查不流于形式。**（来源：本空间学习快照确证定义）

要点拆解：
- 它是一份**会后的记录物（artifact）**，不是会议本身；
- 内容分两类：**问题/疑问/建议**（会议中提出的发现）与**结论/行动项**（对每条发现给出的处置与责任人）；
- 目标是**跟踪到修订完成**——只有闭环了，走查的投入才算兑现。

> ⚠️ 标注说明：以下各节中，凡带【先验·待验证】的条目为本助手基于软件评审领域通用认知的整理，受本会话采集条件所限未找到原文佐证，需按 IEEE Std 1028-2008 / ISO-IEC 20246-2022 或组织实际模板人工核对。

## [区:why] 为什么必须有这份产出

评审/检查类活动（走查属其一）的价值在于**发现缺陷并将其转化为改进**。有据依据如下：

> “Software inspection has proved to be the most effective and efficient technique enabling defect detection and prevention. Inspections carried at all phases of software life cycle have proved to be most beneficial and value added to the attributes of the software.”（arXiv:1001.3725 摘要）

推论链（部分为模型先验，逻辑自洽但需结合上句核对）：
1. 若只开会、口头提问题而不**落成清单**，发现随记忆消散——走查流于形式；
2. 若清单不**指定行动项并跟踪**，问题悬置、无人修订——走查无法带来改进；
3. 因此“清单 + 跟踪”正是把会议投入转化为可核查产出的闭环装置。【先验·待验证】

## [区:structure] 一份问题清单通常记录什么

以下为常见字段清单【先验·待验证】，请以组织模板 / 企业评审规范为准：

| 字段 | 记录内容 |
| --- | --- |
| 编号 | 唯一序号，便于引用与跟踪 |
| 位置 | 走查对象的工件与位置（如代码文件+行号、页面、章节+段落） |
| 类型 | 缺陷 / 疑问 / 建议 / 不一致 / 范围外 |
| 严重度/优先级 | 决定处理顺序（如 高/中/低） |
| 提出者 | 谁发现的（保留人与角色） |
| 结论/处置 | 是缺陷？如何改？还是澄清即可？ |
| 负责人 | 认领修订或澄清的行动项 owner |
| 期限/版本 | 何时或哪个版本前必须完成 |
| 状态 | 打开 → 已修订 → 待复查 → 关闭 |
| 复查记录 | 修改后由谁复核、结论 |

要点：**问题与建议分开记录**、**每条都有 owner 与期限**，是让清单可执行的关键。

## [区:tracking] 修订跟踪闭环（会后到关闭）

典型闭环如下【先验·待验证】：

```mermaid
flowchart LR
  A[走查会议
记录问题/结论] --> B[会后整理成问题清单
分派行动项] --> C[责任人修订
或给出澄清] --> D[复查/再走查
核对修订] --> E{通过?}
  E -- 否 --> C
  E -- 是 --> F[关闭该条
保留审计记录]
```

要点：
- **复查(re-inspection/验证)是必须环节**：修订不等于完成，需对照原问题核验后才可关闭；
- 未关闭项应进入**下一轮走查或里程碑评审**的回顾清单，防止悬置；
- 清单本身可留作**过程审计与改进依据**（重复问题类型可反哺流程改进）。

> 此处的“复查闭环”描述为模型先验；IEEE 1028 系列对不同评审类型的输出与后续处理有正式定义，待原文补证。

## [区:pitfalls] 常见坑（自查清单）

均为模型先验归纳【先验·待验证】，作自查用：

1. **只口头不落单**——会议结束即遗忘；
2. **问题与建议混淆**——类型不分导致处置方式混乱；
3. **无负责人/无期限**——行动项无人认领，无限期悬置；
4. **修订后不复查直接关闭**——改了≠改对了；
5. **把“疑问”当“缺陷”定性**——造成对立氛围，削弱走查的非对抗协作属性；
6. **清单无归属**——没人维护状态，跟踪断链。

自查口诀：**条条有单、单单有主、主主有期、改后必查、查完才关**。【先验·待验证】
