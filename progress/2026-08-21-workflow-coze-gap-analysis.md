# 工作流平台化差距梳理：对标扣子（Coze）

> 日期：2026-08-21 ｜ 目的：评估把当前工作流功能打造成类似扣子（Coze）的低代码 AI 编排平台所需增加的模块
> 参考：扣子公开能力（插件市场/变量/数据库/记忆/多 Agent/发布渠道等）

---

## 一、当前系统能力盘点（已有家底）

- **编排引擎**：30 个内置节点——流程控制（start/end/condition/parallel/loop/delay/assign/human-review/form-collect）、
  AI（llm-chat/kb-retrieve/kb-qa/kb-ingest/web-search/translate/image-gen/tts/stt）、
  数据（http-request/oas-tool/web-extract/parameter-extractor/template-transform）、输出（report/report-image/message/app-notify）
- **RAG 知识库**：向量库 + 分段 + QA 对 + rerank + BM25 混合检索（对标扣子知识库的强项）
- **人机协作**：human-review 三模式（choose/input/approve）+ form-collect 中途挂起（扣子/Dify 同级能力）
- **发布**：应用四渠道（会话/分享链接/API/定时 cron）+ 免登录分享页 + REST invoke/SSE
- **质量**：图校验器（环检测/出边约束/配置深度校验）、试运行、运行历史/详情、节点目录一致性自检、TDD

## 二、差距清单（扣子模块 → 当前状态 → 需新增）

| # | 模块 | 扣子能力 | 当前系统 | 差距 | 优先级 |
|---|------|---------|---------|------|--------|
| 1 | **第三方 API 接入/工具** | 插件市场：常见 API 一键接入 + 凭据库 + 可复用封装 | 部分（http-request/oas-tool 可调任意 API，但 key 手填明文、无凭据库、无预设模板、无法封装复用） | **凭据管理 + 预设工具模板 + 自定义工具封装**（复用现有 http-request/oas-tool 与 SecureStorage） | **P0（最高）** |

## 三、Roadmap 建议

- **P0（对齐核心编排平台能力 + 生态价值基础，4~5 周）**：
  1. **第三方 API 接入完备化（首项）**：
     - 凭据库：第三方 API key 加密存储（复用 SecureStorage），http-request/oas-tool 支持凭据引用/下拉选择，杜绝配置明文
     - 预设工具模板：内置常见 API 一键接入（搜索/翻译/天气/OCR/新闻/图片等，URL+鉴权+参数映射模板）
     - 自定义工具封装：把常用 API 调用保存为"自定义工具"（名称+URL+headers+参数 schema），工作流节点直接引用
  2. 代码节点（sandbox 执行 JS/Python 子集，R4 安全边界）
  3. 子工作流节点（复用现有 runService，definitionId 嵌套 + 入参/出参映射）
  4. 变量节点 + 数据表（persisted 存储，按 user 隔离）
  5. Webhook 触发器（token 免签 + 入参 → start inputs）
- **P1（平台体验，2~3 周）**：
  6. 插件化节点 SDK（manifest + 注册表 + 编辑器面板动态加载，建立在 #1 之上）与完整插件市场
  7. 调试增强（断点/单步/变量面板）
  8. 版本对比/回滚 + 模板市场
  9. Agent 节点（工具循环）
- **P2（生态与规模）**：记忆、视觉理解、IM 渠道、用量面板、团队协作

---

## 四、结论

当前系统在**编排引擎、RAG、人机协作、发布渠道**四个方向已有对标扣子的扎实基础；
**第三方 API 接入（工具能力）是最大短板也是最大机会**——现有 http-request/oas-tool 已能调任意 API，
补齐"凭据库 + 预设模板 + 自定义工具封装"三件套后即可达到扣子工具市场的最小可用形态，
再叠加代码节点/子工作流/变量/Webhook 即完成 P0 平台底座。
