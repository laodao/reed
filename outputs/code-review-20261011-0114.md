### H1. browser-render 并发信号量死锁——实测复现，任务永久挂起且不可取消

- **提交**：cbf8e897
- **位置**：`src/core/platform/workflow/nodes/browser-render.ts:60-72`
- **问题**（独立脚本复现确认）：`releaseRenderSlot()` 移交槽位给等待者时**不递减** `activeRenders`——被唤醒者重查条件仍为真重新入队。两个渲染槽饱和且有第三个调用者排队后，`activeRenders` 永久停在 2，**之后所有 renderPageHtml 永久挂起**。加重因素：排队等待不受 30s 超时约束（timer 在 acquire 后才启动）、不响应 AbortSignal；`render` 缺省即 `auto`——存量多链接抓取工作流遇 ≥3 个反爬页即可能永久挂死且无法取消。验收跑的是串行 loop 故未暴露。
- **建议**：release 无条件 `activeRounds--` 或改"唤醒即授予"；abort 时 reject 所有排队者。

### H2. browser-render「SSRF 双闸门」不覆盖页面内子请求；重定向闸门是事后检查

- **位置**：`browser-render.ts:88-102`（webRequest 只 cancel image/media/font）、`:217-222`（finalUrl 校验）
- **问题**：闸 2 在页面**完全加载后**才校验最终 URL——重定向到内网时浏览器已完成请求并下载响应体；更大的缺口：页面 JS 可自由发请求（fetch/XHR/iframe/script/websocket 均不被拦截），向 `127.0.0.1`/`169.254.169.254`/`192.168.x` 的盲打 SSRF 完全可行（SOP 限制回读，但"发请求"不受控）；DNS rebinding 可同时绕两道闸。对比：HTTP 路径是逐跳先过闸再跟随——浏览器路径弱于自家纪律。
- **建议**：onBeforeRequest 对每个请求 URL 过 `validateOutboundUrl` 不过即 cancel（一次性覆盖重定向/子框架/页面内子请求）；加 `will-navigate` 拒绝未过闸导航；修正"双闸门"的高估表述。
