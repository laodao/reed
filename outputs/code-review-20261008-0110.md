## 高危（5 项）

### H1. capMemory 截尾方向与设计完全相反——丢的是最新情节，保的是最早情节（实测复现）

- **提交**：903bc59d
- **位置**：`src/core/platform/services/kb-brain/book-reading.service.ts:86-114`
- **问题**：函数头注释与提示词纪律（「优先压缩情节进展**最早**段落的细节」）都声明最早细节先丢；实现却是顺序扫描保留预算内**前段**（最早章）、超线后丢弃**全部后段**（最新章）。实测（300 章情节、cap=2000）：保留第 1~42 章，丢弃第 43~300 章。滚动阅读最要紧的恰是最近批次建立的剧情状态——该 backstop 在模型超出 8000 字软纪律时触发，砍的正是下一批合并所需的最新上下文。
- **附带缺口（同函数，实测）**：① 超限记忆若无「## 情节进展」标题（模型不守结构时）整体 passthrough，硬上限失效；② `lines.indexOf(line)` 遇重复行（尤其空行）取首个 occurrence，截断触发点恰在空行时 `rest` 起点错位 → 段落重复推送。
- **建议**：从「情节进展」段**尾部**向前保留（丢段头）或按行倒序装填；无该标题时退化为整体尾部截断兜底；indexOf 改索引循环。

### H2. `<think>` 剥离未作用于最终返回值——思考里的 JSON「草稿」会被解析成正式答案（实测复现）

- **提交**：903bc59d
- **位置**：`src/core/platform/services/kb-brain/llm.ts:110-137`（`return full` 原样返回）+ `book-reading.service.ts:285`
- **问题**：`stripThinkBlocks` 只用在空输出判定与截断判定两处循环条件里，函数返回的仍是含 `<think>` 的原文，raw 直接交给 `extractJsonFromResponse`。实测（严格复刻 ai-call 判定链）：`<think>我需要输出 {"memory":"草稿"}</think>{"memory":"正式答案"}` 解析结果为 `{"memory":"草稿"}`——推理模型在思考里起草 JSON 是常态，轻则整批因缺字段失败，重则把思考草稿当正式记忆沉淀。think 无花括号时侥幸走通。
- **建议**：`defaultBrainLlm` 最终 `return stripThinkBlocks(full)`，或在 `extractJsonFromResponse` 入口先剥 think（后者惠及所有调用方）。

### H3. 云审核拦截章仍会拖死整书——「不拖死整书」承诺未实现

- **提交**：903bc59d
- **位置**：`src/core/platform/services/kb-brain/digest-orchestrator.service.ts:819` + `:396-421`
- **问题**：审核拦截时 digestChapter 返回 `{ outcome: 'exhausted', moderation: true }`，但外层循环 `if (outcome === 'exhausted') exhaustedChapters.push(...)` 先于 moderation 判定执行——该章同时进两个数组，随后 `exhaustedChapters.length > 0` 命中 → **文档标 failed 并提前 return**，`moderationSkipped` 的 warn 分支在有审核章时永远不可达，stale 重链/实体摘要/书级汇总全部跳过；还会经 automation 反复入队重试至耗尽成永久 failed——恰是提交信息声称要避免的结果。新增测试只测了 `isModerationRejection` 纯函数，没有文档级终态用例，276 全过也没暴露。
- **建议**：`if (outcome === 'exhausted' && !moderation)` 才计入失败；补「审核拦截章 → 文档仍 digested + 留痕」的编排级测试。

### H4. Web 端「全书精读」参数形状错位——多租户 Web 端功能静默失效

- **提交**：903bc59d
- **位置**：`src/web/client/channel-map.ts:273-274` vs `src/preload/index.ts:1280-1281` vs `BrainPanel.vue:1458,1479`
- **问题**：preload 新方法用**对象参数**（`readingStatus: (p: { kbId })`），BrainPanel 也传对象——Electron 端链路通。但 Web 端 bridge 按 CHANNEL_OVERRIDES 的 `wrap: (kbId) => [{ kbId }]` **位置参数**约定转换：传入的对象被整体塞进 `{ kbId: {kbId:'...'} }`——handler 收到对象后所有查询空转，返回 `queued: true` 但**什么都不跑**，UI 轮询 5 秒后静默停止。同文件既有调用全是位置参数，只有这两个新方法偏离约定（renderer 依赖 `electronAPI: any` 全局声明，无类型检查兜住）。
- **建议**：统一为位置参数（改 preload 签名 + BrainPanel 调用）或 channel-map wrap 改透传对象；补 Web 端形状断言。

### H5. 看护 15min 判据与本提交引入的 16K→64K 预算翻倍重试自相矛盾

- **提交**：903bc59d
- **位置**：`src/core/platform/services/kb-brain/automation.service.ts:299-317` vs `llm.ts:34-40,105-111`
- **问题**：看护宣称「存活的消化循环必然持续触碰台账」，但单章内部只有章首一次 `setRunning`——64K token 输出生成普遍 15-35 分钟，推理模型 16K 思考耗尽本身就要数分钟，**单章 LLM 调用超 15min 是翻倍重试机制的常态后果，必然触发误复位**。后果推演：chain 串行 + ensurePass 幂等保证不双跑章、无数据损坏，但会造成重复全文档幂等重扫（大书数百次查询浪费）+ 状态闪烁 + 日志噪音；且看护对「进程内 LLM hang」（chain 堵死）无效——它无法区分「进程活着但慢」与「进程死了」。
- **建议**：STALE_MS 提到 ≥ 翻倍重试最坏时长（≥45-60min），或改用进程内心跳（digest 循环定期 touch 内存注册表，看护读注册表而非只看 DB）。

## 中等（9 项）

**M1. maxTokens 统一常量 8000→16000 全局抬高且无 clamp** — `llm.ts:29-30`、`simple-llm.ts:53`。本提交把 `BRAIN_LLM_MAX_TOKENS` 本身抬高，影响所有走该常量的既有产线；显式小预算调用（consolidate 2000/corpus 1500）空输出翻倍时会被抬到 4 倍。翻倍机制本身正确（封顶 64K、≤2 次、重试真携带新预算），但 `maxOutputTokens` 无按模型输出上限的 clamp，输出上限 <16K 的模型是否 400 取决于 provider；且翻倍只对空输出触发，provider 直接报错不重试。

**M2. 断点锚点只哈希批末章** — `book-reading.service.ts:264-271`。done-same-hash 只比对批末章 hash：批内其他章改动不失效；批边界由 env/过滤规则/章节集合决定，任一变化后新批末章恰与旧锚点重合时，内容已不同的批被误跳过。建议整批各章 hash 合成。

**M3. 失败批续跑乱序合并仅靠提示词兜底** — `book-reading.service.ts:298-304`。批 i 失败批 i+1 成功后，续跑重读批 i 时记忆已含 i+1 内容，倒序合并正确性完全依赖提示词「以晚出章节为准」，无代码保障无测试。

**M4. reading-run 不校验 doc 归属 kb + kbRow 判空缺失** — `kb-brain.handler.ts:388-423` + `book-reading.service.ts:221-227`。`run()` 只查 doc 存在不校验 `doc.knowledgeBaseId === kbId`：把 B 库 documentId 塞给 A 库可读 B 库章节、在 A 库产出指向 B 库文档的记忆卡。跨租户被 ALS 兜住，同租户跨库成立。紧邻的 book-passes-run 有 kbRow 判空，新通道漏了——kbId 无效仍照常 fire-and-forget。

**M5. 审核拦截识别只覆盖 digest 管线** — `digest-orchestrator.service.ts:1428-1430`。book-reading 对审核拦截与普通失败同路径，续跑会反复重撞被拦批（有界 3 次，但每次是整批 24K 字成本）；正则按中英文文案匹配，Gemini SAFETY、Azure content_management_policy 等措辞不覆盖。建议 book-reading 复用 `isModerationRejection` 直接标 exhausted。

**M6. 双发竞态可并发起两个 run** — `kb-brain.handler.ts:389`。isRunningKb 检查与 run() 注册 key 之间隔着 await，连点两次可双跑；两个 run 交错 evolveCard 是 last-writer-wins，记忆可能丢批。与 book-passes 同款模式（非新引入），新通道窗口更大。

**M7. 提交信息虚假声明** — 提交信息声称「provider customParams 双重编码修复」，该修复不存在于本提交的任何文件（ai-call.ts 的 +42 是 JSON 平衡扫描）；所谓修复实为 reset 脚本里的运维动作；且若历史真有双重编码存量数据，读侧无任何兼容处理（读出 string 静默 undefined）。建议提交信息如实描述、读侧补 string→parse 兼容。

**M8. reset 脚本失败路径留脏状态** — `scripts/kb-brain-reset.cjs:94-118`。第 2 步事务已把**全库**文档置 pending 并提交，第 3 步找不到目标文档时 assert 退出——automation 会把全部文档重新消化，违背脚本自己的设计。目标查找应前置。另：遗漏清 `kb_automation_log`（残留 noteIds 指向已删卡）；只连本机 LanceDB，pgvector 后端的 Web 部署完全清不到。

**M9. 测试缺口集中漏网** — 三个高危的漏网处均无用例：capMemory 只断言保住头尾段名未断言丢哪头（H1）；extract-json 未覆盖 think 混入形态（H2）；digest 只测纯函数无文档级终态（H3）；Web bridge 形状无断言（H4）。book-reading 的 fake LLM `void req` 丢弃请求——「每批携带上一批工作记忆」这一核心机制**零断言**。
