## 一、结论摘要

DramaClaw 和本项目属于**同一赛道**（AI 影视/剧集工业化生产平台），产品主线几乎同构：**文本 → 资产 → 剧本/分镜 → 画面音频 → 合成成片**。本项目（episode-production 包）已完成约 80% 的主线能力，且在若干环节**反而领先**（长文写作上游联动、AI Agent 直驱生产、参考视频反向导入、质量自检、双端）。

按**对视频输出质量的贡献**重排后，值得借鉴的功能分为四档：

| 档位 | 功能 | 质量贡献机理 | 工程成本 |
|---|---|---|---|
| **Q-S：决定每帧画面上限** | ① 导演世界 L1 导演工作台 | 空间/站位/构图 → 控制图 → 首帧 → I2V 强继承，视频生成前唯一的确定性画面控制 | 2–4 周（地基大半现成） |
| | ② 资产版本历史 + 写回影响范围提示 | 资产是每一帧的输入；角色脸/服装/场景回归（变差无法回滚）= 全片性劣化 | 小（数据已在，差 UI） |
| **Q-A：防劣化、保一致** | ③ 风格模板库（含避免指令） | 跨镜头/跨集风格一致 + 负向提示直接压 artifact（文字残留、水印） | 中 |
| | ④ 阶段检查清单产品化 | 坏帧拦截在进入下一阶段之前，阻断"上游错、下游全错"的传播链 | 小（quality-check 已有，差产品化） |
| | ⑤ 关键镜头精修工作台（虾画折中形态） | 关键镜头多候选并排+参考拖拽+局部重绘，把"抽卡"变"选择" | 中 |
| **Q-B：内容正确性与节奏（间接作用于画面）** | ⑥ 解说剧产品线（AI 改写口播稿） | 口播稿节奏 ↔ 画面节拍对齐，解说剧成片观感的主导因素 | 小–中 |
| | ⑦ 手工镜头管理补齐 | 叙事完整性（插入反应镜头/过渡镜头） | 小 |
| | ⑧ 导入体检报告 | 上游文本正确性，章节断裂/乱码在源头拦截 | 小 |
| | ⑨ 画幅/模型集级统一 | 避免混合模型导致的风格跳变 | 小 |
| **Q-C：质量贡献低，工程价值另计** | 任务中心、项目归档、成本预估、Agent 快捷问法、ZIP 素材包 | 不直接提升画面，但关系生产可靠性与规模化管理（任务中心防"失败任务无人知晓→缺素材进成片"的间接质量风险） | 任务中心中，其余小 |

**排序依据**（第二节展开）：成片质量 = 资产稳定性 × 构图/空间控制 × 风格一致性 × 单帧质量门槛 × 内容正确性。Q-S 两项作用在"每帧都受益"的乘法项上，故居首。

## 二、排序框架：成片质量由哪些环节决定

把"视频输出质量"拆成可归因的五环，每个候选功能只在其作用的环节上得分：

| 环节 | 决定什么 | 失败表现（DramaClaw 手册 12.2 常见问题对应） |
|---|---|---|
| 1. 资产稳定性 | 每一帧的角色脸、服装、场景身份 | "角色长相不稳定"、"同一场景前后不一致" |
| 2. 构图/空间控制 | 站位、景别、正反打方向、镜头间空间连续 | 站位漂移、构图失控、人物出画 |
| 3. 风格一致性 | 跨镜头/跨集的色调、质感、画面语言 | 风格跳变、文字残留、水印 |
| 4. 单帧质量门槛 | 坏帧是否流入下一阶段 | "草图可用但首帧不对"、合成后才发现废镜头 |
| 5. 内容正确性 | 叙事完整、节奏、画面与文案对齐 | 剧情断裂、缺镜头、节奏拖沓 |

手册两条原则是这套框架的出处：

- 第四章顺序提醒："**前面的文案、角色、场景或首帧错了，后面的视频通常也会跟着错。**"（坏帧会沿流水线传播，所以 1/3/4 环的权重高于末端）
- 11.3："不要盲目反复抽卡；**先判断问题出在文案、草图、渲染图/首帧、音频还是视频提示词**。"（质量问题的可归因性本身就是产品质量）

本项目的质量链路现状：环节 3（风格锚点常量）和环节 4 的机器部分（`quality-check.service.ts` 四指标 + `stage-gate` + `StageGapBanner`）已有基础；**环节 2 几乎空白**（只有文字描述约束构图）；环节 1 有"设为主图"但无回滚护栏。这决定了 Q-S 两项的排序。

## 三、能力逐项对照

### 3.1 本项目整体架构（调查结论）

- 后端业务服务在 `src/core/platform/episode-production/`（平台层，PC/Web 双端共用），IPC 接线在 `src/core/packs/episode-production/`（175 个 `ep:*` channel）；前端在 `src/renderer/src/packs/episode-production/` + `views/Episode*.vue`。
- **六阶段流水线**：① 内容识别 → ② 资产盘点 → ③ 剧本编辑 → ④ 分镜 → ⑤ 画面+音频 → ⑥ 合成成片；状态机 7 态 `pending → asset_prep → scripting → storyboarding → producing → composing → completed`（`src/core/platform/episode-production/workflow/episode-status.machine.ts:23-52`），阶段门控 `workflow/stage-gate.service.ts`。
- **入口**：菜单"剧集制作"（`src/renderer/src/packs/episode-production/index.ts:85-94`），路由 `/episode-production` → `/all` → `/:projectId/creator` → `/:projectId/studio/:episodeId`；工作台 4 个 tab（剧本/资产/分镜/合成）+ 右侧 EpAgentPanel。
- **真实多模态生成**：图像（DashScope 通义万相/百炼/AI Hub/ComfyUI + OpenAI/火山 SDK）、视频（火山/百炼/ComfyUI/AI Hub，文生/图生/关键帧序列三模式）、TTS（DashScope + CosyVoice + 克隆音色）、本机 ffmpeg 合成 1080p MP4（字幕烧入/转场/混音）。
- 另有"AI 一键成片"快速通道（`quick-mode/orchestrator.service.ts`，一句话 → 7 步出片）。

### 3.3 本项目独有、DramaClaw 没有的（反向优势）

这些**不需要借鉴，反而是差异化卖点**：

1. **长文写作强联动**——大纲/章节直通剧集项目（`video_projects.long_writing_project_id`）、实体自动绑定（`auto-binding/episode-auto-binding.service.ts`）、新实体 AI 检测与临时实体模板复用（`lw_temp_character_templates` 等）；DramaClaw 的虾料是孤立导入。
2. **参考视频反向工程**——ffmpeg 抽帧+镜头检测+VLM 镜头推断→转分镜骨架（`reference-video/analysis.service.ts`、`vlm-shot-inferrer.ts`、`narrative/import-from-parsed-shots.service.ts`），DramaClaw 手册未见此能力。
3. **AI 一键成片**——`quick-mode/orchestrator.service.ts` 一句话 7 步出片，DramaClaw 需手动走主线。
4. **质量自检四指标**——关键帧引用覆盖率/字幕↔对白一致性/时长偏差/VLM 相似度（`services/quality-check.service.ts`）。
5. **平面布局图先行（floor_plan）**——根地点先生成俯视平面图作主图参考（`main-image-generator.service.ts:250`），是空间一致性的轻量实现，理念上接近"导演世界"的降级版。
6. **预设数字人 + 跨项目用户资产库**（`preset-digital-human.service.ts`、`user_assets` 表）。
7. **双端同构**（PC/Web 共用 platform 层，`src/web/server/api/register-channels.ts`）。
8. **电子书格式支持更广**（epub/mobi/azw3/pdf）。

## 四、值得借鉴的功能（按视频输出质量贡献重排）

> 每项标注：质量贡献机理（为什么排这个档位）→ 本项目现状证据 → 借鉴方案 → 工程成本。
> 与 v1 的"工程性价比"排序（P0/P1/P2）的对照见第五节。

### Q-S1 导演世界 L1 导演工作台（质量贡献最高）

**质量贡献机理**：作用于第二节环节 2（构图/空间控制），且是**视频生成前唯一的确定性控制手段**——现有手段（文字画面描述）对构图的约束力很弱。链路：空间+站位+机位固化为控制图 → 注入关键帧生成（i2i 参考）→ 首帧确定 → 图生视频强继承首帧。视频是单次成本最高的生成调用，首帧构图对，视频就对；这也是一集几十个镜头站位一致性的唯一可规模化方案（空间数据化：场景摆一次、多机位各导一张）。

**现状证据与分层结论**：详见附录 A。要点：DramaClaw 的"3GS"实质是可取景的 2.5D 代理片场（非真 3D 重建）；本项目 L1 地基大半现成——three.js 已在依赖（`package.json:124`）、`PanoramaViewer.vue` 已有 yaw/pitch/fov 取景+截图、角色 7 类视角派生图即 billboard 人物卡素材（`character-view-hints.ts:25-60`）、`floor_plan` 天然是俯视摆位画布（`main-image-generator.service.ts:250`）、`storyboard.backgroundRefImageId` 写回槽位已存在（`storyboard.entity.ts:179`）。

**借鉴方案**：L1 = three.js 场景（背景卡=场景主图或全景球）+ billboard 人物/道具卡 + 拖拽摆位 + 透视相机（对齐 `lens-presets`）+ 按景深合成导出控制图 → 写回 backgroundRef / 加入挑图参考。入口放在分镜卡/关键帧面板"导演取景"按钮，floor_plan 俯视摆位 + 透视预览双视图。

**实现关键点**：① 控制图与风格参考**必须分槽**（占位剪影的粗糙质感不能污染成片）；② 摆位数据程序化生成构图提示词（文字+控制图双通道约束）。**成本**：2–4 周前端为主，风险低。L2 深度代理（1–2 个月）视 A/B 数据决定；L3 真 3DGS **不做**。

### Q-S2 资产版本历史 + 候选/写回安全边界

**质量贡献机理**：作用于环节 1（资产稳定性）。资产是每一帧的输入——角色主图/身份图一旦被一次失败的重新生成覆盖且无法回滚，劣化是**全片性**的（比单镜头废片贵一个数量级）。DramaClaw 手册 12.2 排第二的常见问题就是"角色长相不稳定"，解法是"先统一虾塘角色资产"；6.1 的"历史"设计（多次生成后及时恢复/标记可用版本）就是为此兜底。9.9 写回设计的另一半价值是**影响范围提示**："角色/场景/道具是全局资产，写回影响多个镜头"——让用户在覆盖前知道爆炸半径。

**本项目现状**：`asset_image` 多行累积 + "设为主图"（`docs/manual/episode-production.md` §8.2）已构成**隐式版本历史**，这一半够用；缺：① 显式的历史浏览与"恢复/标记可用"操作；② 主图/关键帧替换前的影响范围提示（"该角色主图被 N 个分镜引用"）。

**借鉴方案**：画廊编辑器（`CharacterGalleryEditor.vue` / `LocationGalleryEditor.vue`）加"历史"分组（只差 UI）；替换操作加影响范围确认弹窗。**成本**：小改动，质量回报/成本比全表最高。

### Q-A3 风格模板库（含避免指令）

**质量贡献机理**：作用于环节 3（风格一致性）。连续剧的"跨集风格一致"是观众感知质量的显性维度；**避免指令（negative prompt）对文字残留、水印、多余肢体等 artifact 有直接压制作用**——这正是 DramaClaw 渲染图检查表（8.3.3）里"文字残留：画面中不应出现多余文字、水印"的治本手段。参考图反推风格参数则把"风格"从口头描述变成可复制的数据。

**本项目现状**：20 种内置风格锚点（`assets/constants/style-presets.ts:24-45`）+ 题材/年代/电影感注册表（`prompts/{genre-profiles,era-profiles,cinematic-registry}.ts`），提示词工程扎实，但用户**无法保存自己的风格组合**，无避免指令管理，无"参考图反推风格"。

**借鉴方案**：`ep_style_template` 表（项目级/用户级两层，字段对齐虾格：风格指令 + 避免指令 + 风格 Tag + 配置 JSON）；反推用现有 VLM 通道（质量自检/镜头推断已在用）。**成本**：中。

### Q-A4 阶段检查清单产品化

**质量贡献机理**：作用于环节 4（单帧质量门槛）。坏帧的价值损失在于**传播**："前面的文案、角色、场景或首帧错了，后面的视频通常也会跟着错"（手册第四章）。在每个阶段出口放一张可判定的检查表，把废片拦截在最便宜的位置。DramaClaw 8.3.3 的渲染图通过标准（角色脸一致/服装身份/场景/道具/文字残留/视频可用性）和 12.1 的分阶段检查表是现成的产品化蓝本。

**本项目现状**：机器部分已有（`quality-check.service.ts` 四指标 + `stage-gate` + `StageGapBanner` + 导出阻断），但**没有把"检查项+通过标准"作为显式 UI 呈现给用户**，人工检查靠用户自觉。

**借鉴方案**：把 DramaClaw 的分阶段检查表融入现有 StageGapBanner/质检服务，做成各 stage 出口的 checklist 卡片；渲染图检查项与"挑图"（`reference_overrides`）联动——不合格项一键重生。**成本**：小（检查逻辑大多已在，差产品化串联）。

### Q-A5 关键镜头精修工作台（虾画的折中形态）

**质量贡献机理**：作用于环节 2+4。批量镜头靠流水线，但一集总有若干关键镜头（情绪高点、动作戏、转场）决定成片观感上限；对这些镜头，"一次生成定生死"的抽卡模式质量方差极大。精修工作台（当前分镜上下文 + 多候选并排 + 参考图拖拽 + 局部重绘）把抽卡变成选择，是 DramaClaw 虾画 80% 高频用途（修单个镜头）的轻量替代。

**本项目现状**：关键帧已有多候选基础（参考板 + 挑图），但没有面向单镜头的并排候选比较与局部重绘入口。

**借鉴方案**：关键帧 stage 加"精修弹窗"；画布化（vue-flow 节点编辑器，workflow 包已有技术储备）留作长期选项。**成本**：中。

### Q-B6 解说剧产品线（AI 改写口播稿 + 项目类型 + 默认解说声线）

**质量贡献机理**：作用于环节 5（内容正确性/节奏）。解说剧成片观感的主导因素是**口播稿节奏与画面节拍的对齐**——DramaClaw 用"目标行数 + 每行字数范围"约束 AI 改写，保证每行解说对应可画的画面节拍。解说剧/小说推文同时是这个赛道量最大的市场，属"质量+商业"双收益。

**本项目现状**：`narration-synthesis.service.ts`（旁白合成）单点，无"解说剧"产品概念。

**借鉴方案**：① `video_projects` 加 `project_type`；② 剧本阶段加带行数/字数约束的口播稿改写（`script-generator` 前加一道 LLM 改写）；③ 项目级默认解说声线。三步都不动渲染管线。**成本**：小–中。

### Q-B7 手工镜头管理补齐

**质量贡献机理**：作用于环节 5。叙事完整性缺口（缺反应镜头、过渡镜头）直接拉低成片观感；AI 拆分镜不可能永远覆盖人工的叙事判断。DramaClaw 支持在任意 Beat 前后插入手工镜头、删除后编号重排。

**本项目现状**：分镜手工插入已实现（`narrative/storyboard-insert.ts`），差删除后编号重排的显式反馈等 UX 补齐。**成本**：小。

### Q-B8 导入体检报告

**质量贡献机理**：作用于环节 5 的最上游。章节断裂/乱码/章节识别错误会在分集和脚本阶段放大成叙事断裂（手册 5.2："导入前整理原文比导入后反复修正省时间"）。对画面的作用是间接的，故排 Q-B 而非 Q-A。

**本项目现状**：批量建集有章节识别，无导入后确认页。**借鉴方案**：`ep:analyze-script-file` 结果补字数/章节列表/预计集数，前端加导入预览确认。**成本**：小。

### Q-B9 画幅/模型集级统一设置

**质量贡献机理**：作用于环节 3 的次级项——同一集混用不同渲染模型/画幅会产生风格跳变；DramaClaw 的"切换只影响新生成资产"规则避免了已生成素材被静默污染。

**本项目现状**：模型选择分散在各生成面板，无集级统一。**成本**：小。

### Q-C 工程线（质量贡献低，但工程/生产价值仍在）

按工程价值排序，与质量线**并行推进**（见第五节）：

1. **任务中心**（对标虾条 10.3）——不直接提画面质量，但"失败任务无人知晓 → 缺素材进成片"是间接质量风险；且批量生产依赖它。**2026-10-13 复查修正**：`task-queue.service.ts` 全库无任何消费者（不可作为复用基础）；本项目已有的 `/agent-tasks` 是 agent 执行任务树（规划→批准→质量门，schema 为 parent/root/depth/budget，语义不匹配生成任务）；**全局通知中心**（`stores/notification.ts` + 顶栏铃铛 + `user_notification_reads` 表）是现成的全局 UI 载体，任务终态可推通知。因此任务中心应**定位为平台级生成任务中心**（新建 `src/core/platform/services/` 下通用任务登记服务 + 全局任务抽屉，EP 只是第一个接入方），而非 EP 私有模块。**工程性价比全表最高，v1 排 P0，维持早做。**
2. **项目归档**（对标 2.2）——批量生产的项目管理刚需，无质量贡献。`video_projects.status` 加 archived + 列表筛选排序。
3. **成本预估**（对标 2.4）——有 `ep:ai-usage-stats`，可加生成前 token/张数预估。
4. **Agent 快捷问法 chips**（对标 10.1）——"哪些资产缺失/哪集未就绪"预设问法有间接质量价值（早发现缺口），做成 `EpAgentPanel` 快捷 chips。
5. **ZIP 素材包导出**（对标 8.4）——后期交接用，无质量贡献。

## 附录 A：导演世界 / 3GS 专项分析（2026-10-13）

### A1 它解决什么问题

AI 视频废片三大根因：空间不连续（同一房间每镜头不一样、正反打穿帮）、站位/构图失控（人物出画、多人乱叠）、运镜失控（提示词可部分解决）。导演世界解决前两个，链路是：**空间+站位+机位在生成前固化为控制图 → 注入关键帧生成（i2i 参考）→ 首帧确定 → 图生视频强继承首帧**。视频模型对首帧的依赖是确定性的——首帧构图对，视频就对。

杠杆逻辑：视频是单次成本最高的生成调用，在最贵环节前加一道零边际成本的确定性控制，废片率下降直接省钱；且一集几十镜头都要站位一致，只有空间数据化（场景摆一次、多机位各导一张）能撑住批量生产。

### A2 DramaClaw "3GS" 的实现真相（从 UX 反推）

- "正面 3GS：基于**场景源图**建场；背面 3GS：补反打"——真多视图重建不需要用户手动生成背面图，说明底层是**图像代理**（分层深度/补洞）。
- "放置人物、道具或**占位**"——人物是卡片/占位剪影，非绑定 3D 角色。
- 手册自认"导演世界不负责最终肤色、服装材质、光照"，输出仅控制图。

结论：实质是"**可取景的 2.5D 代理片场**"，3D 只是取景器外壳。不需要真 3D 化即可拿到全部用户价值。

### A3 本项目 L1 地基（逐条已验证）

| 已有能力 | 证据 | 在导演世界中的角色 |
|---|---|---|
| three.js 已在依赖（0.179.1 + three-spritetext） | `package.json:124-125` | 3D 取景器技术栈零引入成本 |
| 全景取景器：yaw/pitch/fov 事件 + `captureCanvas()` 截图 | `shared/PanoramaViewer.vue:11-18,42` | "取景→导控制图"原型，全景球背景子集已做完 |
| 角色 7 类视角派生图（正面全身/半身、左右四分之三、左右侧身） | `assets/prompts/character-view-hints.ts:25-60` | billboard 人物卡的多角度素材（同一批数据） |
| floor_plan 平面布局图先行 | `main-image-generator.service.ts:250` | 天然"俯视摆位画布"，拖人/拖道具比 3D 空间摆位更符合导演直觉 |
| 分镜背景参考槽位 + set/get | `storyboard.entity.ts:179`、`storyboard.service.ts:105-119` | 控制图写回目标现成 |
| 关键帧参考板 + 用户挑图 | `keyframe-generation.service.ts:1478` | 控制图注入通道现成 |
| ComfyUI 局域网网关 | `providers/image`、`providers/video` | L2 深度估计可经 ComfyUI 节点跑 |
| 质量自检含 VLM 相似度 | `quality-check.service.ts` | 上线后可 A/B 验证收益 |

### A4 分层难度与路线

| 层级 | 做什么 | 工作量 | 风险 | 价值 |
|---|---|---|---|---|
| L1 导演工作台 | three.js 场景（背景卡/全景球、地面）+ billboard 人物/道具卡（视角派生图）+ 拖拽摆位 + 透视相机（对齐 `lens-presets`）+ 按景深合成导出控制图 → 写回 backgroundRef / 加入挑图参考 | 前端为主 2–4 周 MVP | 低 | ~80%（构图/站位/机位/正反打方向） |
| L2 深度代理 | 单图→深度（ComfyUI）→网格/点云，相机 ±20–30° 视差环游，遮挡区 i2i 补洞 | 1–2 个月 | 中（补洞质量） | 机位活动范围变大 |
| L3 真 3DGS | 多视角一致图生成→splat 训练→Web 实时渲染 | 3 个月+，GPU 成本高 | 高 | 相对 L2 增量有限，**不做** |
| L4 导入 glTF | three.js 原生支持 | 天 | 低 | L1 免费扩展项 |

难的不是"3D 化"，是"重建"；价值主体 L1 本质是"带透视相机的排版工具"。

### A5 价值兑现的两个关键点

1. **控制图与风格参考分槽**：控制图是构图参考不是风格参考，混槽会把占位图粗糙质感带进成片；注入时提示词需明确其地位并控制权重。
2. **摆位数据程序化生成构图提示词**："中景、女主画面左侧背对镜头、男主右侧面向镜头、俯角 15°"应由摆位数据自动写入画面描述，文字+控制图双通道约束；`lens-presets`/`camera-movements` 常量直接复用。

验证方式：同一组分镜开/关控制图 A/B，用 `quality-check` VLM 相似度 + 人工废片率对比，数据支撑再投 L2。

### A6 前置接线与风险

- 关键帧生成侧目前未直接消费 `backgroundRefImageId`（仅 set/get），需在挑图/参考板合成时接通。
- 双端 WebGL 已有 PanoramaViewer `preserveDrawingBuffer` 先例，Electron/Web 兼容风险可控。

| 任务中心（Q-C1） | M+ | **平台级 18–22 人日（4–5 周）；EP-only 简版 12–15 人日** | **复查修正**：`task-queue.service` 全库无消费者（不可复用）；`/agent-tasks` 是 agent 执行任务树（parent/root/depth/budget，语义不匹配生成任务，不扩展）；全局通知中心（`stores/notification.ts`）可复用为终态通知载体 | 定位改为平台级基建后置实施；取消能力按 provider 参差降级 |

**合计**：全部 13 项 ≈ **85–125 人日（约 4.5–6.5 人月）**；两期路线（见第七节）第一期约 26–38 人日，第二期约 37–54 人日，多人并行可按人数折算。

### B2 大项拆解

**导演工作台 L1（MVP 15–20 人日）**：
1. 数据模型：摆位/机位状态挂 `location_bindings` 扩展或新表 + 迁移（2–3d）
2. three.js 场景：背景卡（场景主图）+ 地面 + billboard 人物/道具卡（视角派生图）+ `three-spritetext` 名称标签（5–7d）
3. 交互：拖拽摆位/缩放/朝向；双视图 = 同一场景的正交俯视相机（对齐 floor_plan）+ 透视预览相机（5–7d）
4. 相机系统：FOV/高度/角度，焦段对齐 `lens-presets`（2–3d）
5. 合成导出：`preserveDrawingBuffer` 截图 → 控制图（PanoramaViewer 同款方案，2d）
6. 写回链路：写 `backgroundRefImageId` + 关键帧参考板接通消费（3–4d）
7. 构图提示词程序化生成：摆位数据 → 画面描述注入（2–3d）
完整版增量：全景球背景（复用 PanoramaViewer 思路）+5d、多机位保存/切换 +3d、道具占位细化 +2–3d。

**任务中心（15–20 人日）**：`ep_task` 表+迁移（1–2d）→ 关键帧/视频/TTS/合成四类链路埋点（5–6d）→ 任务抽屉 UI：状态/进度/日志/跳转（4–5d）→ 取消/重试（按 provider 能力降级，3–5d）→ 清除已完成/筛选（1–2d）。

**精修工作台（MVP 8–12 人日）**：精修弹窗宿主（2–3d）→ 同参考多候选并行生成与并排比较（2–3d）→ 参考图拖拽编排（复用 `AssetGalleryPicker`，2d）→ 写回挑图/关键帧（2d）。二期局部重绘：前端遮罩画笔（3–4d）+ ComfyUI inpaint 通道（3–5d）或支持 mask 参数的云 provider。

**风格模板库（8–12 人日）**：`ep_style_template` 表+迁移（1d）→ CRUD IPC（1–2d）→ UI：列表/结构化编辑/应用到项目（3–4d）→ 注入点改造：主图/派生图/关键帧三处 prompt 组装读项目模板，负向指令接通既有 `negativePrompt` 通道（2d）→ 参考图反推（VLM 一次调用+解析，1–2d）。

### B3 依赖与排程建议

1. **任务中心后置但接口先行**（2026-10-13 修订，取代原"任务中心最先做"）：复查确认 `task-queue.service` 无消费者、`agent_tasks` 语义不匹配，任务中心改为平台级基建后置；第三批（精修/导演台）开工前先定 task registry 接口（登记/进度/终态/跳转）并按其埋点，后置上线即接入，避免二次返工。
2. **风格模板库先于导演工作台**：控制图"与风格参考分槽"（附录 A5）依赖模板层的参考分槽概念先就位。
3. **精修工作台与导演工作台共享"候选-写回"组件**，无论先后，第二个复用第一个的组件可省 2–3 人日。
4. 导演工作台上线即跑 A/B（`quality-check` VLM 相似度），数据支撑再投 L2。
5. 上述估算不含提示词调优的收敛周期（口播稿改写、构图提示词生成各预留 2–3 轮迭代，已计入）。

### B4 任务中心专项复查结论（2026-10-13）

用户提问"任务中心是否应该是系统全局的"，复查结果：**是，且本项目已有类似但语义不同的功能**——

| 已有系统 | 位置 | 语义 | 与生成任务中心的关系 |
|---|---|---|---|
| Agent 任务树（`/agent-tasks`） | workflow 包，`agent_tasks` 表（parent_id/root_id/depth/budget_json/quality_score/executor/run_id） | AI 长程任务分解：规划→人工批准→逐任务质量门 | **语义不匹配**：是"执行计划树"不是"生成任务列表"，不扩展此表 |
| 通知中心 | `stores/notification.ts` + 顶栏铃铛 + `user_notification_reads` 表，全局跨包 | 未读/已读、分页、持久化 | **可复用**：任务终态（完成/失败）推送为通知；但没有进行中状态/进度/取消语义，不能替代任务中心 |
| 采集任务（ic_task） | info-collection 包，自带 store | 采集流程任务 | 又一个独立任务系统，佐证"全局生成任务层缺失" |
| `task-queue.service.ts` | `src/core/platform/services/` | 通用队列（并发/优先级/重试/超时） | **全库无任何消费者**（已核实），不可当作现成地基，仅可参考其接口设计 |

结论：本项目缺的不是"任务视图"，而是**平台层的生成任务登记协议 + 一个全局任务抽屉 UI**。正确做法是建在 `src/core/platform/services/`（task_type 可扩展），EP 只是第一个接入方，后续对话生图（`stores/image.ts`）、采集等可逐步收编；UI 复用通知中心的顶栏入口模式。
