# 长文图谱·流程化抽取工作流 详细设计

- 日期：2026-10-15
- 范围：长文写作（longwriting）图谱数据链路——实体/事件/关系/状态切片的提取、校验、补全、治理
- 数据佐证：天下女捕项目（`lw_1790041065151_pvxgkkff1`，44 章 / 13.7 万字）实测
- 关联：52 号图谱提取链路修复、44 号关系演变、49 号一致性 R7/R8、54 号复测 R10

---

## 1. 背景与现状

### 1.1 现状实现（图谱数据是怎么来的）

图谱数据在**章节保存/生成时同步**产出，入口两处，都调用同一个流水线：

- 章节写作完成：`chapter-writing-executor.ts:362`
- 手动触发（GRAPH_EXTRACT_CHAPTER）：`longwriting.handler.ts:3379`

流水线 `ChapterGraphProcessor.process()`（`chapter-graph.processor.ts`）步骤：

| 步骤 | 内容 | AI 调用 | 产物落库 |
|---|---|---|---|
| 0a | 内容 hash 短路（同内容不重跑） | 0 | — |
| 0b | 新实体检测入册（LwEntityDetectionService） | 1 | lw_story_characters / locations / items |
| 1 | 事件提取（2-6 个）→ 名称→ID 解析 → 共现补挂 | 1-2 | lw_events（involved_entities JSON） |
| 1.5 | 伏笔提取 | 1 | lw_foreshadows |
| 2 | 实体状态切片 | 1-2 | lw_entity_state_snapshots |
| 3 | 自动建边（已废弃，involves 边由事件 JSON 推导） | 0 | — |
| 3.5 | 人物关系**演变**提取（结婚/决裂，关旧开新） | 1 | lw_graph_edges |
| 4 | 章节状态摘要 | 1-2 | lw_chapter_state_summaries |

图谱组装（`graph.service.ts getGraph`）：节点 = 五类实体表 union + 事件表；边 = 事件 `involved_entities` 推导的 involves 边 + `lw_graph_edges` 语义边。写后另有一致性检查 R1-R11（`consistency.service.ts`）。

### 1.2 实测问题（天下女捕）

- 67 人物中 **33 个孤立**（无任何边），其中：
  - **~12 个是假人名**：张纸(正文 27 次)、白天(13)、朱笔(12)、何时(7)、张贴、钱在、方向压、金纹、水上张、沈家（家族指称）等——正则误报/AI 过度提取后转正，永不会被事件/关系挂上；
  - **~8 个真实龙套断链**：许三、周婆子、陈绣娘、老冯掌柜等正文出现 4-11 次但 0 事件挂载、0 关系边；
  - **~6 个未登场预设**（昭平帝、贾掌柜等）：正文 0 次，属正常暂时孤立。
- **技能 5/5 全孤立**：事件提取名册参考不含技能、关系演变只做人物↔人物——技能在自动管线中**没有任何建边路径**。
- 语义边仅 63 条，只触达 23/67 人物；静态基础关系（同僚/亲属/隶属）只有手动"图谱关系构建"才产。
- **20 个事件含 22 处悬空引用**（指向已删除实体：县太爷、说书人、雪狸猫……）。
- 每章事件数长期顶在 prompt 预算上限（4-6 个，44 章均值 ~5.4）。

### 1.3 为什么单次 LLM 调用必然不完整（结构性论据）

1. **输出预算封顶**：事件提取 prompt 限"2-6 个"、总字数 ≤2000（maxTokens 2048）。多人章的次要人物事件被预算挤掉——这是**设计上限**，不是偶发。
2. **一遍定稿无纠错**：每个步骤单次调用直接落库，抽漏了没有第二遍补，抽错了没有门禁拦。
3. **无提及基线**：系统不知道"正文到底出现了谁"（只有 R9 正则粗扫），因此无法度量"漏了多少"，更无法定向补。
4. **全局结构无人负责**：实体消歧（别名/简称/称谓）、跨章关系网络、孤立节点治理，没有任何周期性全局步骤。
5. **噪声与事实同权入库**：假人名与真实实体走同一条入册路径，无"人名资格"校验。

结论：**把"一次抽全"改为"多遍抽取、逐层收敛、每层带质检"**——即抽丝剥茧式工作流。

## 2. 设计目标与原则

### 目标

| 指标 | 现状（天下女捕） | 目标 |
|---|---|---|
| 名册人物挂载率（≥1 边） | 51% | ≥85%（未登场预设除外） |
| 主角/重要人物章级覆盖（出场即有事件+切片） | 无度量 | 100%，违反即告警 |
| 假人名入库 | ~12 个 | 0（入库前拦截） |
| 悬空引用 | 22 处 | 0（删除即清理 + 定期体检） |
| 技能/势力建边路径 | 无 | 有（事件名册纳入 + 关系发现） |
| 图谱健康度可见性 | 无 | 每章产出健康分 + 问题台账 |

### 原则

1. **素材与定稿分离**：正文提及（mentions）、人名候选是素材层；名册、事件、边是定稿层。素材允许糙，定稿必须过门禁。
2. **先候选后入库**：一切自动入库的 LLM 产物（实体/边/切片）先进候选态或带 `origin` 溯源，可按来源批量回滚。
3. **规则优先，LLM 兜底**：能用确定性规则校验的（引用完整性、自环、黑名单）不花 token；LLM 只做规则做不了的语义判定（是否人名、是否同一实体、是否漏主事件）。
4. **LLM 产物必须正文锚定**：关系、切片、审计结论都要求给出正文原句依据（伏笔提取已有此纪律，推广到全链路）；给不出依据的条目丢弃。
5. **警告与阻断分离**：质量问题进问题台账（lw_graph_issues），只有"数据坏了"（引用悬空、解析失败）才记 failedSteps 触发重跑；风格/完整类问题告警不阻断。
6. **自动修复与人工确认分离**：补挂边、清理噪声实体默认可自动执行但可撤销（软删/墓志）；合并实体、删除他人建的边必须人工确认。
7. **幂等可重跑**：所有步骤保持现失败的 failedSteps + 内容 hash 语义（全成功才记 hash），jobs 化后支持断点续跑。

## 3. 总体架构：六层流水线

```
                      ┌─────────────────────────────────────────────┐
                      │            L6 编排层（任务队列/预算/进度）      │
                      └──────────────┬──────────────────────────────┘
   章节保存/生成 ──► 入队 ────────────┤
                                     ▼
 L1 章节素材层（每章，异步）
   A1 提及扫描（正则+人名候选）→ lw_entity_mentions
   A2 事件提取（现有，主线 2-6）→ 候选事件 → 解析挂载
   A3 关系演变提取（现有）
   A4 状态切片（现有）+ 章节摘要（现有）
   A5 伏笔（现有）
                                     ▼
 L2 实体定稿层
   B1 人名判定器 NameGate：规则层 → LLM 批量复核 → 存疑进人工队列
   B2 实体解析：mention/候选 → canonical 实体（别名/归一/唯一包含，扩展现有 findByName）
   B3 悬空引用修复：事件/边指向已删实体 → 按名重解析或清引用
                                     ▼
 L3 挂链补全层
   C1 定向补漏第二遍：对"本章出现但 0 挂载"的名册实体定向问询
   C2 共现弱挂载：纯背景提及挂同章事件（标记背景级 involves）
   C3 静态关系发现：新实体入册后抽"同僚/亲属/隶属"等静态边（不止变化）
   C4 技能/势力纳入：事件提取名册参考补 skills/factions
                                     ▼
 L4 质检层（每章）
   V1-V9 规则校验器（确定性门禁，零 token）
   H 图谱健康分（挂载率/主角覆盖/噪声率/悬空率 → 面板展示）
   J LLM 抽样审计（judge）：正文 vs 产物对账 → 问题台账（不直接改库）
                                     ▼
 L5 全局整理层（每 N 章周期 / 手动触发）
   E1 连通性分析：孤立节点/子图分类 → 未登场(等) / 断链(补) / 噪声(清)
   E2 关系网络重推：全量名册 + 近 K 章正文 → 静态关系 diff 幂等落库
   E3 噪声清扫：假人名/零提及实体 → 墓志（可恢复）
   E4 重复合并：别名/简称/称谓簇 → LLM 判定同人 → 人工确认合并
```

## 4. 数据模型变更

### 4.1 新增 `lw_entity_mentions`（提及索引，完整性度量与补漏的基石）

```
id, project_id, chapter_number, outline_id
entity_type      -- character|location|item|faction|skill|null(未解析候选)
entity_id        -- 可空：解析失败=候选提及
mention_text     -- 原文名（含称谓变体原文）
anchor_excerpt   -- 首个出现句摘录（≤50 字，供人工确认与审计锚定）
mention_count    -- 本章出现次数
kind             -- roster(名册命中) | candidate(新人名候选) | alias(别名命中)
resolved         -- 0|1
created_at, updated_at
UNIQUE(project_id, chapter_number, mention_text, entity_type)
```

索引：`(project_id, chapter_number)`、`(project_id, entity_id)`。
重跑幂等：按章删除重建（与事件同策略）。

### 4.2 新增 `lw_graph_issues`（问题台账）

```
id, project_id, chapter_number
rule_id          -- V1..V9 / J(audit) / E(consolidation)
severity         -- error(阻断重跑) | warn(告警) | info
entity_type, entity_id, event_id, edge_id   -- 定位（可空）
message          -- 人读描述
evidence         -- JSON：正文摘录/引用目标等锚定证据
status           -- open | fixed | acked(知情保留) | dismissed
created_at, resolved_at
```

替代现在散落在 console.error 里的质量问题；复用冲突疑点的 ack 语义（`conflict-gate` 的登记保留先例）。

### 4.3 新增 `lw_graph_jobs`（流水线作业，断点续跑）

```
id, project_id, chapter_number, type   -- chapter_pipeline | consolidation
status           -- pending | running | done | failed | cancelled
step_status      -- JSON: { extract_events: done, name_gate: failed, ... }
attempts, last_error, token_cost
content_hash     -- 复用现有短路语义，落库防重启丢失（现状是进程级 Map）
created_at, updated_at
```

现 `ChapterGraphProcessor.contentHashes` 是进程级 Map（重启即失），迁到本表。

### 4.4 现有表扩展（最小化）

- `lw_graph_edges`：加 `strength`（normal | weak 共现弱边），不加新表；
- `lw_events.involved_entities`：条目加 `role`（main | background）标记背景提及挂载；
- 实体表：沿用 `importance`，NameGate 拦截的噪声不入册（无字段变更）。

## 5. 各层详细设计

### L1 章节素材层

**A1 提及扫描（新增，零/低 token）**

- 输入：本章正文 + 当前名册（五类实体名 + aliases）。
- 两段：
  1. 名册命中（确定性）：直接文本 includes + 句级锚定 → `kind=roster`；
  2. 新人名候选：复用 `scanNameCandidates`（姓氏+动词前瞻正则，consistency.service.ts:89）产出候选 → `kind=candidate`（**不再直接入队/入册**，定稿交给 L2 NameGate）。
- 副产物：R9 队列数据源从"正则即入队"改为"NameGate 通过才入队"。

**A2 事件提取（改造现有）**

- 主线事件提取保留现 prompt 骨架，三处强化：
  1. 输出预算上限从"总字数 2000"放宽为"事件数 2-8，超出时优先保证主角事件完整"；
  2. `involvedEntities` 的名册参考**补齐 skills**（现缺，技能建边死角根因）；
  3. 要求每个事件给出 `evidence`（正文原句 ≤20 字），解析时校验：原句不存在于正文 → 该事件记 issues（J 规则），不落库。
- 解析失败的实体仍走 `resolveEventEntities` + 共现补挂（现有逻辑），但补挂结果标 `role=background`。

**A3/A4/A5**（关系演变、状态切片、伏笔、摘要）：沿用现有，仅两点调整——
- 状态切片输入实体清单改由 A1 mentions 的 roster 命中驱动（替代现 `collectInvolvedEntities` 的三路并集），命中数超 40 时按 importance 排序截断；
- 关系演变产物同样要求 `description` 引用正文原句。

### L2 实体定稿层（核心新增）

**B1 人名判定器 NameGate**（新服务 `graph/name-gate.service.ts`）

三级流水，候选必须逐级通过才可入册/入队：

- **G0 规则层（零 token，硬拦截）**：
  - 时间/疑问/方位词类：`何时|白天|夜里|当时|此刻|方才|顿时|随即|怎么|为何…`（可维护常量表）；
  - 量词搭配残片：候选首字为量词性用法（`一张纸→张纸`）——规则：候选在正文中的全部出现语境里，若 ≥60% 前邻字符 ∈ `一|半|几|这|那|张|个|条`，判非人名；
  - 器物/概念词表 + 词性启发（朱笔/金纹）；
  - 家族指称：扩展现有 `isFamilyReferenceName`（X家）→ `X家(二|三)?(公子|小姐|老爷|夫人)`；
  - 泛称表：沿用 `NAME_SCAN_STOPWORDS` 并入本层；
  - 名册/别名/子串命中（现有 isKnown 逻辑）→ 直接过（`kind=roster`）。
- **G1 LLM 批量复核（低档模型，50 候选/批）**：输入候选 + 各自 `anchor_excerpt`（±1 句），输出三态 `person|not_person|uncertain` + 理由（一句话）。`not_person` 丢弃并记 issues（info）；`uncertain` 进未登记人物队列人工确认。
- **G2 人工确认**：沿用现有"未登记人物"队列 UI 与一键转正（lw_custom_entities, kindKey=未登记人物），转正动作写 `origin=manual`。

成本：每章新增候选通常 <20 个，G1 每 2-3 章触发一次批量调用。

**B2 实体解析（强化现有 `findByName` → 独立 `EntityResolutionService`）**

- 保留 精确→别名→归一化→唯一包含 四级；
- 新增**称谓映射表**：`魏大人→魏宗简`（现 isKnown 有同姓+称谓豁免，反向解析缺失）——解析失败时尝试 `姓+称谓后缀` 反查名册；
- 新增**合并建议**（供 L5-E4 用）：归一化/编辑距离聚簇 + 同章共现特征 → 疑似同人簇 → LLM 判定 → 人工确认合并（合并 = 迁移 mentions/events/edges 引用 + 旧实体入墓志，purge 级联已有）。

**B3 悬空引用修复（新增，随章跑 + 体检跑）**

- 扫描 lw_events.involved_entities / lw_graph_edges 端点，ID 不在名册 → 按名字重解析（走 B2）；
- 重解析失败 → 清除该引用 + issues(warn, V1)；
- 根治：实体删除路径统一接 purge 级联清引用（purge.service 已有实体级 purgeEntityData，补"事件 JSON 引用清理"步）。

### L3 挂链补全层

**C1 定向补漏第二遍（新增 AI 调用，每章至多 1 次）**

- 触发条件：mentions.roster 命中中存在"本章出现 ≥2 次且 0 事件挂载"的名册实体（主角/secondary 优先）。
- 输入：这些实体名单 + 各自 anchor 句 + 本章已有事件摘要。
- 输出二选一：`补一个事件`（走与 A2 相同格式与锚定校验）或 `标记纯背景提及`（落 involved 无需事件，仅写 mentions.resolved=background）。
- **宁缺毋滥**：明确指示"没有可提取的事件就标背景，禁止编造"；产物同样过 V 规则校验。

**C2 共现弱挂载（零 token）**

- 纯背景提及自动挂到**同章共现密度最高**的事件上，边标 `strength=weak`、`role=background`；
- 图谱前端弱边虚线渲染（GraphView 已有边样式体系，加一类样式）；
- 目的：让龙套在图上"可达"，同时不污染主事件结构。

**C3 静态关系发现（新增 AI 调用，新实体入册章触发）**

- 输入：本章新入册实体 + 本章正文相关句 + 现有边清单（幂等参考）；
- 输出：静态关系提案（师徒/同僚/亲属/隶属/邻里…），走 `syncEntityRelations` 幂等落库（去重键已内建，graph.service.ts:307）；
- 与 3.5 关系**演变**互补：演变抓动态，本步抓设定层静态。

**C4 技能/势力纳入（改 prompt 即可，P0）**

- A2 事件提取名册参考补 skills（factions 已有）；
- 关系演变 prompt 的 sourceType/targetType 放开 faction/skill（现硬编码 character↔character）。

### L4 质检层

**规则校验器 V1-V9（新服务 `graph/graph-qa.service.ts`，确定性，每章必跑）**

| 规则 | 内容 | 级别 |
|---|---|---|
| V1 引用完整性 | 事件 involved_entities / 边端点 ID 必须存在 | error |
| V2 人名合法性 | 名册 character 名命中 NameGate G0 黑名单类 | warn（存量）/ error（新增即拦） |
| V3 挂载完整性 | mentions 出现 ≥2 次的名册实体本章 0 挂载且未标背景 | warn |
| V4 主角强制 | importance=primary/secondary 出场章必须有 ≥1 事件挂载 + 最新切片 | error |
| V5 时间线合法 | 边 valid_from ≤ valid_until；事件 storyTime 非空时与章节序单调性抽检 | warn |
| V6 拓扑健康 | 自环边、完全重复边、孤事件（0 有效挂载） | error |
| V7 切片锚定 | 状态切片 stateSummary 的实体名必须在正文出现（防张冠李戴） | error |
| V8 事件规模 | 每章事件数 <2 或 >12 | warn |
| V9 孤立分类账 | 新增孤立实体按 L5-E1 三分类落 issues | info |

- error → 记 issues + failedSteps（重跑语义不变）；warn/info → 仅台账。
- 全量校验同时在项目级提供 `runHealthCheck(projectId)` 入口（设定集/图谱页手动触发）。

**健康分 H（Graph Health Score）**

```
score = 100
  - 40 × (1 - 人物挂载率)          // 未登场预设从分母剔除
  - 20 × (1 - 主角覆盖率)
  - 20 × min(1, 假人名数/名册人物数 × 5)
  - 10 × min(1, 悬空引用数/10)
  - 10 × min(1, open issues 数/20)
```

展示：GraphView 顶部状态条 + 每章流水线结果（ChapterGraphProcessResult 加 `health` 字段）+ 设定集概览。

**J LLM 抽样审计（judge，新增，低成本档）**

- 触发：每章流水线末尾；输入：正文 + 事件/切片产物 JSON（紧凑格式）；
- 输出固定 schema 的对账清单：`漏报的主事件（给正文原句）/ 事件挂载漏人 / 切片与正文矛盾 / 其他`；
- 产物只写 lw_graph_issues（rule_id=J），**不直接改库**；其中"挂载漏人"类 issue 可由 C1 消费自动补抽；
- 防幻觉回路：judge 与提取用不同调用（不同 seed/温度），且 judge 结论同样要求正文锚定——judge 给不出原句的指控自动 dismissed。

### L5 全局整理层（每 5 章自动 / 图谱页手动）

**E1 连通性分析**：getGraph 数据上跑连通分量 → 对孤立节点打三分类标签（未登场=mentions 全为 0；断链=mentions>0 但无边；噪声=NameGate 应拦未拦）→ 分类结果回写 issues（V9）。
**E2 关系网络重推**：升级现有 `generateEntityRelations`（longwriting-ai.service.ts:3960 附近）——名册参考扩到 skills、输入注入近 5 章 mentions 摘要做证据、输出走 syncEntityRelations 幂等落库。
**E3 噪声清扫**：候选=NameGate 复判 not_person + 正文 0 提及 + 无边 → 移入"已删除人物墓志"（lw_custom_entities 现有 kind，23 条先例），可一键恢复。
**E4 重复合并**：B2 的合并建议簇 → 人工确认 → 引用迁移合并。

### L6 编排层

- **触发**：两处现有入口（executor:362 / handler:3379）改为**入队即返回**，前端经现有 IPC 事件收进度（流水线结果不再阻塞保存/生成路径；写作完成的 postCheck 报告改为订阅 job 完成事件）。
- **队列**：复用 `task-queue.service.ts`（并发/优先级/重试已具备）+ lw_graph_jobs 落库（进程重启后 pending/failed 可恢复；单项目内章序串行——章间有状态依赖，跨项目并行）。
- **断点续跑**：step_status 逐步记录，失败步从断点续（现 failedSteps 语义 jobs 化）。
- **预算**：每章流水线 token 上限（默认 8 次 AI 调用），超限记 issues 并停止非关键步（V 校验与落库永远执行）；NameGate G1 与 judge 走低档模型（providerConfig 支持按步指定 modelId，现 stage 模型机制可复用）。
- **幂等**：content hash 落库（4.3）；每步独立提交语义保留。

## 9. 风险与取舍

1. **补漏遍编造小事件**：靠"宁缺毋滥 + 背景标记 + evidence 锚定 + V 校验"四重约束；宁可标背景不硬造事件。
2. **NameGate 误杀真人名**：G0 只拦高置信黑名单类；边界情况全部导向 G1/人工；拦截动作记 issues 可回溯。
3. **异步化改造面**：写作完成路径的 postCheck 报告依赖流水线结果——P1 用 job 完成事件衔接，过渡期保留同步开关（配置项）。
4. **judge 双幻觉**：judge 结论必须正文锚定，无原句指控自动丢弃；judge 不改库只记台账。
5. **存量数据治理**：天下女捕等既有项目的 33 孤立/22 悬空靠 P0 一次性脚本 + P2 体检收敛，不做运行时自动大清洗。
