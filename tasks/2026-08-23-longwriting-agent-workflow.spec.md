# 长文写作「对话式工作流」设计方案 v1

> 状态：待评审
> 日期：2026-08-23
> 背景：用户反馈现有"向导"（步骤条 + 分步表单）与"高级模式"（7 阶段平铺）本质区别不大，都不是期望的形态。
> 期望：**只有一个对话框（类似 agent），通过与 AI 的对话逐步完成长文创作；生成的内容按长文写作的数据结构落库并逐步展示（生成人物就显示人物，生成世界设定就显示世界设定……）；流程由工作流驱动，而非 UI 固定步骤。**

---

## 1. 背景与问题重述

### 1.1 现状

| 形态 | 流程控制者 | 交互 | 问题 |
|---|---|---|---|
| 高级模式（7 阶段平铺） | 用户手动点阶段 | 表单 + 生成按钮 | 用户要自己知道该做什么；AI 只是"生成器"，不是"协作者" |
| 向导（步骤条） | UI 写死顺序 idea→characters→world→plot→outline→chapters | 分步表单 + 上一步/下一步 | 流程固定，与用户实际创作节奏脱节；本质上还是"表单的另一种排列" |
| 图谱/一致性服务（已建） | — | 数据层 | 是工作流的地基，但本身不驱动流程 |

### 1.2 用户诉求提炼

1. **一个对话框**：交互入口只有对话，像和一位写作顾问聊天。
2. **AI 逐步引导完成**：从"我有一个想法"到"写完全部章节"，AI 在对话中推进，用户随时插话、改方向。
3. **内容实时落库 + 逐步显示**：生成的人物/世界/故事线/大纲/章节按现有数据结构（lw_story_characters、lw_backgrounds、lw_plots、lw_outlines、lw_chapters…）保存，并**在界面上实时可见**——"生成了人物，界面上就有人物"。
4. **一个界面显示不完**：全部数据需要精心设计布局（对话 + 分区数据面板）。
5. **工作流驱动**：流程不写死在 UI，由"工作流"这一层驱动。

---

## 2. 什么是「工作流驱动」—— 深度思考

### 2.1 为什么之前做成了"步骤条"？

"工作流"这个词容易让人误解为"步骤序列 + 进度条"。我把向导做成了固定步骤条，本质是**把流程硬编码在 UI 里**：
- UI 规定顺序，用户只能按顺序走；
- "完成判定"只是数据非空，流程本身没有参与决策；
- AI 只在每个步骤内被动生成，不知道整体走到哪、下一步该做什么。

这不是工作流驱动，这是**表单驱动**。向导和高级模式的差异只是"表单的排版方式"。

### 2.2 长文写作的本质：为什么适合工作流驱动

长文写作是一个**长周期、多产物、强依赖、弹性顺序**的生产过程：

- **多产物**：故事概要、人物、世界设定、故事线、大纲、章节正文——每一类都是独立的、有结构的数据。
- **强依赖**：大纲引用人物/故事线，章节挂在大纲节点下，章节正文受"当前时间点实体状态"约束（已建的图谱/状态切片/一致性服务就是为了这个）。无依赖约束地生成，产物必然互相矛盾。
- **弹性顺序**：作者不按固定顺序创作。可能先有高潮场景再补人物，可能边写边补世界观，可能推翻重来。固定顺序对创作是枷锁。
- **迭代性**：生成 → 审视 → 修改 → 再生成，不是线性一次过。
- **决策依赖上下文**："下一步做什么"取决于"现在已有什么"，这正是 AI 擅长的判断。

### 2.3 工作流驱动的正确定义

> **工作流 = 数据依赖规则 + 项目生产状态；流程由 AI 在依赖约束内自主推进；用户通过对话随时干预。**

具体拆解为三层：

```
┌─────────────────────────────────────────────────┐
│  对话层（交互外壳）                                │
│  用户 ↔ AI，一切指令/反馈/修改都通过对话表达         │
├─────────────────────────────────────────────────┤
│  Agent 层（决策内核）                             │
│  读懂用户意图 → 决定执行哪些"生产动作" → 执行 → 汇报 │
├─────────────────────────────────────────────────┤
│  工作流引擎（数据内核）                            │
│  ① 依赖规则（写死最小前置条件，不写死顺序）          │
│  ② 生产状态（从数据库实时计算：已有什么、缺什么）     │
│  ③ 动作执行（调用现有生成方法 → 落库 → 更新状态）    │
└─────────────────────────────────────────────────┘
```

关键结论（与步骤条的本质区别）：

| 维度 | 步骤条向导（错误理解） | 工作流驱动（正解） |
|---|---|---|
| 顺序 | UI 硬编码 | 引擎只约束**依赖**，顺序由 AI 按对话推进 |
| 下一步 | 用户点"下一步" | AI 判断（结合依赖规则与用户意图） |
| 用户干预 | 只能在当前步骤内 | 任何时刻可以插话、改方向、重来 |
| 状态 | 步骤 index + 数据非空 | 数据依赖 + 生产状态实时计算 |
| 产物展示 | 每步一个表单 | 对话中内嵌预览 + 常驻数据面板 |
| 失败处理 | 卡在当前步骤 | AI 解释原因并给替代路径 |

### 2.4 为什么不用"纯自由对话"（无工作流层）？

如果只是把长文写作做成一个自由聊天机器人，AI 说什么就只显示什么，会有三个致命问题：

1. **数据无法结构化落库**：AI 聊出来的"人物设定"停留在对话文本里，无法进入 lw_story_characters，后续大纲/章节/图谱/一致性校验都用不上它——等于每次写作都从零开始，且无法支撑几十章的长篇一致性。
2. **无法保证数据依赖**：没有引擎把关，AI 可能在没有大纲的情况下"写"章节，或者生成与已有设定矛盾的内容。
3. **无法复用现有资产**：图谱、实体状态切片、一致性扫描、向量记忆——这些已经建好的能力全部依赖结构化数据。没有工作流层，它们全部失效。

所以正确形态是：**对话是壳，工作流是核**。AI 在对话中"执行动作"，动作落库成结构化数据，数据反过来成为后续对话的上下文。这正是"工作流驱动"的完整闭环。

## 3. 总体架构

### 3.1 Agent 循环（每轮用户消息）

```
用户发消息
  │
  ▼
① 组装上下文
   · 项目数据摘要（各实体数量 + 关键信息，非全文）
   · 对话历史（最近 N 条）
   · 生产状态（已有什么 / 缺什么 / 依赖提示）
  │
  ▼
② AI 决策调用（非流式，短 JSON）
   → { reply: 简短回应, actions: [ {type, params} ] }
   · actions 为空 = 本轮只是问答/闲聊/建议
  │
  ▼
③ 顺序执行 actions（引擎逐条处理）
   · 校验依赖 → 调用现有生成方法（流式）→ 解析 → 落库
   · 每个动作产生执行摘要（如"新增角色：苏婉儿（女二号）"）
   · 中途失败不中断后续动作，错误进入摘要
  │
  ▼
④ AI 总结调用（流式，展示给用户）
   输入 = 动作执行摘要 + 更新后的生产状态
   输出 = 自然语言回复（介绍结果、说明下一步建议）
  │
  ▼
⑤ 持久化对话（user + assistant 消息，assistant 带动作元数据）
  │
  ▼
⑥ 前端：对话流追加消息 + 数据面板按"变更分区"自动刷新
```

### 3.2 为什么决策与总结分两次调用（而不是一次工具调用）

已确认 provider 层（base-provider / openai-compatible / sdk 各实现）**没有 tools / function calling 支持**，chatStream/chatSync 只接受纯文本消息。因此：

- 决策调用：一次轻量调用，约束输出 JSON（max_tokens 较小，秒级返回），前端可先显示"AI 正在思考…"。
- 执行动作：动作内部已有流式事件（如生成人物时 AI 逐 token 输出 JSON），引擎把进度转成前端可见的"正在生成人物卡片…"。
- 总结调用：流式输出给用户看，用户感知为"思考几秒 → 生成中（有进度）→ 结果流式呈现"。

若未来 provider 支持工具调用，可把②④合并优化，协议层预留即可，不影响本次实现。

### 3.3 组件划分（后端）

```
src/core/services/longwriting/agent/
├── agent.types.ts          # AgentAction 类型、决策 JSON 类型、执行摘要类型
├── agent-workflow.service.ts  # 编排：sendMessage(projectId, message) → ①-⑥
├── agent-context.ts        # 组装决策/总结上下文（数据摘要 + 历史 + 生产状态）
├── agent-actions.ts        # 动作分发：actionType → 现有生成方法/落库通道
├── agent-deps.ts           # 依赖规则表 + 生产状态计算（数据存在性）
└── agent-events.ts         # 事件推送（longwriting:agent:${projectId}）
```

复用（不重写）：
- 现有生成方法：generateStoryOverview / generateCharacters / generatePlots / generateOutlineStory / generateChapter / polishBackground / generateLocations / generateFactions / generateSkillsItems
- 现有落库通道：updateStoryOverview / createCharacter / BATCH_CREATE_PLOTS / createOutline / SAVE_CHAPTER / updateBackground / createLocation / createFaction / createSkill / createItem…
- 对话历史表：lw_design_conversations + lw_design_messages（已建，repository 已可用）
- 摘要格式化：context/entity-formatters.ts（已有格式化器）

## 4. Agent 决策协议

### 4.1 决策调用输出格式（system prompt 约束为纯 JSON）

```json
{
  "reply": "好的，我来为故事补充一位女二号。",
  "actions": [
    {
      "type": "generate_characters",
      "params": {
        "requirements": "增加一位女二号，与主角有情感纠葛，性格外冷内热"
      }
    }
  ]
}
```

- `reply`：给用户看的简短回应（可选；若 actions 非空则用摘要生成最终回复，reply 只用于无动作轮次）。
- `actions`：0~N 个，引擎按顺序执行。
- 决策 JSON 解析失败 → 降级为"无动作纯对话"（见 §9）。

### 4.2 动作类型清单（v1）

| type | 含义 | 对应生成方法 | 落库目标 | 前置依赖（最小） |
|---|---|---|---|---|
| `generate_overview` | 生成/重做故事概要 | generateStoryOverview | lw_story_overviews | 无（允许只有想法） |
| `generate_characters` | 生成/补充人物 | generateCharacters(+requirements) | lw_story_characters | overview.coreIdea 存在 |
| `generate_world` | 生成世界设定（背景/地点/势力/技能/物品，按 enabledFeatures 裁剪） | polishBackground / generateLocations / generateFactions / generateSkillsItems | lw_backgrounds / lw_locations / lw_factions / lw_skills / lw_items | overview 存在 |
| `generate_plots` | 生成/补充故事线 | generatePlots | lw_plots | overview 存在 |
| `generate_outline` | 生成大纲（可指定 structureLevel） | generateOutlineStory | lw_outlines | overview 存在 |
| `write_chapter` | 写章节（可指定 outlineId/targetWords；缺省由引擎选下一未写节点） | generateChapter | lw_chapters + 章节后处理（状态提取/图谱事件） | 存在未写的大纲叶子节点 |
| `update_entity` | 修改已有实体（用户提出修改意见） | —（直接调现有 update 通道，AI 输出 patch） | 各实体 | 实体存在 |
| `delete_entity` | 删除已有实体 | —（现有 delete 通道 + 图谱边级联清理） | 各实体 | 实体存在 |

> 注：`generate_characters` / `generate_plots` 天然支持"增量补充"——生成方法已注入"已有实体名"避免重复（generateCharacters 的 existingCharacters 注入已实现），引擎在落库时**按名称去重，只入库新实体**，这样"再补一个女二号"语义正确（AI 可能仍返回整批，但只有新增的会入库）。

### 4.3 依赖规则（引擎内置，约束而非顺序）

- 引擎只检查"最小前置条件"，不强制顺序。
- 不满足前置时：**不执行该动作**，把"缺什么"作为提示交给 AI 总结阶段说明，AI 给出替代路径（如"还没有大纲，要不要我先搭一个粗大纲？"）。
- 例外：用户明确要求强推时，引擎允许 `generate_outline` 在只有 overview 时执行（AI 决策时自行权衡），但 `write_chapter` 必须有 outline 节点（这是硬依赖，正文必须挂在大纲节点下，数据结构决定）。

### 4.4 生产状态（每次组装上下文时实时计算）

```
{
  overview: { exists, title, storyType, coreIdea, summary, coreConflict, estimatedChapters },
  characters: { count, names[] },
  world: { background: bool, locations: n, factions: n, skills: n, items: n },
  plots: { count, titles[] },
  outline: { count, writtenChapters, unwrittenChapters },
  chapters: { written: n, totalWords }
}
```

- 由 AgentDeps 用现有查询通道实时计算（不持久化硬状态，数据即状态）。
- 直接拼进决策/总结上下文中，AI 据此判断"下一步该做什么"。

## 5. 界面设计（重点：回答"一个界面显示不完"）

### 5.1 总体布局：左右分栏

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏 [返回]  项目名                    [进度带] [图谱] [设定] [高级]│
├───────────────────────────────────┬──────────────────────────┤
│ 对话区（自适应宽度，可滚动）          │ 数据面板（固定 360-400px）  │
│                                   │ ┌──────────────────────┐ │
│  AI: 你好！我是你的写作助手，         │ │ Tab 条：              │ │
│      把你的想法告诉我就好…            │ │ 概览|人物|世界|故事线|  │ │
│                                   │ │ 大纲|章节             │ │
│  [你] 我想写一个明朝锦衣卫的故事      │ ├──────────────────────┤ │
│                                   │ │ 当前 Tab 内容（独立滚动）│ │
│  AI: 正在分析你的想法…（决策中）     │ │                      │ │
│  AI: 正在生成故事蓝图…（进度）       │ │                      │ │
│  ┌─────────────────────────────┐  │ │                      │ │
│  │ 📖 故事蓝图（内嵌预览卡）       │  │ │                      │ │
│  │ 标题：《绣春刀·暗夜》          │  │ │                      │ │
│  │ 核心冲突：…  预估 30 章        │  │ │                      │ │
│  └─────────────────────────────┘  │ │                      │ │
│  AI: 已生成故事蓝图，角色草案见      │ │                      │ │
│      右侧「人物」面板。接下来想先     │ │                      │ │
│      设计主角，还是先搭世界观？      │ │                      │ │
│  [下一步] 设计主角   先搭世界观     │ │                      │ │
│                                   │ │                      │ │
│  ┌─────────────────────────────┐  │ │                      │ │
│  │ [输入框：和 AI 对话…]     [发送]│ │                      │ │
│  └─────────────────────────────┘  │ └──────────────────────┘ │
└───────────────────────────────────┴──────────────────────────┘
```

### 5.2 对话区设计

- **消息气泡**：用户消息右对齐；AI 消息左对齐，支持 Markdown 渲染。
- **AI 消息内嵌"产物预览卡"**（回答"生成了什么马上看得见"）：
  - 动作执行后，AI 消息里插入对应数据的迷你预览：
    - 生成人物 → 横向角色小卡（姓名 + 定位 tag + 一句话简介）
    - 生成故事线 → 情节列表（title + 摘要）
    - 生成大纲 → 章节树摘要（卷/章数）
    - 写章节 → 章节卡（章节名 + 字数 + "打开阅读"按钮）
  - 预览卡点击 → 跳转右侧面板对应 Tab 并高亮；数据量大时预览只显示前 3-5 条 + "查看全部 →"。
- **过程消息**（视觉弱化，小字灰显）：决策中 / 正在生成人物… / 已生成 5 位角色。过程消息与正式回复在同一个 AI 消息气泡里演进：先显示过程状态，完成后替换为正式内容。
- **下一步建议 chips**：AI 消息末尾渲染（如"设计主角""先搭世界观"），点击 = 直接把该文本作为用户消息发送。chips 由引擎按"生产状态缺什么"生成候选 + AI 总结时也可补充。
- **输入框**：底部固定，多行自适应，Enter 发送 / Shift+Enter 换行；生成中禁用发送（或允许"打断"）。

### 5.3 数据面板设计（回答"一个界面显示不完"）

右侧面板按数据类型分 Tab，每 Tab 独立滚动，**只渲染当前 Tab**（v-show 保持状态）。数据驱动刷新：agent 事件带"变更分区"，前端自动重拉对应 Tab。

| Tab | 内容 | 空态 |
|---|---|---|
| 概览 | 标题/类型/摘要/核心冲突/预估章节 + 生产状态（各环节 ✓/○） | 尚未生成概要 |
| 人物 | 卡片网格：头像占位圆 + 姓名 + 定位（主角/配角/反派）+ 简介；点击卡片 → 详情/编辑弹窗 | "还没有人物，可以在对话里让我设计" |
| 世界 | 折叠组：背景设定/地点/势力/技能/物品（按 enabledFeatures 显示组）；组内列表可点开详情 | 空组显示引导文案 |
| 故事线 | 纵向时间线：序号 + 标题 + 摘要 + 涉及角色 tag | 空态引导 |
| 大纲 | 树形（卷→章→节），节点显示状态/字数；点击章节 → 阅读/编辑弹窗 | 空态引导 |
| 章节 | 列表：章节名 + 字数 + 更新时间 + 状态；点击打开阅读弹窗（可续写/重写） | 空态引导 |

- **进度带（顶栏）**：想法 ✓ → 人物 ✓ → 世界 ○ → 故事线 ○ → 大纲 ○ → 章节 ○。**只作状态展示**，点击跳到面板对应 Tab；**绝不是流程导航**（避免回到"步骤条"的老路——用户是通过对话推进，不是点进度带）。
- 面板 Tab 与对话联动：对话中生成人物 → 面板自动切到/刷新"人物"（或仅刷新不切换，用户可配置；v1 默认刷新当前 Tab + 角标提示"人物 +5"）。

### 5.4 设计原则

1. 对话是**唯一指令入口**；面板是**只读展示 + 详情/编辑弹窗**（编辑也通过对话表达，但允许直接在弹窗改并保存，改完自动同步）。
2. "生成了什么"两层可见：对话内嵌预览（即时）+ 面板（常驻完整）。
3. 进度带是**镜子**不是**闸门**。
4. 所有展示复用现有数据与尽量复用现有组件（OutlineStage 树、ChapterStage 阅读等），不另造数据模型。

## 6. 数据流与 IPC

### 6.1 新增 IPC 通道（沿用 CHANNELS + ipcBridge.handle 模式）

| 通道 | 参数 | 说明 |
|---|---|---|
| `AGENT_SEND` | (projectId, message) | 发起一轮 agent 循环；内部经事件流推送过程，invoke 返回 { conversationId } |
| `AGENT_HISTORY` | (projectId) | 返回对话历史（最近 N 条，含元数据） |
| `AGENT_CANCEL` | (projectId) | 中断当前轮（决策/动作/总结） |
| `AGENT_STATE` | (projectId) | 返回生产状态（面板概览 Tab + 进度带用） |

事件通道：`longwriting:agent:${projectId}`（preload 暴露 `onAgentEvent(projectId, cb)`，返回退订函数，同 onGenerateEvent 模式）

事件类型：
```
{ type: 'stage', stage: 'deciding' | 'acting' | 'summarizing' }
{ type: 'action:start', actionType, label }        // "正在生成人物…"
{ type: 'action:done', actionType, summary, changed: string[] }  // changed=变更分区
{ type: 'reply:start' }
{ type: 'reply:content', content }                  // 总结流式增量
{ type: 'reply:done', suggestions: string[] }       // 下一步 chips
{ type: 'error', error }
```

### 6.2 生成动作的流式进度复用

现有生成方法已通过 `longwriting:generate:${eventId}` 推送 content 事件（generateOutlineStory 还推 progress）。Agent 动作执行时：
- 引擎为每个动作生成独立 eventId，订阅其事件并转译为 `action:progress` 推给前端（或直接复用原事件通道，前端同时订阅两个通道）。
- 决策/总结调用的 eventId 与动作 eventId 区分，避免混淆。

### 6.3 落库后一致性闭环

- `write_chapter` 落库后，沿用现有 ChapterWizardStep 的流水线：`extractChapterEvents`（事件提取+图谱建边）→ `extractEntityStates`（状态切片）→ `extractChapterStateSummary`（章节状态摘要）→ 向量记忆提取。**写一章 = 数据全链路更新**，图谱自动长出节点/边（已有能力，直接调用）。
- 动作失败（AI 返回格式错误等）→ 执行摘要记 error，AI 在总结中向用户解释。

## 7. 对话持久化

- 每个项目一条 conversation：`lw_design_conversations`（stage='agent'，projectId 索引已建）。

- 重进项目：拉历史渲染对话流；数据面板直接从数据库读（天然持久）。

## 8. 容错与降级

| 场景 | 处理 |
|---|---|
| 决策 JSON 解析失败 | 降级为无动作纯对话：直接把用户消息 + 项目摘要交给总结调用，AI 以顾问身份回复 |
| 动作执行失败（前置缺失/AI 格式错误） | 不中断其余动作；失败进执行摘要；总结阶段 AI 说明原因并给替代路径 |
| 用户消息是提问/闲聊（无生成意图） | actions 为空，跳过执行，直接总结回复 |
| 用户中途打断（点发送时正在生成） | 输入框保留但发送禁用；提供"打断"按钮 → AGENT_CANCEL（abort 决策/总结/动作的 AbortController） |
| 长对话 token 增长 | 历史只取最近 20 条 + 项目数据用摘要（entity-formatters 复用）；ContextBuilder compressor 思路可参考 |
| AI 决策到一半用户关窗 | 对话已逐条持久化，重进恢复；未完成轮次丢弃 |

| 模块 | 关系 |
|---|---|
| 高级模式（7 阶段） | **保留**。对话式工作流成为项目默认入口；高级模式保留完整编辑能力（右上有"高级"按钮切换，数据同源） |

| 评论类项目 | 本轮不动（评论项目仍走评论大纲/评论章节流程，不在对话式工作流范围） |
