# Part 7 · 价值复盘：局域网协作功能是否值得做？（07/07）
> 状态：复盘（2026-08-27）｜本文档为**独立的价值评估**，结论基于对本项目现状、用户场景、
> 技术成本与替代方案的深度分析。与功能设计（01~05）无关的部分可独立决策。

## 一、功能价值主张回顾（需求原文）

1. 局域网内自动发现其他用户（设备），可邀请加入团队；
2. 共享资产（选成员/团队）；
3. 像本地资产一样使用共享资产（对话 @ / 工作流引用）；
4. 工作流人工环节指派给团队成员，对方 App 弹提示处理。

## 二、真实用户场景分析（最重要的一步）

**本项目是谁在用？**
- 这是一个**个人 AI 工具箱**（Electron 桌面应用），当前数据库单用户
  （`local-default-user`），用户是独立开发者自己；
- 多租户（users 表）是为 **Web 部署版**设计的，不是桌面局域网协作；
- 资产、工作流、长文、套图等全部功能都是**单人使用**模式。

**局域网协作的适用场景假设**：
- 假设 1：同一公司/家庭局域网内**多台电脑各装 The Bot**，多人协作；
- 假设 2：这些人愿意安装一个**个人开发的私有工具**、注册设备、维护信任名单；
- 假设 3：他们之间需要共享资产（图片/文本/模板）或协作审核工作流环节。

**逐条审视假设**：
- 假设 1：成立的概率取决于用户是否有"多机协同"的现实需求。开发者自用场景下，
  更常见的需求是**自己两台电脑（家里/公司）同步数据**——但那是"同一身份跨设备同步"，
  **不是本设计**（本设计是"不同身份成员互访"，成员=设备、无身份合并，00 §5.1 明确
  一人多设备=多成员，V1 不做合并）。**这是个根本性错配**：
  - 若真实需求是"我的两台电脑数据互通"→ 应该做**身份同步/数据同步**（Syncthing 模式），
    而不是"团队成员共享/指派"；
  - 若真实需求是"与同事协作"→ 同事为什么要装你的私有工具？他们大概率用
    微信/钉钉/网盘/飞书——**共享资产这件事有大量成熟替代品**。
- 假设 2：新用户要理解"设备身份/邀请码/信任名单"概念，且要维护多端安装——冷启动成本高；
- 假设 3：工作流指派要求双方**同时在线 + 安装同一私有应用 + 在工作流里显式配置 assignee**，
  这是极强的使用前提。

## 三、成本盘点（诚实评估）

### 3.1 直接成本
- **开发**：约 13~15 人天（06 §五），P1~P5 五个部分 + TDD；
- **新增依赖**：bonjour-service（mDNS）—— 需评估其 Electron 兼容性/维护状态；
- **长期维护**：P2P 网络层（发现/重连/协议版本）是**持续维护负担**——协议升级、防火墙、
  网络环境差异、Electron 升级兼容，都会长期消耗维护精力；
- **复杂度税**：协作层贯穿引擎（assignee）、资产（影子行）、事件（tapEvents 桥）、UI（待办）
  四个子系统，任何一处改动都要考虑协作分支——**对后续所有功能的开发都是负资产**。

### 3.2 机会成本
- 13~15 人天可以换来的替代项：**一套完整的"多设备数据同步"**（对自用用户价值更高）、
  知识库/长文/套图体验打磨、Web 版功能补齐、或纯粹的功能质量提升。
- 考虑到这是**个人开发者的业余项目**（无团队、无商业压力），15 人天是很大的投入。

### 3.3 隐性成本
- 安全面扩大：P2P 监听端口 + 信任名单 + 邀请码，引入新的攻击面（虽为内网信任模型，
  但"局域网任意设备可尝试连接"本身是风险敞口）；
- 调试成本：跨实例时序问题（离线/重启/重试）极难本地复现，排障耗时；
- 用户心智负担：设置页多一个"协作"模块，对 99% 只用单机功能的用户是噪音。

## 四、收益盘点

| 功能 | 真实收益 | 打分（0-10） |
|---|---|---|
| 局域网发现 + 配对 | 无独立价值（纯地基） | 0（必要但不产生价值） |
| 团队管理 | 无独立价值 | 0 |
| 共享资产（图/文/模板） | 若存在"同事间互传素材"场景，价值 5——但替代品（网盘/微信）已覆盖 90% | 2 |
| 对话 @ / 工作流引用共享资产 | 在共享成立的前提下才有价值；且要求源在线 | 1 |
| 工作流指派 | 强前提（同事装应用 + 同时在线 + 配置指派）；工作流本身是"单人自动化"工具，
  指派场景属于"工作流 → 人工介入点"，把"人"变成团队成员，逻辑上成立，
  但**目标用户群（个人开发者）几乎不会用到** | 1.5 |
| 系统通知/待办 | 是 04 的配套设施，无独立价值 | 0 |

**总收益评分：约 5/10 的价值上限，且全部集中在"共享资产"一个点，且被替代品稀释。**

## 五、替代方案对比（诚实结论）

| 需求 | 成熟替代 | 替代成本 | 本方案优势 |
|---|---|---|---|
| 共享文件/图片/模板 | 网盘（百度/阿里）、微信/钉钉文件、LocalSend（已开源成熟） | 几乎为零 | 与资产中心/工作流引用**集成**（唯一优势） |
| 工作流协作 | 无直接替代（工作流指派是独有） | — | 独有，但前提苛刻 |
| 多设备数据互通（自用） | Syncthing/网盘自动同步 | 低 | 本方案**不支持**（身份不合并） |

**结论：本方案唯一的真实差异化 = "共享资产直接进入本应用的资产中心/对话/工作流引用"。
但为这一个差异化，要付出 P2P 网络层 + 团队 + 指派 + 通知四个部分的全套成本。**

## 六、对"工作流指派"单独的价值审视（用户关心的点）

用户明确问"这个功能是否有价值"，指派是最复杂的一块（04），单独评估：

**支持方的论点**：
- 工作流引擎已有 waiting_review 挂起/恢复机器，指派是"顺水推舟"（04 证明改动可控）；
- 多人协作审核是真实的企业场景（Bisheng/Coze 都有此能力，00 文档参考过）。

**反对方的论点**：
- 本项目的使用者是**个人**，工作流是个人自动化工具；"指派给团队成员"意味着
  **至少两方都深度使用本应用**——这不是个人工具的自然延伸，而是"产品转型为团队协作工具"，
  与项目定位（个人 AI 工具箱）冲突；
- 引擎扩展本身（E1~E4）是有价值的（**为未来多用户 Web 版预留处理人能力**），
  但**跨实例部分（inbox/决策 RPC/边界处理）是纯局域网协作成本**；
- 如果未来做 Web 多用户版（中心化服务器），处理人/指派可以**零 P2P 成本**实现
  （用户表已存在、事件已按 userId 路由）——局域网 P2P 版本的技术路线反而**不可复用**。

**关键洞察**：`assignee` 概念（处理人）的价值独立于局域网；而"P2P 跨实例"是实现它的
**最贵路径**。若为未来多用户版铺路，引擎侧 E1~E4 值得做；P2P 侧（01/02/04 的跨实例部分）
应等"是否转向团队协作产品"的决策再定。

## 七、最终建议（三档）

### 方案 A：不做（推荐度 ★★★★★ 若目标是"个人工具打磨"）
- 理由：成本 15 人天、收益上限 5/10、替代品覆盖 90% 共享需求、与产品定位冲突；
- 保留：无。01~06 文档归档备查。

### 方案 B：只做"处理人概念 + 中心化多用户"（推荐度 ★★★★ 若目标是"Web 版多用户"）
- 引擎侧 E1~E4（assignee 字段/校验/事件）**独立实施**（约 2 天，TDD 可测）；
- 放弃 P2P 局域网全套；未来 Web 多用户版直接在中心化架构上实现指派（用户表现成）；
- 收益：处理人能力就位，成本 2 天，无 P2P 维护负担。

### 方案 C：全量做（推荐度 ★★ 除非有明确的"同事协作"实证需求）
- 前提：必须有**真实的多机协作需求**（如"我和同事每周互传素材并互相审核流程"），
  且已排除网盘/微信替代；
- 建议实施前先做 **P1 PoC**（06 §四）：公司网 mDNS 可用性 + 防火墙放行是硬门槛，
  PoC 失败则整个方案不可行，直接回退方案 B。

## 八、如果做，最简有价值切片（V0 缩减建议）

假设选择方案 C 且 PoC 通过，为控制成本，建议把范围砍到：
- **砍掉**：团队管理（02）首版 → 直接"成员 = 已配对设备"，共享/指派目标=设备多选；
  系统通知（05 消费层）→ 只做应用内 ElNotification；
- **保留**：P1 发现/配对/连接（地基）、P3 事件桥、P4 共享资产（text/json/file）、
  P5 指派（仅 human-review，form-collect 文件回传延后）；
- **结果**：约 8~9 人天，覆盖"共享资产 + 指派通知"核心闭环，砍掉团队/系统通知/表单文件
  三个非核心项。

## 九、复盘结论（一句话）

**局域网协作对当前"个人 AI 工具箱"定位是负资产：成本高（13~15 人天 + 长期维护）、
收益低（共享有替代品、指派无使用场景）、与产品定位冲突；唯一值得提前做的是引擎侧
"处理人"概念（约 2 天），为可能的中心化多用户版铺路——P2P 局域网部分建议暂缓，
除非出现明确的多人协作实证需求。**
